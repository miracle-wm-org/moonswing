### Rendering backend (`linux/runner/my_application.cc`)

**The shell runs on Skia, and Impeller is switched off in the runner rather
than at the command line.** Impeller's GLES backend is the engine's default on
Linux and it is the single largest performance fact about this shell — bigger
than anything in the Dart tree by an order of magnitude.

Measured against a live miracle session, an **idle** shell showing nothing but
the bar and its ticking clock:

| backend | raster mean | p50 | p90 | max |
|---|---|---|---|---|
| Impeller GLES | 55.9 ms | 53.3 | 67.6 | 95.5 |
| Skia | **17.1 ms** | 15.3 | 23.3 | 32.6 |

Impeller encodes every draw as an individual GL operation through its reactor:
~574 `ReactorGLES::Operation`s **per frame** (38,486 across 67 frames), plus
~314 `TexImage2DInitialization`s. Scrolling a settings pane ran at 6.5 fps
under it and 22.8 fps without, and `ReactorGLES` leaves the timeline entirely.
Throughout all of it the **UI thread sat at 1.8 ms idle and 4.4 ms scrolling**,
so none of this is Dart-side work and no amount of repaint containment reaches
it — which is the thing to remember before optimizing a widget tree here again.

Three things a change to this has to keep true:

- **It is a compiled-in default, not a flag.** `flutter run --no-enable-impeller`
  reaches the engine as a `FLUTTER_ENGINE_SWITCH_*` environment variable, so it
  cannot help the *shipped* artifact: the snap and a `make install` build would
  both keep the slow default however carefully a developer invokes the tool.
  Setting it on the `FlDartProject` is what makes the fast path the one users
  get, and it costs the snap nothing — no wrapper change and no staged library,
  because the decision is in the binary.
- **`GRACEFUL_SHELL_IMPELLER=1` is the way back, and `flutter run
  --enable-impeller` is not.** The runner sets the project property explicitly,
  so the env var is the override that exists; use it to reproduce the table
  above or to re-test after an engine bump.
- **This is expected to be temporary.** Impeller's GLES backend is under active
  development, and the machine these numbers came from carries both an Intel
  iGPU and a discrete Radeon (with `eglinfo` reporting llvmpipe on the core
  profile), so the fault may be in which context it lands on rather than in
  Impeller everywhere. Re-measure with the env var before assuming it still
  holds.
- **Why the shell is hit so much harder than a plain app is not known.** A
  standalone `flutter create` benchmark on the same machine — flat text, a
  `CustomPainter`, and a scene of several hundred `ClipRRect` + `Opacity`
  layers — shows Impeller only about 1 to 1.5x slower than Skia, near the noise
  floor, with no scene reproducing anything like the 3.3x measured here. So the
  cost is coming from something this shell does that a single opaque window
  does not: ~7 transparent layer-shell surfaces composited per frame, the
  embedder's multi-view compositor path, or the sheer layer count of a real
  UI. That is worth identifying before anyone tries to report this upstream —
  the shell's own numbers are reproducible, but they are not yet reduced to a
  minimal case.

System dependencies required at build time: `libgtk3`, `gtk-layer-shell`, `libasound2-dev`, `libmpv-dev`.

Required at runtime for the lock screen: `libgtk-session-lock0` (`ext-session-lock-v1`) and `libpam` — both loaded with `dlopen`, so the shell builds and runs without them; only locking is unavailable.

### Packaging (`snap/snapcraft.yaml`, `.github/workflows/`)

A **classic** snap, built nightly from `main` and published as a rolling `nightly` release. Classic confinement is what makes the rules here unusual: the snap runs in the host namespace, so the host's libraries are on the default loader path and `LD_LIBRARY_PATH` only *prepends* `$SNAP`.

Five things a change here has to keep true:

- **Bundle a library only when the host cannot be trusted to have it, or to have a compatible one.** `libgtk-layer-shell0`, `libmpv1`, `libpulse0`, `libasound2` are staged; `libpipewire-0.3`, `libpam`, `libudev`, `libwayland-client`, `libdbus` and the whole GL/EGL/GBM/DRI set are deliberately *not* — the `prime:` exclusion list exists because a bundled core22 Mesa against host DRI drivers produces `libEGL fatal: did not find extension DRI_Mesa version 1`, and the same reasoning kills every other candidate for a client/server version split. **Staging one is only half the job, because `LD_LIBRARY_PATH` only prepends what it is told to.** Debian keeps some libraries out of the triplet directory — `pulseaudio/`, and the `update-alternatives` dirs `blas/` and `lapack/` — and creates the soname link beside them from a maintainer script snapcraft never runs, so a staged copy the loader cannot see is the same as no copy at all. Each such directory has to be named in the `environment:` block explicitly. BLAS and LAPACK arrive through `libmpv` → `libavfilter` → `libpocketsphinx`/`libsphinxbase`, ffmpeg's `asr` filter, which nothing here invokes; they still cannot go in the `prime:` exclusion list the way the Mesa set can, because `DT_NEEDED` is resolved at load and a missing one aborts start-up instead of falling back — on a host with no BLAS installed that is `libblas.so.3: cannot open shared object file` before the first frame.
- **`libgtk-session-lock` is built from source, and stages no GTK.** There is no `libgtk-session-lock0` in core22 (it first appears in resolute), and without it **Lock silently does nothing**. It is dlopened into a process that already has the host GTK3 mapped, so it links by soname at build time and resolves to the host at run time; staging `libgtk-3-0` would put a second, different GTK in the same address space.
- **Portal registration is split in two halves because precedence forces it, and neither half can be dropped.** `portals.conf(5)` searches `$XDG_CONFIG_HOME` → `$XDG_CONFIG_DIRS` → `/etc` → `$XDG_DATA_HOME` → `$XDG_DATA_DIRS`, and **directory precedence beats file specificity**: a user's generic `~/.config/xdg-desktop-portal/portals.conf` out-ranks a desktop-specific `/usr/share/xdg-desktop-portal/mir-portals.conf`. So `snap/hooks/{install,post-refresh,remove}` — thin shims over `snap/local/portal-setup`, staged as `$SNAP/bin/graceful-shell-portal-setup` — write the `/usr/share` copy as a *machine default* for every account, and `snap/local/graceful-shell-wrapper` writes the per-user copy that is the only one high enough to actually override an existing preference. A hook cannot do the second half: it runs as root with no `SNAP_REAL_HOME` and no idea whose session it is registering for. Both write `miracle-wm-portals.conf` **and** `mir-portals.conf`, because `XDG_CURRENT_DESKTOP` is `miracle-wm:mir` and which name is reached first follows that list. Three invariants inside this: the hooks are **marker-guarded** (`# graceful-shell-snap-managed` appended to every file they write; anything without it is a distro's or a user's and is neither rewritten nor deleted), they are **never fatal** (a non-zero `install` hook aborts `snap install`, and `/usr` is read-only on an immutable host — the per-user copy is the fallback), and `remove` deletes per-user files only from the manifest the wrapper records in `SNAP_USER_COMMON`, filtered to `.portal` files, so it cannot eat a `make install-portal` file or a conf the user edited. `/etc/pam.d/graceful-shell` still needs root at a path snapd will not manage; `PamAuthenticator` falls back to the `login` service.
- **The wrapper restarts xdg-desktop-portal, once per revision, and never edits a conf it did not write.** xdg-desktop-portal reads `.portal` files and preferences only at start-up, so writing them is half the job — the wrapper used to print instructions telling the user to do the other half. It now runs `systemctl --user try-restart xdg-desktop-portal.service` (`try-restart`, so a session with no systemd user instance is not forced to start one; only the frontend, never the backends) and gates on a `SNAP_REVISION` stamp in `SNAP_USER_COMMON`, because a refresh can change what is shipped but a restart on every shell start is noise. Two refusals are deliberate: `[screenshare] enabled = false` skips registration entirely — the Dart side then declines the bus name, so registering anyway would point the config at a name nobody owns and break ScreenCast rather than leave it on wlr — and an existing `*-portals.conf` routing ScreenCast elsewhere is reported, not overwritten, which also means the *other* name is left unwritten (writing it would silently out-rank the file we just promised to honour).
- **The Flutter revision is pinned, and `flutter-master.yml` is why that is safe.** The shell is built on Flutter's experimental windowing API; the snap used to clone `master` at HEAD, so an upstream rename landing overnight broke the *release artifact*. The daily `flutter-master.yml` job now carries the early-warning role, and the pin is bumped to a revision that job has proven green.

## Architecture

Graceful Shell is a **Flutter Linux desktop application** that renders Wayland layer-shell panels (taskbars) and an optional wallpaper window using GTK and the `gtk-layer-shell` library.

### Startup flow (`lib/main.dart`)

`main()` is split in two by `runWidget`, and which side of that line a piece of start-up work sits on is the whole design. Above it is only what the first frame cannot be drawn without; below it is everything else.

1. All `Module` subclasses are registered in the global registry.
2. `AppConfig.load()` reads `~/.config/graceful-shell/config.toml`, calls `Module.loadAll()` to push per-module config into each registered module, and returns typed config objects. `ConfigStore.initShared()` then reads the same file into the live, writable store.
3. `startThemeService()` seeds the shipped themes into `~/.config/graceful-shell/themes/` and resolves the one `config.toml` names; `startDesktopService()` reads the pinned icons; `startSystemStatsService()` configures the stats store without starting it polling. All three are synchronous reads of already-parsed config.
4. `initSessionLock()` installs the windowing owner, then `runWidget` builds the root `WindowManager` — Flutter's own, from the experimental windowing API — which renders every window in the one `WindowRegistry` it publishes. Flutter's experimental multi-window API (`ExtendedWindowingOwnerLinux`) creates one `LayershellWindowController` per panel per monitor and optional background controllers, from `_GracefulShellRootState.initState`.
5. A post-frame callback hands every remaining start-up task to `ShellServices` — Wayland outputs and global shortcuts, Miracle IPC, the notification daemon, the tray watcher, PulseAudio and the backlight, the ScreenCast portal backend, the polkit authentication agent, logind's power-key inhibitor, and the application index.

Steps 1–3 are the only `await`s before the first frame, and they are two reads of one small TOML file: every native window's geometry comes out of them, so there is genuinely nothing to render until they land.

### Global start-up state (`lib/shell_services.dart`)

`ShellServices` is a `ChangeNotifier` holding a `ServiceStatus` (`loading` / `ready` / `failed`) per `ShellService`, and `ShellServicesScope` is the `InheritedNotifier` that hands it to a window's subtree. `main()` gives it each task instead of awaiting one, and any widget that needs a task's result reads `ShellServicesScope.isLoading(context, …)` and shows a loader until it settles.

Five things a change here has to keep true:

- **Nothing below `runWidget` may be awaited above it.** Every one of these is either I/O the shell cannot make faster (a D-Bus name request, a socket connect, a Wayland round-trip) or a walk of the whole system, and none of them is needed to *paint* — that is what made the shell take seconds to show a bar. A new service belongs in `_startShellServices`, with a `ShellService` value and a consumer that knows how to render its absence.
- **The tasks start from a post-frame callback, and `run` gives each its own event-loop turn.** The application index is thousands of FFI round-trips with no suspension point in them; started any earlier — or on a microtask alongside the others — it would hold the isolate straight through the frame it is supposed to come *after*. Registration order is therefore turn order: the I/O-bound ones go first so their round-trips are already in flight, and `applications` goes last.
- **A loader is not decoration; it is the difference between "not yet" and "none".** Every one of these services fails soft, so an empty list is a legitimate final state. `LauncherOverlay` and `AppChooserCard` take a `loading` flag for exactly this — "No applications" is a lie the user acts on. Both also re-rank in `didUpdateWidget`, because the index can land *under* an already-open launcher.
- **Services throw; `run()` records.** The failure contract is documented on `ShellServices.run` and it is the one that makes `ServiceStatus.failed` mean something: a genuine failure (bus unreachable, name request errored, missing protocol) propagates out of the `start*Service` function and `run()` records it, while a *graceful decline* — another daemon already owns the notification/tray name, a feature switched off in `config.toml` — logs and returns normally (or is `skip()`ped by `main()`), settling `ready`. A service that swallows its own genuine failures makes its loader resolve "ready" with the feature dead, which is the lie this contract exists to prevent.
- **`ShellServicesScope.isLoading` answers false when there is no scope.** A module built alone in a widget test has no `main()` behind it, so nothing is pending and a loader would never come down. That default is what keeps the modules testable in isolation, and it is why the getter is on the scope rather than on the store.
- **It is not a singleton.** Unlike `OsdStore`/`TrayStore`/`ThemeStore` it is constructed in `main()` and passed to `GracefulShellRoot`, the way `MiracleManager` is, so a test can build one carrying whatever statuses the case needs.

- **A start-up status is read through the scope, never from the root's `build`.** The root used to listen to this store as well, because it handed `AppIndex.instance.searchable` down from its own `build` — which meant one service settling rebuilt *every* view the shell owns to deliver a list two overlays read. `_AppIndexBuilder` (`main.dart`) does it instead, and the shape it has is load-bearing: **`AppIndex` does not notify for its initial build** (`start()` → `_rebuild()`, and only `_onApplicationsChanged`/`release()` call `notifyListeners`), so a builder listening to the index *alone* sits on its loader forever. The `ShellServicesScope` dependency is what delivers the first list; the index listener delivers later installs and removals. Both reads have to happen on the one element — split them into nested builders where only the inner one sees the list and the loader never comes down.

The visible consequence is that panels paint before the shell knows which physical display each one is on. `DisplayScope.output` is therefore nullable, `resolveOutput` (`lib/display_provider.dart`) refuses its first-output fallback while `ShellService.displays` is still loading (an output is tracked as soon as its global is advertised but carries no name until its `done`, so mid-enumeration `outputs.first` is simply whichever arrived first — and the wrong display means the wrong workspaces), and `modules/workspaces.dart` renders one button's worth of spinner until either the output or the IPC connection arrives.

**A panel is matched to its output by connector name, and the fallback answers for one output only.** `MonitorInfo` is a *snapshot* taken when the surface was created, while a `WaylandOutput`'s `x`/`y` are rewritten on every `wl_output.geometry` — so matching on make/model/position alone meant that repositioning the displays left *every* panel unmatched, and every one of them then took the same `outputs.first`, which is how both bars came to show one monitor's workspaces. GDK's connector and `wl_output.name` are the same string and neither moves, so the name is tried first; the tuple stays as the second pass for a GDK build that reports no connector. The fallback is now taken only when there is exactly one output — with several, guessing hands every unmatched panel the same answer, which is the bug rather than a mitigation of it. Two things follow: `_syncMonitors` (`main.dart`) has a third branch that replaces a *reconfigured* monitor's `MonitorInfo` in place (creating and destroying nothing), and the root listens to `OutputTracker` as well as to `MonitorWatcher`, because GDK emits neither `monitor-added` nor `monitor-removed` for a reposition and `wl_output.done` is the only signal one produces. That listener is now the panels' alone: miracle re-homes a removed output's workspaces onto another output with no workspace event, which the shell used to infer from its own `wl_output` view through a `MiracleManager.outputsRevision` counter — but miracle.dart 2.0 decodes `OutputEvent`, so both the workspace row and `WorkspaceAppsStore` take that straight off the IPC stream and the counter is gone.

### Module system (`lib/module.dart`, `lib/modules/`)

`Module` is an abstract class with three responsibilities:
- `configKey` — unique string key matching the TOML `[modules.<key>]` section.
- `loadConfig(map)` — called once at startup with the module's TOML subtable.
- `builder` — a `WidgetBuilder` that returns the widget rendered inside the panel.

Modules are registered before config is loaded (`Module.register(...)` in `main()`) and retrieved by name at render time (`Module.lookup(name)`). Adding a module means one `Module.simple(configKey:, fromMap:, builder:)` (or `Module.plain` for a module with no options) as a top-level `final` in its file, plus `Module.register(<name>Module)` in `main.dart` — fourteen subclasses used to spell that identical class by hand. `test/module_registry_test.dart` pins the registry. The one non-trivial `fromMap` is the system monitor's, which pushes its config into `SystemStatsStore` as a side effect, because the overlay's System tab reads the same settings even when no panel carries the module.

The desktop grid has its own registry of the same shape — `DesktopWidgetRegistry` (`lib/desktop/widgets/desktop_widget.dart`), registered from `main()` beside the modules. The two are deliberately separate: a module is a strip of a panel sized by its content, a desktop widget is a rectangle of grid cells the user resizes, and a `DesktopWidgetSpec` therefore carries span limits where a `Module` carries a `configKey` and a `fromMap`.

**`Module.configChanges` is what keeps `[modules.*]` options live, and it is not optional.** Module config is pushed *imperatively* — `loadAll` mutates each module's `_config` in place and `builder` is a getter closing over it — so nothing about a module widget's inputs tells Flutter that anything moved. For as long as the root rebuilt every view on every `ConfigStore` notify that did not matter, because the panels were rebuilt anyway and each `builder` was re-read; once `LiveConfigScope` stopped that, toggling *Clock → Show date* in the settings UI would silently have done nothing until the next restart. `_SimpleModule.loadConfig` therefore compares a stringified signature of the raw sub-map (the `ConfigStore._restartSignature` idiom — the config classes are a dozen unrelated types with no equality between them, but the table they came from is always comparable), returns whether it moved, and `loadAll` fires the notifier once per sweep. `_PanelMainState._buildModule` listens per module, so a `[modules.clock]` edit rebuilds the clock and nothing else. The guard is also what stops the system monitor's side-effecting `fromMap` re-running on every keystroke.

#### Workspace app icons and urgency (`lib/modules/workspace_apps.dart`)

Each workspace button carries the icons of what is open on it (`show_app_icons`, on by default), which is why `_WorkspaceButton`'s square 16px box is now a *minimum* rather than a fixed size — the buttons are no longer all the same width. It also **breathes in the theme's accent while something on it is urgent** (`flash_urgent`, on by default; `urgent_flash_seconds` is one breath, defaulting to 5). The walk, the store and the `app_id` → icon mapping live beside the module rather than in it, so the two pure halves are plain unit tests (`test/workspace_apps_test.dart`); `modules/workspaces.dart` re-exports `WorkspacesConfig`, so importers still reach it at the module's own path.

Five things a change here has to keep true:

- **It is driven by events, and `wakesWorkspaceApps` is the filter.** `MiracleManager` subscribes to `workspace`, `window` and `output`; the store re-reads the tree on an output event, on the workspace changes that create, empty, rename, move or switch to one, and on the window changes that can move a window between workspaces (`created`/`closed`/`moved`, plus an unmodelled `unknown` — better a wasted read than a stale row). **`focused` is the load-bearing exclusion**: it fires on every alt-tab, so an unfiltered listener would re-read the whole window tree each time. **`urgent` is its twin, on both events that carry it** — miracle.dart 2.1 sends `window`/`urgent` and `workspace`/`urgent` together, and neither moves a window, so waking would be a whole `GET_TREE` per notification for icons that cannot have changed. Both switches are exhaustive, so a change miracle.dart grows later forces a decision here. This all became possible in miracle.dart 2.0 — before it, `Event.fromJson` threw `UnsupportedError` for every type but `workspace` from inside the socket's own data handler, which is why this store polled and why `MiracleManager` could not subscribe to `output` (it inferred output changes from its own `wl_output` view instead, through an `outputsRevision` counter that is now deleted).
- **A read that arrives mid-flight is coalesced, not dropped.** With no timer behind this, a discarded refetch leaves the row stale until the next unrelated event — and opening three windows in a burst is three events over one round-trip. `_fetch` sets `_fetchQueued` and loops rather than returning early, which is the one thing the old poll made unnecessary.
- **`SystemStatsStore`'s lease rule, and the lease is the off switch.** `WorkspaceAppsStore` is one reader for the machine — before this every bar on every monitor would have run its own `GET_TREE` — and the row holds a lease only while `show_app_icons` is on, so switching the option off means no round-trip is ever opened rather than one whose result is discarded. `_fetch` therefore checks the lease *before* the round-trip as well as after: the event listener is attached whether or not anybody is drawing icons. The urgency flash is deliberately **not** part of this lease; see below.
- **A read that finds nothing new must not notify.** Every panel on every monitor listens; `_publish` compares a signature so a burst of window events is not re-laying every bar to redraw identical icons.
- **A tree that will not parse costs the icons, never the row.** miracle.dart 2.0 decodes tolerantly, but a reply it cannot read at all is still an adornment failing: the workspace buttons must still render and still switch. Same for the stream's `onError`, which 2.0 uses to report an undecodable payload rather than tearing the stream down — an event we cannot read is one refetch we do not make, and nothing more. Note also that the walk uses its own `containerAppId` predicate rather than `ContainerNode.isWindow`, which the library defines as `window != null` — that is the *X11* window id, so under Wayland it is null for very nearly everything on screen.
- **The icon cache keeps strings, never the `AppEntry` they came from.** An entry out of `AppIndex` holds a `GAppInfo*` the index unrefs on its next rebuild and one out of `loadAppById` is ours to dispose, so copying the two fields the row draws makes both lifetimes somebody else's problem. Resolution is `StartupWMClass=` first (the entry declaring this very mapping — `AppEntry.startupWmClass` was added for it) and spelling heuristics only after; the cache is cleared on an `AppIndex` notify, because it is keyed on the `app_id` alone.

**The flash costs no I/O at all, and `shouldFlashWorkspace` is the whole of it.** miracle.dart 2.1 (`miracle-wm#952`) made `WorkspaceResult.urgent` real — it was documented as "legacy, and always `false`" before, so a flash driven by the list the buttons come from could not have fired — and it propagates urgency up the tree, so a workspace's own flag answers for every window on it, floating ones and ones nested in split containers alike. That flag is on the `GET_WORKSPACES` entry the button is *already* built from, and the change arrives as a `workspace` event the row is *already* subscribed to (the library emits `workspace`/`urgent` beside `window`/`urgent` for exactly this reason: "so that a bar watching workspaces rather than windows still sees the change"). So `flash_urgent` takes no lease on `WorkspaceAppsStore`, opens no `GET_TREE`, and works with `show_app_icons = false` — and `wakesWorkspaceApps` answers **false** for both urgency events rather than true. Reading it out of the tree instead is the tempting shape and it is strictly worse on every count: a round-trip per notification, a lease the icons' off switch would have to share, and a second copy of the propagation the compositor already does.

**The focused workspace never flashes**, which is one guard doing two jobs that happen to agree: the user is already looking at it, and it is the one place the flag can go stale — miracle clears urgency once the window is focused, and the `GET_WORKSPACES` that would say so is still in flight on the frame the switch lands.

`UrgencyFlash` (`lib/modules/workspaces.dart`, public so `test/workspace_urgency_test.dart` can pump it directly) is the animation, and four things about it are load-bearing:

- **Nothing about it exists at rest.** `_WorkspaceButtonState.build` wraps the button in it *only while urgent*, so the ticker is created when the alarm is raised and disposed when it clears. The always-mounted alternative — one widget per button gated on a flag — is a `Ticker` per workspace per monitor running for the life of a shell that is usually being told nothing at all, which is the rule `lib/timers/` and `lib/tux/` state for their own timers.
- **It is three layers — fill, wash, label — and the wash is the middle one.** One wash across the whole button is the obvious shape and it *erases the number the user switches by* at the top of every breath, which reads as the bar glitching rather than as an alarm. The label is therefore the `Stack`'s **last** child and its only **unpositioned** one, so it paints over the wash and is what sizes the surface; the two properties are one fact and a reorder for the paint would take the sizing with it. Keeping the fill separate is also what lets the `AnimatedContainer` under it go on animating hover and press through `ShellDurations.fast` exactly as it does at rest. The wash is `IgnorePointer`ed, because `RenderDecoratedBox.hitTestSelf` answers for any non-null fill and a full-size box across the button would otherwise swallow the tap that switches workspace — `HoverRegion`'s trap, from the other side.
- **The repaint stops there, twice.** A bar has no repaint boundary of its own, so a colour changing every frame in one dot would re-record the whole panel picture — the clock, the tray, every other workspace — sixty times a second, which is exactly the cost the calendar tab documents paying for a second hand. The outer boundary keeps the damage inside the button; the inner one keeps the button's own label and app icons out of the layer that is actually repainting.
- **The phase comes off the wall clock, so every urgent button agrees.** Each bar is its own FlutterView with its own ticker, and two workspaces going urgent a second apart would otherwise breathe out of step — a row of dots pulsing at random phases reads as a rendering fault rather than as one alarm. Offsetting each controller by the phase it *started* at cancels its own start time out of the sum. The breath itself is a raised cosine (`urgencyFlashWash`) rather than a linear ping-pong, which reverses at a corner — the one thing in a very slow animation the eye reliably catches, and it would land on the moment the flash is quietest; and it rests at exactly 0 rather than at a floor, so an urgent workspace passes through the very colour its neighbours are, once a breath, and the flash reads as that button changing rather than as a different button.

### Layer-shell windowing (`package:layer_shell`, `lib/window_manager.dart`, `lib/popup.dart`)

The gtk-layer-shell bridge is no longer in this repo — it is the `layer_shell` git dependency (`mattkae/layer_shell.dart`, pinned by `pubspec.lock`), which owns `LayershellWindowController`, `LayerShellWindow`, `ExtendedWindowingOwnerLinux`, and the generic GTK/GDK/Flutter FFI wrappers (`GtkWindow`, `FlView`, `FlEngine`, `FlWindowMonitor`) that `packages/ext_session_lock` reuses. It also re-exports the `@internal` SDK windowing pieces (`WindowRegistry`, `WindowEntry`, `WindowScope`, `PopupWindow`, `WindowPositioner`), which are unreachable through `package:flutter/widgets.dart`.

That dependency tracks Flutter `master`, and Flutter renames these APIs without notice. **When a build fails with `Type 'X' not found` inside `_window.dart`, the fix is upstream-first**: bump the `layer_shell` pin to a revision whose own *Build against Flutter master* workflow is green, then apply the same rename here. `.github/workflows/flutter-master.yml` is this repo's copy of that early-warning job.

- **The root `WindowManager`** (`lib/main.dart`) — Flutter's own, and the only thing in the shell that renders a window. It takes `initialWindows`, renders the registry it publishes as a `ViewCollection`, and every window the shell has — a panel, a background, an OSD card, a badge, a selection surface, an overlay, a lock screen, and every popup a module opens — is a `WindowEntry` in that one registry. It replaced a per-panel vendored stand-in (`PanelWindowManager`), which existed because the SDK widget renders *only* its registered windows and so ate any panel content nested inside it; at the root there is no content to lose, which is exactly the shape the SDK widget is documented for.

  Three things a change here has to keep true. **The root's set is reconciled, never rebuilt.** `_GracefulShellRootState._desiredWindows` answers what the root wants open and `_syncWindows` diffs it against `_rootEntries`, keyed on the controller, so only a surface actually created or destroyed touches the registry — a declarative list of views returned from `build` would take every module's popup down with it on each rebuild, because they are in the same registry. It follows that a surviving window keeps the `WindowEntry`, and so the *builder*, it was created with, which is why every builder in that list reads the root's fields rather than capturing them. **`_refreshWindows()` is what the root's `setState(() {})` used to be**, and the two halves have to stay in that order: the reconciliation is what drops the view, and the `_destroyAfterFrame` a caller follows it with is relying on that. And **the root is handed its own registry from below.** `WindowManager` creates the registry itself, takes no injected one, and has no `child` slot — so the root, its parent, cannot hold it until a window has built. `_RegistryBinder`, in `_windowChrome`, is what hands it back; until it does, `_syncWindows` bumps the key and remounts the manager, which is free precisely because a manager that has never rendered a window is a manager nothing could have opened a popup from.

  One property this gave up knowingly: the manager renders its registry as *unkeyed* `Window`s, where the hand-built view list keyed each on its controller. Keyless widgets of one type all satisfy `Widget.canUpdate`, so `updateChildren` matches them positionally and dropping a window from the middle shifts every later one down a slot — reparenting rather than rebuilding, since each `RawView` is globally keyed on its own `FlutterView`, but cascading through the windows *after* the one that closed. That is what the registration order in `_desiredWindows` is for: the per-monitor surfaces first, the overlays that open and close all day after them, and the modules' own popups appended last by whoever opened them.

  Reach the registry with `WindowRegistry.of(context)`, from anywhere inside any window.
- **`LayerShellHost` mixin** (`lib/popup.dart`) — reusable `State` mixin for modules that open a full layer-shell window (panel/overlay/dialog) at runtime. The module creates the `LayershellWindowController` and hands it to `openLayerWindow`, which registers a `WindowEntry` into the root's `WindowRegistry`; `closeLayerWindow` unregisters and destroys it. Used by the notifications, clock, and system modules. This is the same registry path popups use — there is no separate runtime-view registry.
- **`PopupHost` mixin** (`lib/popup.dart`) — reusable `State` mixin that manages a single popup window lifecycle; modules that open popups (e.g. `SoundControl`) mix this in. Note the cast to `BaseWindowControllerLinux` when making the surface transparent: `WindowControllerLinux` is the *regular*-window controller and a popup's is not one, so the wrong cast compiles and then throws on the first popup.
- **Popup content carries its own text root.** A popup's child is laid out directly under its own FlutterView, so `_windowChrome` is not above it and nothing supplies a `Directionality` — which every `Text` and `Row` in it needs, in release as well as debug (`Directionality.of` is a null-assert, not an `assert`). Wrap the content in `ShellTextRoot` (or, for the pre-token cards, a bare `Directionality`) inside its `ThemeProvider`; without it the surface maps and the card comes up empty, which is what happened to the weather forecast popup when it moved to `lib/weather/`. `test/popup_content_size_test.dart` cannot catch this — it supplies a `Directionality` of its own to measure under — so a popup's own test must pump it the way the shell builds it, as `test/weather_popup_test.dart` does.
- **Both mixins end their close on `_canRebuild`, not on `mounted`.** Every module that owns one of these windows closes it from its own `dispose()`, and `State.mounted` is still true for the whole of `dispose()` — the framework clears `state._element` only after it returns — while `unmount()` has already made the *element* defunct. `setState` from there is a `markNeedsBuild` on a dead element: an assertion failure in debug, and a build queued for something unbuildable in release. `BuildContext.mounted` is the element's own liveness, so the pair answers "still in the tree" for the ordinary close and the teardown one alike.
- **`PopupTransition`** (`lib/popup_transition.dart`) — the one animation a popup plays, in both directions. It replaced `PopupBounceIn`, a 500 ms elastic scale that fifteen popup content widgets wrapped themselves in by hand, and three things changed with it. **The effect is the theme's** (`popup_animation`, a row of `PopupEffect` in `lib/theme/popup_effect.dart`) rather than the widget's. **The exit is the entrance reversed on the same controller**, so an effect cannot describe an opening it has no closing for and the two can never drift apart; the exit's `reverseDuration` is shorter, because an entrance is paced to be followed and a dismissal is the user saying they are done. And **`PopupHost` wraps the card itself**, inside the shadow's padding and outside the `ConstrainedBox` — a call site that spelled the animation by hand was one that could forget it, and, once there is an exit, one that could route a close around it. `PopupEffect.none` is a true off switch: nothing is wrapped, no controller is created, and the window is destroyed on the frame it is closed. The dock passes it explicitly at both of its popups, whatever the theme says — it is a strip the pointer sweeps along, opening and abandoning a surface at every button on the way past.

#### Dismissal (`lib/popup_coordinator.dart`)

Nothing in the stack tells the shell a popup should go away. The Linux popup controller takes no `gdk_seat_grab`, so the compositor never sends `popup_done` on a click outside; `PopupDelegate.onWindowDestroyed` only fires once the window is already gone; and no layer-shell surface reports focus loss. Every popup therefore closes because its own `State` decided to — which is why two of them used to sit on screen at once. `PopupCoordinator.instance` is the one thing that closes them, and `PopupDismissArea` (wrapped around each panel and the desktop surface in `main.dart`) is the one thing that notices a click elsewhere.

Six things a change here has to keep true:

- **A handle's *chain* is itself plus its transitive parents, and nothing in a chain dismisses anything else in it.** That is the whole group concept, and it is what keeps the app-directory popup alive under its category flyout and the flyout alive under the pin-to-dock menu. Parentage is never passed by a call site: `openPopup` reads `TransientScope.maybeOf(context)`, the same context walk that already finds `WindowScope` and `WindowRegistry.of` from three levels deep. **The `TransientScope` wrapper in the `WindowEntry` builder is therefore load-bearing** — drop it and every nested popup starts closing its own parent.
- **The coordinator requests a *graceful* close, and must never call `closeLayerWindow` itself.** It calls the `onDismiss` the owner registered — for `clock.dart` and `notifications.dart` that is the `_closingNotifier` flip, so the fade/slide-out still plays and the module tears the window down afterwards, exactly as before. `LayerShellHost.openLayerWindow` takes `onDismissRequested` for this. A `closing` flag stops a second dismissal mid-animation from restarting it, and the handle stays registered until `close()`.
- **`TransientPolicy` is two booleans, not an enum.** `dismissesOthers` false is a hover tooltip: crossing the dock must not tear down the menu the pointer is travelling towards. `dismissable` false is a consent prompt or an awaited picker — it displaces, and nothing displaces it, because dismissing the screencast picker is a *denial* and nothing may answer it for the user. Refusal is inherited down a chain, so a surface nested in a modal is safe too.
- **The reopen guard exists because `PopupDismissArea` fires before `onTapDown`.** `GestureBinding` is the last entry on the hit-test path, so an ancestor `Listener` always beats a descendant recognizer — without the guard, clicking the icon whose popup is open would close it and immediately reopen it, and no bar popup could be dismissed by its own button. It is armed on the **primary** button only, because every popup toggle in the shell is a primary tap and every context menu is `onSecondaryTapDown`; a right-click that dismisses something must still be free to open its menu. It is keyed on the host `State`, so a host that opens a *different* popup per trigger passes `ownerKey` — `system_tray.dart` does, keyed on the item, or clicking a second tray icon would be read as re-clicking the first.
- **Root-owned overlays register too, and that replaced the ad-hoc pairs.** The nine of them (settings, launcher, emoji picker, app chooser, screencast picker, file picker, power menu, polkit prompt, notification panel) are `_OverlayWindow` instances in `main.dart` — one helper owning the controller, the sentinel-keyed coordinator handle, the closing notifier, and the AppIndex bracket, with the per-overlay deltas (`policy: modal`, `acquiresAppIndex`, `open(monitor:)`, `create:`) as constructor/call arguments. Eight of the nine are the same full-screen backdrop, which is why `_OverlayWindow` hard-coded that shape for as long as it was the only one; the notification panel is a column down one output edge and passes `create:` instead. What the helper owns is the *bookkeeping*, not the geometry, and that is the seam a new non-full-screen overlay takes. `open()` registers with the coordinator, `take()` unregisters and hands the controller back for `_destroyAfterFrame`, and `dispose()` covers all of it, so teardown cannot be asymmetric with what an open overlay holds. Lock calls `dismissAll()`: the compositor hides every other surface, so anything left registered would be a popup the user cannot reach and would find still open on unlock.
- **A closing popup outlives the host that closed it, and `isPopupOpen` is what makes that safe.** `PopupHost.closePopup` under an animated `popup_animation` *starts* the close: the host drops every reference to the popup on the spot — so `isPopupOpen` answers false synchronously and the several call sites that close one popup and open another in the same gesture (`dock.dart`'s tooltip giving way to its menu, `app_directory.dart`, `desktop_surface.dart`) still work — while the window stays mapped, playing the entrance backwards. Everything still owed to it moves to a `_ClosingPopup`: the coordinator handle, the `WindowEntry`, the native window, and the opener's `onClosed`, which now fires when the card is *gone* rather than when it was told to go. Three things that record has to keep. It **finishes on a timer as well as on the animation**, because a transition that never built — a view dropped before its first frame, a compositor that took the surface away — would otherwise leak a window on every close; that is `WindowTeardown`'s `maxFrames` reasoning one layer up. Its closing flag is **never disposed**, because `PopupTransition` removes its listener from a `dispose` that runs a frame *after* the entry is unregistered, and a `ValueNotifier` throws when a listener is removed from a disposed one. And `PopupHost.dispose` **finishes whatever is left outright**: what is animating there is a card on behalf of a host that no longer exists, and a deterministic teardown is worth more than its last few frames.
- **A native window may only be destroyed once Flutter has let go of its view, and that is checked rather than assumed.** `gtk_widget_destroy` on a window whose view is still live does not leak or glitch — it takes the whole shell down with SIGABRT. The GTK destroy cascade disposes the embedder's per-view renderer, whose `frame_mutex` the *raster* thread holds while it composites (`fl_view_renderer_opengl_present_layers`), and `g_mutex_clear` on a held mutex is a glib `abort()`: `g_mutex_clear() called on uninitialised or locked mutex`. The same abort answers a *second* destroy, because `gtk_widget_destroy` goes through `g_object_run_dispose`, which re-runs dispose on an already-disposed widget. Upstream defends against neither — `PopupWindowControllerLinux.destroy` calls `gtk_widget_destroy` *before* it unregisters the view — so `WindowTeardown` (`lib/popup.dart`) does the waiting: unmap now (so the close still looks instant), then poll `viewIsAttached` once per frame until the framework has dropped the view, then give the raster thread one more frame. Three things it has to keep. It **schedules its own frames**, because `addPostFrameCallback` requests none and a shell with nothing animating produces none — the callback would simply never run. It **destroys anyway at `maxFrames`**, because a window leaked on every popup close is worse than the residual race. And the hide **re-checks `isDestroyed`**, because `windowHandle` throws once the controller is gone and a compositor-initiated destroy can land mid-wait. Every teardown in the shell goes through it: both host mixins here, `_destroyAfterFrame` (`main.dart`) for the root-owned overlays and the OSD, and `SessionLockHost`, which passes `hide: false` — unmapping a lock surface before destroying it shows the desktop it exists to cover. The one-`addPostFrameCallback` hop this replaced assumed the rebuild that drops the view happened in the frame it landed after; under the dock, which opens and abandons a tooltip surface per hover, it does not.
- **Two clicks it cannot catch, by construction.** A click on an ordinary application window reaches no shell surface and there is no grab, so a popup survives it — the fix is a `gdk_seat_grab` in Flutter's `PopupWindowControllerLinux`, two upstreams away. And with `background.entries.isEmpty && !desktop.enabled` there is no background surface at all, so bare desktop cannot be observed. A full-screen invisible barrier is not the answer: the shell has no input-region support, so it would swallow every click on the monitor.

### Scopes (`lib/scopes.dart`)

Six `InheritedWidget` scopes are provided around every panel's widget tree:

| Scope | Provides |
|-------|----------|
| `ThemeScope` | `ThemeConfig` (colors, font) — never constructed directly; see `ThemeProvider` below |
| `ShellServicesScope` | `ShellServices` (how far along each global start-up task is) — see `lib/shell_services.dart` |
| `LiveConfigScope` | `AppConfig` as the user is editing it — never constructed directly; see `LiveConfigProvider` (`lib/live_config_provider.dart`) |
| `MiracleScope` | `MiracleConnection` (workspace IPC) |
| `DisplayScope` | `WaylandOutput?` (the monitor this panel is on — null until output enumeration lands, see the startup flow) — never constructed directly; see `DisplayProvider` (`lib/display_provider.dart`) |
| `BarScope` | `anchor` string (`'top'`, `'bottom'`, `'left'`, `'right'`) |

`ThemeScope`, `ShellServicesScope` and `LiveConfigScope` go together on *every* window, not just the panels — `_GracefulShellRootState._windowChrome` is the single place that pairs them (plus `ShellTextRoot`, below), and every `LayerShellWindow`/`SessionLockWindow` child in `main.dart` goes through it. It is also where `kExcludeSemantics` drops each window out of the semantics tree, for the same "one place every window passes through" reason — see that constant for why accessibility is currently switched off and what it costs.

**Three of the six are provider-only, and that is the pattern to copy rather than a quirk of the theme.** `grep -rn 'ThemeScope(' lib/`, `'DisplayScope('` and `'LiveConfigScope('` should each match `scopes.dart` plus that scope's one provider, and nothing else. Each provider is a `ListenableBuilder` on a store that emits the scope and **passes `child` through unrebuilt**, so a change wakes only the widgets that depend on the value — not the subtree, and emphatically not the root. Resolving any of these in `_GracefulShellRootState.build` instead is what made a single output landing, or a single keystroke in the settings UI, rebuild every panel on every monitor along with the backgrounds, the OSD and every root-owned overlay. The `_refreshWindows()` calls that remain in the root are the ones where its *list of native windows* genuinely changed; those cannot be a scope, because there is no ancestor above the root to hold one and an `InheritedWidget` cannot span FlutterViews anyway.

`DisplayProvider` listens to `OutputTracker` only and reads `ShellService.displays` from the `ShellServicesScope` above it, rather than taking a `Listenable.merge` of the two: `_MergingListenable` defines no `==`, and `ListenableBuilder` is an `AnimatedWidget`, so a merge built in `build` tears down and re-adds its listener on every rebuild.

Every scope resolves through one `_of<S>` helper with `registryOf`-style `FlutterError` diagnostics, and offers `maybeOf`; `BarScope.of` returns the anchor *string* (every caller wants the value), and `DisplayScope.of` is deliberately `maybeOf`-shaped — null means "not known yet" as much as "no scope".

### Shared UI primitives (`lib/theme/tokens.dart`, `lib/hover_region.dart`, `lib/bar_button.dart`, `lib/sky_icon_button.dart`, `lib/shell_text_root.dart`, `lib/overlay_fade_scaffold.dart`)

The layer below the theme, and what new UI reaches for before hand-rolling:

- **`tokens.dart`** — `ShellDurations` / `ShellRadii` / `ShellFontSizes` / `ShellSizes`, plus `kErrorColor` (the one error red) and `kOnAccent`. A theme decides colours and shape; these decide the sizes and timings that read as "the shell" regardless of theme. A literal that matches a token is a token. `ShellFontSizes` is the one tier that is *relative*: its constants are the scale at the theme's default `font_size` (13, which is `ShellFontSizes.body` itself), and the theme multiplies the whole scale through — see the Theming section. So a font size added here is a ratio to `body` whether or not it is written as one. `ShellSizes` is the pointer-target scale: hover and tap are one box (see `HoverRegion`), so these name *that box* and never the glyph inside it.
- **`HoverRegion`** — `builder: (context, hovered) => …`, plus the tap callbacks. The shell has no Material, and dozens of `StatefulWidget`s used to exist only to carry `bool _hovered`; never write that class again. **It emits the `GestureDetector` as well, at `HitTestBehavior.opaque`, and that half is the load-bearing one.** A `GestureDetector` with no `behavior:` is `deferToChild`, and nearly everything a control is built from answers `hitTestSelf == false` — `Padding`, `Align`, `ConstrainedBox`, `ClipRRect`, `Row`/`Column`/`Stack`, `RenderImage`, and a `Container` with neither `color:` nor `decoration:`. So in `Container(width: 26, height: 26, alignment: center, child: FaIcon(size: 11))` the only render object left accepting a hit is the glyph's own `RenderParagraph`, because `FaIcon` is a bare `RichText` with no `SizedBox` around it — the button hovered and cursored over 26 square and fired over about 11. That was the timers' pause/reset/stop buttons for as long as `SettingsIconButton` spelled its own `MouseRegion` around its own `GestureDetector`, and **a centre-tap test passes on every one of them**, which is why `test/tap_target_test.dart` taps corners. The greppable rule the sweep left behind: **every `GestureDetector(` in `lib/` either carries a `behavior:` or is inside `HoverRegion`.** Three corollaries. `Container(decoration: BoxDecoration(...))` *is* hit-testable — `RenderDecoratedBox.hitTestSelf` delegates to `BoxDecoration.hitTest` — but only inside its `borderRadius`, so a pill's four corner wedges are dead. `Container(color: X)` is hit-testable for any `X`, a fully transparent one included, while `Container(color: cond ? c : null)` is hit-testable *only while `cond` holds* — which is how two hover-tinted list rows came to be clickable by the accident of the pointer having entered first. And **opaque is not enough on its own**: a bare `FaIcon` is 11-14px of target, so it needs a box, at least `ShellSizes.minTapTarget` square. The `builder`-only form (hover with no tap) emits no detector, because an unconditional opaque box would swallow hits meant for a `Stack` sibling underneath — `RenderStack.hitTestChildren` stops at the first child that accepts. `enabled: false` is the third state: callbacks dropped, `disabledCursor` shown, box still absorbing, because a disabled button has never been hit-transparent.

  **`onTapDown` is not interchangeable with `onTap`**, and `HoverRegion` exposes both for that reason: every popup toggle in the shell opens on tap-*down*, because `PopupDismissArea`'s ancestor `Listener` fires before any descendant recognizer and the coordinator's reopen guard is armed and consumed inside that one pointer-down (see Dismissal). `bar_button.dart`, `system_tray.dart` and `weather.dart` are the three that depend on it.
- **`BarButton`** — the chrome around a bar module's clickable area. Its hover fill is `theme.surfaceHover` at a wash alpha — the hand-rolled copies all hard-coded `0x28FFFFFF`, which made bar hover the one hover in the shell no theme could touch.
- **`SkyIconButton`** — the round icon action in the corner of a picture-backed desktop card. Generalized out of the fortune widget's refresh button when a second card wanted the same control, which is the settings library's "a control the library lacks gets *added to the library*" rule applied outside it. It takes its colours from the picture rather than the theme (`kSkyForeground` and friends), is barely there at rest because these cards spend nearly all their life being looked at, and is a **tap** rather than a pan so the card stays draggable from under it.
- **`ShellTextRoot`** — the `Directionality` + theme-font `DefaultTextStyle` preamble, applied once in `_windowChrome` so every window's text inherits the theme's `fontFamily` when a `TextStyle` names none. This is what keeps a settings page from drifting off-theme one forgotten `fontFamily:` at a time; per-window copies of the preamble are being retired.
- **`FadeOverlayScaffold`** — the scrim + centred scale-in card, and the owner of the `closing`-notifier handshake (reverse, *then* `onClosed`, which is what may tear the window down). The settings, launcher and screencast overlays all sit on it.

### Controllers (`lib/request_controller.dart`)

The "seam" singletons that let something deep in a surface's tree ask the root for a window come in exactly two shapes, both defined here. `RequestController<Req, Res>` carries a request/response pair (`FilePickerController`, `ScreencastPickerController`) and bakes in three rules no subclass may lose: **no listener means an immediate decline** (a headless run never awaits a window that will not appear — and for the screencast picker this is the consent guarantee), **a second request supersedes the first as declined**, and **dispose answers the awaiting caller** (an unresolved pick is a D-Bus `Start` call hanging forever). `SignalController` is the fire-and-forget shape (`LauncherController`, `SettingsController`, `PowerController`, `NotificationPanelController`) — a monotonic counter plus `notifyListeners`, with any payload in the subclass. Neither is `InputTriggerStore`, deliberately: that store reports *compositor* triggers and its listener toggles on any notification, so a second signal there would trip the wrong handler. `LockController` stays outside both shapes on purpose — its request outlives the response.

### Configuration (`lib/config.dart`, `lib/config_reader.dart`)

`AppConfig.load()` reads TOML and produces:
- `Map<String, PanelConfig>` — one entry per named panel section.
- `String themeName` — the *name* of the active theme, not the palette. Resolving it is `ThemeStore`'s job (see Theming below).
- `BackgroundConfig?` — optional wallpaper config from `[background]`.

If the config file is absent, a default two-panel layout is written to disk and defaults are used.

`config.dart` holds the app/panel/section types and *re-exports* the pieces that live with their subsystems, so importers need not care where a type moved: `ThemeConfig` in `lib/theme/theme_config.dart` (its 30 keys spelled once in a const table driving `fromMap`/`toMap`/`colorKeys`/`==`/`hashCode`), the desktop model in `lib/desktop/desktop_config.dart`, the default-config TOML in `lib/default_config.dart`, the media-extension predicates (`isImagePath`/`isVideoPath` and their sets) in `lib/media_paths.dart`, and the power-button policy in `lib/power/power_config.dart`.

**Every field read goes through `TomlReader` (`lib/config_reader.dart`), and the invariant it carries is the one rule of this layer: a wrongly-typed value costs that one key, never the whole table.** A throw out of any `fromMap` — a module's included, because `Module.loadAll` runs inside `AppConfig.fromMap` — is caught by `AppConfig.load`, which answers by discarding the user's *entire* config. The readers therefore type-test and coerce (`height = 32.0` is a TOML float; `intOr` lands it as 32), treat NaN/infinity as absent (infinity survives `clamp()`, and `nan.toInt()` throws), and clamp via `min:`/`max:` where a painter or timer needs a sane range. New config classes and new module options use these readers; never a bare `as X?` cast. Only a TOML *syntax* error still costs the whole file, and that path logs to stderr rather than reverting silently. `test/config_golden_test.dart` pins the defaults, the built-in themes, and the per-field degradation behaviour.

**`AppConfig` and every section class under it carry value equality, and it is load-bearing rather than decorative.** `ConfigStore.appConfig` mints a fresh object graph on every read and `ConfigStore` notifies on every keystroke anywhere in the settings UI, so without `==` the `ValueNotifier` behind `LiveConfigScope` would fire on all of them and the scope could never refuse one. With it, a keystroke in any field that is not one of `AppConfig`'s typed fields — which is most of the settings UI, since `[modules.*]` goes through `Module.configChanges` and the audio/network/bluetooth/display pages and every theme edit write elsewhere — rebuilds nothing at all. `Map` fields hash on `length` (equal maps can iterate in different orders, and nothing here is ever a hash key); `List` fields use `listEquals` + `Object.hashAll`. `ThemeConfig`'s equality is spelled through its const key table because it has 30 keys; the largest class here has 9, so these are written out plainly. `test/live_config_provider_test.dart` pins the consequence.

### Theming (`lib/theme/`)

A theme is a file, not a config section. Each one is a flat TOML table under `~/.config/graceful-shell/themes/`, and `config.toml` names the active one with a top-level `theme = "dracula"`. The file *is* the table, with the same key names the old `[theme]` section used, so `ThemeConfig.fromMap` parses a whole theme document unchanged.

| File | Responsibility |
|------|----------------|
| `theme_config.dart` | `ThemeConfig` — the palette type itself, moved here from `config.dart` (which still re-exports it). Each of its 30 keys is spelled once, in a const key table that drives `fromMap`/`toMap`/`colorKeys`/`==`/`hashCode`; the const constructor with per-field defaults survives unchanged. |
| `builtin_themes.dart` | `kBuiltInThemes` — slug to full TOML text for `graceful` (the default, and the palette earlier versions hard-coded), `forest`, `dracula`, `glassy`, `midnight` and `carbon`. Between them the six are also the engine's coverage: the last two exist partly to hold down the corners of it — `carbon` is the only one that turns the shadow *off* (so the documented off switch is a shipped configuration rather than a claim), attaches its popups and flares the join, paints an opaque flat bar, and — alone among the shipped themes — **rims that bar while attaching**, so the collar that joins a flare to a panel's rim has a shipped configuration too; its `panel_border` and `panel_border_width` are its `popup_border` and `popup_border_width` exactly, because the line turns the corner from one surface onto the other and a step in either would show at the two points where it does; `midnight` is the only one whose shadow is a **glow** (accent-hued, zero offset, positive spread) and the only one that moves `font_size` off `ShellFontSizes.body`, so the `TextScaler` path has a shipped theme exercising it. Embedded as constants rather than installed to a share dir because nothing in the shell resolves paths relative to the bundle; the wallpapers the Makefile *does* install are found only via a hardcoded `$HOME/.local/share`, which breaks under a custom `PREFIX`. Seeding from a constant works identically in `flutter run`, `make install`, and the snap. |
| `theme_store.dart` | `ThemeStore.instance` + `startThemeService()` — the same singleton-`ChangeNotifier` shape as `OsdStore`/`AppIndex`. Owns the resolved palette, the catalogue, seeding, `select`/`create`/`edit`/`delete`, and a debounced atomic write lifted from `ConfigStore.save()`. |
| `theme_provider.dart` | `ThemeProvider` — a `ListenableBuilder` on the store wrapping a `ThemeScope`. |
| `font_catalog.dart` | `FontCatalog.instance` — the installed families, from `fc-list --format '%{family[0]}\n'`. Injectable runner and empty-on-failure, the `DiskReader` shape; the *future* is memoised so racing callers share one fork. Loaded lazily by the settings font picker, never from `main()`. |

Nine things a change here has to keep true:

- **`ThemeProvider` is the only thing that constructs a `ThemeScope`.** `grep -rn 'ThemeScope(' lib/` should match `scopes.dart` and `theme_provider.dart` and nothing else. The shell renders into many independent FlutterViews — one per panel per monitor, plus a window for every popup, overlay, OSD card and lock surface — and an `InheritedWidget` cannot span them, so each tree is given the theme separately. Every module used to do that by reading `ThemeScope.of` in the handler that opened the window and passing the value in, which froze it: an open popup never restyled. Listening instead of snapshotting is what fixes it, and it works even though `PopupHost.openPopup` builds the content once and captures it in a `WindowEntry` builder (`lib/popup.dart`) — the widget instance never comes back, but the `ListenableBuilder`'s element is mounted in that view's tree and rebuilds itself. `test/theme_provider_test.dart` pins this with a `const` child.
- **`font_size` is applied as a `TextScaler`, on the `MediaQuery` `ThemeProvider` publishes, and it has to be.** A theme carries a font *size* as well as a family, and the size is the shell's body tier — `ThemeConfig.textScale` is `font_size / ShellFontSizes.body`, so the whole `ShellFontSizes` scale moves as one and `13.0` is `TextScaler.noScaling`, which is what makes a theme written before the key existed render identically. It is the scaler rather than a `DefaultTextStyle` size because a default size reaches only the text that names none, and `grep -rn 'fontSize:' lib/` runs to three hundred lines: the obvious implementation is the setting that appears to do nothing. And it goes on `ThemeProvider` rather than on `ShellTextRoot` because a dozen popups still open with the bare `Directionality` preamble that widget is retiring, and a font size that reached the panels but not the menus they open would be worse than none — every themed tree in the shell is under a `ThemeProvider` by construction, which is the same property the `ThemeScope(` grep pins. Two consequences. **A `TextPainter` that decides a layout has to be given the scaler**, or it answers for text a different size from the one being drawn: `TrackMarquee` (which therefore measures from `didChangeDependencies`, not `initState` — an inherited widget cannot be read before the first one), `fitFortuneText`, and the weather card's `_measureText`/`_Sections`/`_forecastDays` are the four in `lib/`, and a new one is a bug the default theme cannot show. And **pixels are not scaled**: `ShellSizes`, a panel's `height`, the desktop grid's cell size and every icon size stay put, because growing the type is not an instruction to grow the bar — a large enough font in a bar left at its default height crops, and the answer is that panel's own `height` key.
- **`ThemeStore` reads `ConfigStore` for the `theme` key alone.** Never `ConfigStore.appConfig` — that getter rebuilds the whole typed config and re-applies every module's options via `Module.loadAll`, which would fire on every keystroke anywhere in the settings UI.
- **Shipped themes are read-only, and re-seeded when they drift.** `edit` forks a built-in into a user copy first, so `themes/dracula.toml` stays byte-identical to what was seeded. Membership in `kBuiltInThemes` *is* the read-only test, so there is one source of truth for "shipped". `_seedBuiltIns` rewrites any shipped file whose content differs, which is what makes a palette fix reach an install that has already run: seeding used to skip an existing file, and the first panel-colour fix silently never landed because the stale `glassy.toml` on disk had none of the new keys. User themes are never touched.
- **The bar has its own colour, and one opacity.** `panelBackgroundDecoration` (`lib/panel_background.dart`) paints `panel_background`, whose alpha is honoured verbatim — it is the surface sitting directly on the desktop. The panel used to be derived from `workspace_background` at a hardcoded 93%, which made it the one thing in the shell no theme could open up while its own popups obeyed. `panel_gradient = false` gives a flat sheet (what `glassy` wants); true fades `accent` -> `surface_pressed` -> `panel_background` with **every stop taking its alpha from `panel_background`**, so an author sets the bar's transparency in one place and no stop can band across the middle.
- **`panel_margin` is a native margin, and it must not touch the exclusive zone.** `setPanelMargin` (`lib/popup.dart`) calls `controller.setMargin` on each edge `anchorEdgesForPosition` returns — never a Flutter `Padding`, because the shell has no input-region support and an inset inside a full-size surface would leave the surface swallowing every click in the gap instead of letting it reach the desktop. The zone stays `panelConfig.height`: per wlr-layer-shell's [`set_margin`](https://wayland.app/protocols/wlr-layer-shell-unstable-v1#zwlr_layer_surface_v1:request:set_margin), *"the exclusive zone includes the margin"*, so the compositor adds it and sending `height + margin` reserves it twice — the symptom is a dead strip under the bar that no window will occupy, which reads as a compositor bug. Unlike every other panel geometry field this one follows the theme live, from `_onThemeChanged` in `_GracefulShellRootState`: a theme switch that rounded the corners but did not lift the bar until the next restart would just look broken. The cached `_panelMargin` compare is load-bearing — `ThemeStore` notifies on every frame of a colour-picker drag, and re-committing every layer surface that often makes the bars flicker. Corner rounding follows from the same field: `panelCornerRadius` rounds all four corners only when the bar floats, because a flush bar with rounded outer corners cuts wallpaper wedges out of the display's own corners. `popup_gap` is this key's analogue one layer up — that floats the bar off the screen, this floats a popup off the bar — and the corner rule is deliberately mirrored; see the attached-popup bullet below.
- **`popup_animation` is one key for two animations, because the second is the first reversed.** A theme decides shape and colour, and a card's *arrival* is part of its shape: a menu that unrolls out of the bar and one that fades in place belong to different themes even when every colour matches. So it sits beside `popup_gap` and `popup_radius`, which decide the same card's other two dimensions. There is deliberately no `popup_animation_out`: `PopupTransition` plays one controller forward to open and backward to close, which is what makes an exit impossible to forget and impossible to contradict — the elastic bounce this replaced had no exit at all, so every popup in the shell blinked out of existence. Two things follow at the call site. The effect is **snapshotted at open**, with the rest of the theme and for a reason of its own — a theme edited while a popup is open would otherwise close it with an animation that is not the reverse of the one it opened with. And the directional effects (`slide`, `grow`, `flip`) take their direction from the **bar's** anchor, so a bottom bar's menus rise where a top bar's drop; a menu anchored to the pointer has no bar to travel out of and is treated as hanging below its anchor, which is where the compositor puts it. `kPopupSlideDistance` is small on purpose: the card is translated *inside* a window sized to its content plus the shadow's reach, and GTK3 resolves the placement once at map time, so a long travel would be clipped at the surface edge on the frames that needed it most.
- **A popup's shadow grows its compositor surface, and the positioner takes that back.** `popup_shadow_*` is one CSS-style box-shadow painted by `popupDecoration` (`lib/popup_surface.dart`), and a `BoxShadow` paints *outside* its box — but a popup is its own surface, sized to its content by the post-frame `gtkWindow.resize` in `PopupHost.openPopup`, and clips at its edge. So `openPopup` pads the *measured* box by `popupShadowInsets` (outside the `ConstrainedBox`, never inside — the popups that pin a width with `minWidth == maxWidth` must keep their content width and widen the window instead), and passes `popupShadowAnchorOffset` as the `WindowPositioner.offset` so the card lands exactly where an unshadowed one would. Both halves or neither: the padding alone moves every menu in the shell away from its button by the shadow's reach, and the offset alone slides them under it. **A third piece has to hold for either to mean anything: the window must be *allowed* to be that size.** `PopupWindowController`'s `constraints` are not layout constraints — the Linux backend registers its sized-to-content view with an unbounded `1x1 .. G_MAXSIZE` metrics range, so they never reach Flutter's layout, and turns them into the GTK window's `GDK_HINT_MIN_SIZE`/`GDK_HINT_MAX_SIZE` geometry hints instead — so `popupWindowConstraints` (`lib/popup.dart`) grows them by the same insets and the `ConstrainedBox` inside keeps the card to what the call site asked for. Handing the card's own constraints straight through is what made GTK clamp the `resize` back to the card's maximum: every popup that pins a width with `minWidth == maxWidth`, or passes `BoxConstraints.tightFor`, mapped a surface exactly as wide as its card and then drew that card `insets.left` inside it — off its button by half the shadow's reach and clipped on the far side — while the loose-constrained menus, whose content sat under their maximum and so was never clamped, stayed put. The insets are snapshotted at open, like the constraints and for the same reason — GTK3 resolves `gdk_window_move_to_rect` once at map time. `kOsdWindowSize` is the one fixed-size case: the OSD card's `Row` has an `Expanded` so it fills its surface, and `_createOsd` (`main.dart`) inflates the window and gives the bottom margin back. A fully transparent `popup_shadow_color` restores the exact pre-shadow geometry, which is what makes it a real off switch rather than an invisible shadow that still costs margin.
- **A bar popup is anchored to the *panel's* inner edge, centred on the module, and `popup_gap` is the distance off it.** `popupAnchorsForBar` returns edge-*centred* anchors, so the compositor reads one point off the anchor rect; handing it the module's own rect (`popupAnchorRect`) put that point wherever the module's padding ended — a `BarButton` is inset 2px vertically, on top of the section's own — so every popup opened a couple of pixels *inside* the bar, overlapping it, by a different amount per module. `barAnchorRect` (`lib/popup.dart`) grows the rect across the panel's whole cross-axis extent and leaves the other axis alone, which is what makes the anchor the bar's edge for every module alike while keeping the popup on its own icon; the panel's size comes from the `MediaQuery` its `View` installs, which is the very space `localToGlobal` reports in. A degenerate panel size falls back to the widget rect, because a zero-extent anchor rect is an `xdg_positioner` protocol error rather than merely a bad placement. `popupGapOffset` is then a second `WindowPositioner.offset` term beside `popupShadowAnchorOffset` — the two answer different questions and must not be folded together.
- **`popup_gap = 0` is the attached mode, and three decorations have to move together for it to read as one surface.** The card is flush with the bar; `popupCornerRadius` **squares off** the two corners on the join and leaves the far pair `popup_radius`, `panelCornerRadius`'s asymmetry one layer up and for the same reason; the rim on that edge is dropped, because a hairline across the seam is the one thing that gives away that the card is a second surface; and `popupShadowInsets` clamps that side's inset to the gap, so the *surface* is flush too and the compositor's own clip cuts the shadow exactly at the join. The clamp is `min(inset, gap)` rather than a zero, so one rule covers the range — the shadow fills a small gap and stops rather than crawling under the bar, and a gap past the shadow's reach is a no-op that leaves a floating theme byte-identical to what it was. The two offsets then compose to the gap exactly: on the joined edge the correction term contributes `gap - min(reach, gap)`. All of this reaches the card through `PopupAttachScope` (`lib/popup_surface.dart`), the `OpaquePopupScope` pattern with a value, because a popup's content is a *sibling* FlutterView under the root `WindowManager` and cannot read the panel's `BarScope`.
- **`popup_attach_radius` is a concave fillet, not a corner radius, and that is why `popupDecoration` answers a `Decoration`.** It reads as a rounding and is the inverse of one: a convex corner curves *away* from the surface behind it, leaving a transparent wedge either side of the join so the card reads as resting against the bar, where the join wants each side sweeping *outward* as it reaches the panel — widest exactly where the two meet. No `BorderRadius` can express that, so above zero it is `AttachedPopupBorder` inside a `ShapeDecoration`, the one card in the shell that is not a `BoxDecoration`; `PopupCard` therefore asks `decorationClips` rather than testing `borderRadius != null`, and the shape takes its rim from `_popupSide` rather than off a `Border`, because reading `_popupBorder(...).top` would read the very side an attached card has just dropped. The outline is built once in a canonical frame with the join along `y = 0` and mapped per edge by a `Matrix4` — two of the four maps are reflections, which is harmless, since a reflection reverses the winding and flips every arc's handedness together. `paint` strokes the *open* outline at twice the rim width clipped to the shape, so only the inner half lands: a rim drawn inside its own outline with no second set of radii to keep in step with the first, and nothing drawn across the join. `getInnerPath` is contract-only and deflates the rect, the approximation `RoundedRectangleBorder` makes.
- **The flare paints outside the card's box, so the surface has to carry it, and the two margins compose by `max` rather than by sum.** `popupAttachInsets` is the flare's reach on the two sides that meet the join — `popupShadowInsets`'s job for a different piece of paint — and `popupSurfaceInsets` takes the per-side larger of the two, which `openPopup` then uses for the padding, the positioner offset and the window constraints alike. Larger rather than sum because both measure the same thing and the flare is part of the silhouette the shadow is already cast from; summing would push every attached window out by a margin nothing draws in, and the shell has no input-region support, so that margin swallows clicks meant for the desktop. It is the same rule `PopupHost.openPopup` states about keeping the shadow margin to the shadow's actual reach. Only bar popups get an edge — every menu anchored to the pointer keeps its geometry byte-for-byte, as does the OSD, which grows by the one-argument `popupShadowInsets` in `main.dart` and pads by the same in `osd/osd.dart` with no compiler link between the two. `openBarPopup`'s `attach: false` opts out of the *shape* alone, which the three hover tooltips pass: the edge anchor, the gap and the shadow clamp are not optional.
- **A bar may carry a rim because `popupAttachCollar` reaches the card into it, and that reach is the join's rather than the flare's.** `panel_border_width` draws the bar's rim along its **inner** edge as well as its outer one — the very edge an attached popup meets — so a rimmed bar used to put a hairline straight across the mouth of every menu it opened, which reads as a card taped under a line rather than as the bar opening. That is why `graceful` and `dracula` attach their popups and ship `panel_border_width = 0`, and why `carbon` did. The fix is one number: **any** attached card (`popup_gap = 0`) reaches `panel_border_width` back **into** the panel and its own fill takes that hairline out across the whole mouth. What `popup_attach_radius` decides is only how the line *resumes* at either end: with a flare the card is at its widest exactly at the join and the two arcs, which leave their tips tangent to the join line, pick the line up and carry it down the card's sides; with a square butt join the bar's rim simply stops at the card's sides and the card's own rim continues it at a right angle. Either way the result is one outline: along the bar, off it where a menu is open, round the card, and back. Four things it has to keep. **The collar is what forces the shape, so a square join takes `AttachedPopupBorder` too** — the reach paints one rim-width *outside* the card's own box and a `BoxDecoration` cannot do that at any radius, which is why `popupDecoration` branches on `popup_attach_radius > 0 || collar > 0` and why `AttachedPopupBorder` builds a square-cornered outline at `attachRadius: 0`. Reading `popup_attach_radius` in `popupAttachCollar` — which it used to — is what left every square-joined theme with the hairline this exists to erase, and it is not a shape the flare can be made a precondition of. **The margin is the join's, so it goes in `popupAttachInsets`** — on the joined side, which is the one side the flare itself takes nothing on, so a collared square join asks for that side and nothing else — and `popupSurfaceInsets` then hands it through whole, because the shadow's inset on that side has already been clamped to `popup_gap` and attaching *is* that gap being 0; `popupShadowAnchorOffset` shifts the window back by the same amount, so the card lands exactly where it did and only its surface grew. **It is drawn, not communicated.** The panel is a *different* FlutterView and cannot be told where a popup's mouth is — the compositor resolves the placement, `kPopupSlide` may move it, and the card's width is not known until it lays out — so the erasure is the popup's own fill painted over the bar, which is correct wherever the popup lands. And **a collar of 0 is byte-identical to no collar**: `popupAttachInsets` answers `EdgeInsets.zero` when neither the flare nor the collar reaches anywhere, `popupDecoration` keeps the plain `BoxDecoration` there, and `AttachedPopupBorder` builds its outline at a depth of `into + collar` and shifts it back — so an unrimmed bar's square join draws exactly the card, the layers and the surface it drew before either parameter existed.
- **A full-screen layer-shell surface must call `spanFullOutput`.** gtk-layer-shell defaults the exclusive zone to 0, and per wlr-layer-shell that means "move me so I don't occlude surfaces that reserved space" — so the compositor shrinks the surface to the gap *between* the panels. `spanFullOutput` (`lib/popup.dart`) sets it to -1, "extend me to the edges I'm anchored to". The wallpaper window needs it or there is nothing behind a translucent panel but the compositor's empty background, and a see-through bar renders as a flat black strip identical on every monitor edge; the settings, launcher and power-menu overlays need it or their backdrop stops short of the bars. This was invisible for as long as every panel was opaque.
- **There is no `blur` key, because a `BackdropFilter` here can only ever be a bill.** A layer-shell surface is transparent and the compositor owns everything under it; Mir exposes no blur protocol — which the key's own documentation admitted, keeping it on the grounds that it still softened the `scrim`. It did not: a filter reaches only what Flutter has *already painted* beneath it, and `FadeOverlayScaffold` is the first thing painted into its window, with the scrim as its own child. So the backdrop was empty and the filter changed no pixel (`test/fade_overlay_scaffold_test.dart` pins its absence; a raster diff of a filtered and an unfiltered tree over an empty backdrop differs in zero of 480,000 bytes) while every frame the overlay animated paid for a full-output Gaussian. That was the shell's one per-frame full-screen effect, and the reason the settings pages visibly lurched between one another. Translucency over the desktop comes from alpha, which is how `glassy` is built.

The settings UI for this is `_AppearanceSection` in `lib/overlay/settings/shell.dart`: a picker of swatch cards, a "New theme…" action, and a colour editor that is dimmed behind a "Duplicate to edit" button while a built-in is active. The HSV colour picker it uses (`SettingsColorField`, `SettingsColorPicker`, `formatHexColor`) lives in `lib/overlay/settings/controls.dart` beside the other shared controls, as does the font picker (`SettingsFontField`).

Two things the font row has to keep true, both now owned by `AnchoredSearchDropdown` (`lib/search_list.dart`), which `SettingsFontField` and the calendar's time-zone picker are thin wrappers over — as, since the settings UI stopped having two kinds of dropdown, are `SettingsDropdown` and the string-list editor's module adder. **It floats in the *root* overlay and takes its list as a parameter**, for the reasons `SettingsColorField` documents: the settings content pane is a nested `Navigator` whose `Overlay` would clip a list hanging below the row, and a control that read `FontCatalog` itself could not be widget-tested without forking `fc-list`. The `Future` is started in the state's field initialiser, never in `build` — this section rebuilds on every `ThemeStore` notify, which includes every frame of a colour-picker drag. **The row degrades rather than locks out.** With no fontconfig the catalogue is empty and the row falls back to the free-typed `SettingsTextField` it used to be, so `font` is never a key the UI can no longer set; and a theme naming a family this machine does not have is prepended to the list rather than dropped, or the picker would silently disown the value it is showing.

### D-Bus plumbing (`lib/dbus_service_object.dart`, `lib/dbus_clients.dart`)

Every `DBusObject` the shell exports extends `DBusServiceObject`: an interface table (methods, read-only properties, signals) declared once drives `handleMethodCall`'s interface guard and dispatch, `getProperty`, `getAllProperties`, and `introspect` — the five objects used to list their members two or three times each, which is how one lost its interface guard and another's `GetAll` returned nothing. The file is Flutter-free, because the screencast portal must stay compilable into `tool/screencast_spike.dart`. One-shot queries share the process-wide clients in `dbus_clients.dart` rather than opening a `DBusClient` per call — the bluetooth page is the documented exception (BlueZ scopes discovery to the requesting connection, so its per-operation client is what guarantees discovery stops). Long-lived services own their connections as before.

### Notification service (`lib/notification_service.dart`, `lib/notification_badge.dart`, `lib/notification_panel_controller.dart`)

Implements the FreeDesktop `org.freedesktop.Notifications` D-Bus interface via the `dbus` package. `startNotificationService()` registers on the session bus so the shell receives desktop notifications, which the `NotificationsModule` and the floating badge display.

**There are three surfaces and one panel, and that ratio is the design.** The bell (`lib/modules/notifications.dart`, `configKey = 'notifications'`, in the default bottom panel to the left of the launcher) lives in a bar the user may not have; the badge (`lib/notification_badge.dart`) is a root-owned window in every output's top-right corner, drawn only while there is something to report; and the panel is a full-height column down one output's right edge. The panel used to be the bell's own `LayerShellHost` window, which is exactly what a second trigger cannot reach — a `LayerShellHost` window is opened from the panel's own tree, and the badge is a sibling FlutterView with no widget ancestry in common with any bar. So the panel is a seventh `_OverlayWindow` in `main.dart` and both triggers go through `NotificationPanelController` (`SignalController`'s shape; see the Controllers section). Two things fall out of that. The controller's `isOpen` is a **separate `ValueListenable`**, not state on the notifier itself: the root *listens* to the controller for the toggle, so publishing the flag through the same `notifyListeners` would make the root's own write on opening come straight back in as a second toggle and close the panel it had just opened. And the bell's pressed state reads that flag rather than a field of its own, because the panel it opens may equally have been opened from a badge on another monitor.

Three things the *panel's* surface has to keep true: it is on `LayerShellLayer.overlay` and calls `spanFullOutput`, because a zone of 0 means "move me so I don't occlude surfaces that reserved space" and the compositor would shrink it into the gap *between* the bars — so the slide-in would start and end short of the screen edges instead of covering them. It is `LayerShellKeyboardMode.onDemand`, the settings overlay's mode, because a layer surface with no keyboard interactivity never sees a key event and the panel's own Escape binding would never fire — and deliberately not `exclusive`, which would hold the keyboard off whatever the user was typing in for as long as a panel they only glance at is open. And its width is `notificationPanelWidth` — a quarter of the output, floored at 360 and capped at 560 — rather than the bare `width / 5` it was: a fifth of a 1366px laptop is 273px, which wraps a two-word summary and stacks the action buttons one per row, and a quarter of an ultrawide would cover what the user was reading. It is pure, so both ends are pinned by `test/notification_panel_test.dart`.

**The badge's surface is the panel's inverted, and the inversion is the whole of "it does not overlap the bars".** It keeps gtk-layer-shell's *default* exclusive zone of 0 — which is the very thing `spanFullOutput` exists to switch off — so the compositor has already placed it clear of a top bar and of a right-hand one, their `panel_margin` included, because per wlr-layer-shell the zone includes the margin. `panelInsetsFor` on top of that would count every bar twice and hang the badge a bar's height out into the middle of the screen, and `spanFullOutput` would put it under them. Four more things it has to keep. It is **per monitor**, the OSD's rule rather than the launcher's: the badge is the shell saying something arrived, and a user looking at the other display would never see it — and each one opens the panel on *its own* monitor, which the root can do because it created the window and the badge cannot, which is why `onTap` is a parameter rather than a `NotificationPanelController` call. It **exists only while there is something to report**, again the OSD's rule and for the OSD's reason: the shell has no input-region support, so a permanently mapped corner surface would eat every click that landed on it. It comes down **while the panel is open**, because the panel is a column down the same edge and the badge would sit under the thing it exists to open. And **nothing on it animates at rest** — the entrance plays once, a bump plays when the count goes *up* (never when a dismissal takes it down, which would draw the eye back to what the user is clearing), and both settle, so a surface that may be on screen for hours costs nothing per frame; `test/notification_badge_test.dart` pins that with a settle plus `transientCallbackCount == 0`. `kNotificationBadgeWindowSize` is bigger than the button because the count bubble is drawn outside its box and the button casts a shadow, both of which the surface would otherwise clip — `popupShadowInsets`' problem one layer down — and the same test pins the two constants adding up, since the root reads one and the widget lays itself out under the other with no compiler link between them.

And **its two animations are two controllers, because the way out is not the way in reversed.** The entrance is the `SlideTransition` alone, never a `PopupBounceIn`: that widget's scale pivots on the centre, which on an edge-anchored full-height surface pulls the panel off the edge it is anchored to and opens a gap that closes as it settles. The exit has its own controller so it can be both shorter — `ShellDurations.overlayFade` against the entrance's 300ms, because an entrance is paced to be followed while a dismissal is the user saying they are done — and a different animation: a beat of wind-up, then the panel takes off to the right, shrinking towards and fading into its edge. That flourish lives inside the same constraint the entrance states, which is why every part of it either scales on `Alignment.centerRight` or moves the panel further *off* the output. Anything that moves it left — an overshoot, an anticipation dip, a centre-pivoted scale — opens a transparent strip along the screen edge, which is the one thing this surface must never do; `test/notification_panel_test.dart` walks the exit frame by frame and asserts the panel's right edge never moves inwards. Every dismissal goes through the same `closingNotifier` — the bell, the badge, the header's close button, Escape, and the `PopupCoordinator` alike — so none of them can skip the animation by tearing the window down itself; the root's `_onNotificationPanelClosed` is what takes the window, and it is the only thing that does.

**Losing the bus name is a visible state, not a silent one.** `NotificationStore` carries a `NotificationDaemonStatus` (`starting` / `running` / `unavailable`) alongside the items, and `startNotificationService` records both of its exits into it — the graceful decline (another daemon owns `org.freedesktop.Notifications`) and the rethrown failure alike. That is deliberately *not* a duplicate of `ShellService.notifications`'s `ServiceStatus`: that one answers "should I show a spinner?", for which a decline and a success are the same answer, so it settles `ready` either way and must keep doing so. This one answers "do notifications work?", where a decline is a flat no — every notification on the machine is going to a daemon the shell cannot see. Without the second answer the shell renders an idle bell over an empty panel, which is indistinguishable from a quiet day.

**The panel is read, not scanned, and it is sized for that.** Its text root is `ShellFontSizes.label` rather than the shell's body tier, and every size on a card is a rung above where it was: the app name is a caption, the summary is `ShellFontSizes.title`, the body is the panel's own body size at six lines rather than four, and the actions are boxed buttons at `ShellSizes.minTapTarget + 6` instead of footnote-sized text a pointer had to be aimed at. The tiers are the point rather than the numbers — `ShellFontSizes` is the scale a theme's `font_size` multiplies through, so raising the root raises the whole card with it and a theme still moves all of it together. Three smaller rules with the same reason behind them. The header carries a **count** under the title (singular for one, because "1 notifications" is what makes a panel read as generated), and "Clear all" is a bordered button rather than a tinted word, because it destroys every item on the list. The cards are separated by a **gap**, not a hairline: at these sizes a rule between two three-line blocks reads as a table, and what is wanted is a stack of separate messages. And the panel's fill is **opaque whatever the theme says** — `overlayPanelFill`'s rule, for its reason: this is a column of prose read over whatever application window is behind it, and a translucent palette puts that window's own text straight through it. The empty state says what the surface is *for* rather than reporting that it has nothing, because it is the state the user sees most often.

The failure UI is in two halves, because the two questions the user has are asked at different moments. The bell grows an exclamation dot (`_BrokenDot`, bottom-right so it never collides with the unread count) with a hover label saying what is wrong — that is the half that answers "why have I had no notifications all day?" without a click. The open panel carries `NotificationDaemonBanner` above the list — above, because with the daemon down the list is empty and "No notifications" is a lie the user would act on — with the reason and a **Retry** button that re-runs `startNotificationService` through `NotificationStore.retryDaemon`. Both failure modes are recoverable without restarting the shell (the other daemon can be stopped, the bus can come back) and the shell cannot detect either happening, so the retry is the user's to trigger. `retryDaemon` refuses to stack on an attempt in flight and refuses outright once the name is won; `daemonStarter` is injectable so the whole path is a unit test, and the banner is public — as `NotificationPanel` itself now is — because in its one real home it is inside a layer-shell window no widget test can pump, so the pieces with behaviour worth pinning have to be reachable from a test directly. `test/notification_daemon_test.dart` pins all of it.

### System tray service (`lib/status_notifier_service.dart`, `lib/dbus_menu.dart`)

Implements the freedesktop/KDE **StatusNotifierItem (SNI)** system tray. `startStatusNotifierService()` (called from `main.dart` right after `startNotificationService()`) makes the shell own `org.kde.StatusNotifierWatcher` on the session bus and register itself as a `StatusNotifierHost`, so tray applications (Discord, Steam, network/VPN applets, etc.) attach to it. Each registered item is tracked via a `DBusRemoteObject` — its icon/title/status/menu properties are read and kept live through the item's `NewIcon`/`NewStatus`/… change signals — and published through the `TrayStore` singleton (`ChangeNotifier`, same pattern as `NotificationStore`). Item removal is detected via `nameOwnerChanged`. Like the notification daemon, it fails silently if another tray watcher already owns the name.

`lib/dbus_menu.dart` is the client for the `com.canonical.dbusmenu` protocol: it fetches an item's context menu (`GetLayout`) into a `MenuNode` tree and reports clicks (`Event`). Icons arrive either as themed names (rendered with `XdgIcon`) or as raw ARGB32 pixmaps (decoded to a Flutter `ui.Image`).

The `SystemTrayModule` (`lib/modules/system_tray.dart`, `configKey = 'system_tray'`, in the default top panel) renders the icons in a condensed, overlapping strip that spreads apart on hover; clicking an icon opens that app's menu in a themed popup (via `PopupHost`). Config options under `[modules.system_tray]`:

| Key | Type | Default | Meaning |
|-----|------|---------|---------|
| `icon_size` | number | `16` | Rendered icon width/height (logical px). |
| `collapsed_overlap` | number | `10` | How far each icon overlaps its neighbour at rest. |
| `expanded_spacing` | number | `6` | Gap between icons when the strip is hovered. |
| `hidden_items` | string list | `[]` | SNI `Id` or `Title` values to hide from the tray. |

### Media (`lib/media/`, `lib/modules/media_player.dart`, `lib/desktop/widgets/media_player_widget.dart`)

What is playing, and the controls for it, over MPRIS (`org.mpris.MediaPlayer2.*`). Two surfaces render it — the bar module and the desktop widget — and neither owns it.

| File | Responsibility |
|------|----------------|
| `mpris_store.dart` | `MprisStore.instance` — the singleton `ChangeNotifier` holding every player, the active one, and `playPause`/`next`/`previous`/`stop`. Flutter-free apart from `ChangeNotifier`. |
| `media_controls.dart` | `MediaTransportButton`, `TrackMarquee`, `PlayingBars` — the pieces both surfaces are made of, each taking what it draws as parameters. |

Four things a change here has to keep true:

- **One connection for the machine, leased, with a *detail* tier.** All of this used to live in `MediaPlayerState`, which meant a second consumer would have meant a second session-bus connection, a second `listNames()` walk and a second subscription per player — and two bars on two monitors already meant two of everything. It is now `SystemStatsStore`'s lease rule: the bus connection and the per-player subscriptions exist only while somebody holds a lease, and a **detail** lease adds the one-second `Position` poll that a progress bar needs and a bar module does not. That poll also stops whenever nothing is playing, so an idle shell with the widget on screen wakes for this exactly never.
- **Progress is derived from a reference point, never accumulated.** A player publishes `Position` on request and, per the MPRIS spec, deliberately **not** through `PropertiesChanged` — a property signal per second would be absurd. The store therefore keeps the last read *and when it was read*, and interpolates, exactly as `lib/timers/` does: a ticker that added its own period would drift by however late each wakeup was. A backwards clock step is dropped rather than subtracted, and the result is clamped to the track length so a read taken a moment before a track change cannot run past the end of the bar it is drawing.
- **The store is the only thing that mutates an `MprisPlayer`.** Consumers read the fields and are told to rebuild by the notification; a surface that wrote one would be publishing state no other surface would hear about. `MprisStore.forTesting()` is **offline** — it never opens a bus — so a widget test can take a real lease and feed the store through `seed`.
- **A marquee measures; it does not count characters.** The same 30 characters fit at 11px and overflow at 16px, and the bar's old `length > 32` rule got both wrong under a theme with a wider font. `TrackMarquee` lays the text out with a `TextPainter` and re-measures whenever the text, the style or the width moves. Its scrolling form is two absolutely-positioned copies inside a `ClipRect`, **not** a `Row`: the box is exactly `maxWidth` wide and hands that down as a tight constraint, so a row — which is by definition wider — overflows and Flutter reports it every frame. Nothing that renders a marquee may be `pumpAndSettle`ed; a scrolling title never settles.

The desktop widget's layout is chosen by its **span**, but whether that layout *fits* is decided by pixels: a cell is configurable down to 32px, so a 2-row widget on a short grid falls back to the compact layout and a card smaller than the content can be drawn in is laid out at its own minimum and clipped, rather than reporting a flex overflow every frame on a surface whose console nobody is reading. What degrades first is deliberate: skip-track goes before play/pause (that is the control somebody put a media player on their desktop for), and the level meter goes before the artist's name.

Two things the *animations* are honest about, because the shell cannot see the audio. `PlayingBars` is an ornament with a per-bar phase, not a visualiser — the shell has no access to the stream's samples, and a PulseAudio peak-metering monitor source per player is not a price a wallpaper widget gets to charge. And both it and `AlbumArt` **settle** rather than freeze when playback pauses: a visualiser stopped mid-bounce reads as a rendering bug, while a flat rest line and a still disc read as "paused", which is what happened.

### Weather (`lib/weather/`, `lib/modules/weather.dart`, `lib/desktop/widgets/weather_widget.dart`)

What the sky is doing, and two surfaces drawing it. Same split as `lib/media/`, and for the same reason: all of this used to live in the bar module's `State`, so the desktop widget would have meant a second IP geolocation lookup, a second forecast poller and a second parse — on top of the one per bar per monitor there already was.

| File | Responsibility |
|------|----------------|
| `weather_condition.dart` | The WMO `weather_code` table, resolved once, into a name, a nominal cloud cover, what is falling and how hard, and whether it flashes. Flutter-free, so it is a plain unit test. |
| `weather_api.dart` | `WeatherClient` — Open-Meteo's forecast and geocoding endpoints and ipapi.co's IP fallback, behind an interface, with `parseForecast`/`parseGeocoding`/`parseIpLocation` as pure functions over a decoded map. |
| `weather_config.dart` | `WeatherConfig` — `[modules.weather]`, beside the store the way `system/system_monitor_config.dart` sits beside its sampler. `modules/weather.dart` re-exports it. |
| `weather_store.dart` | `WeatherStore.instance` — the singleton `ChangeNotifier` with `SystemStatsStore`'s lease rule. One fetcher for the machine. |
| `weather_icons.dart` | A glyph per row of the table, from `weather_icons_animated` (the Meteocons set), plus `WeatherIcon` — the one place the family and the tint policy are spelled. Only ever the pack's `svg-static` files; nothing here animates. |
| `weather_sky.dart` | The painted sky the desktop card sits on — one still picture, no ticker: `SkyPalette` per condition, `SkyField` (the layout), `SkyPainter`, `SkyScrim`. |

Seven things a change here has to keep true:

- **The code table is resolved once, as data.** The bar needed an icon and a name, the popup a name, and the sky a cloud fraction, a precipitation type, an intensity and a lightning flag — three `switch`es over the same codes is three places to miss one of them. An unrecognised code answers `WeatherKind.unknown` rather than throwing: it arrives from a web API, and a value this build predates must cost the icon, not the panel.
- **The measured cloud cover beats the nominal one.** `WeatherReading.cloudCover` prefers the response's `cloud_cover` percentage and falls back to the condition's figure. "Partly cloudy" spans two wisps to a nearly closed lid, and the sky is the one consumer that can show the difference.
- **Night is the location's, not the machine's.** `is_day` comes back from the forecast API for the place's own longitude, which is the only correct answer for a user watching a city eight time zones away.
- **A failure is a visible state.** `WeatherStore.error` is set by every failed refresh and the *last reading stays on screen* — an hour-old temperature is worth more than a blank card, and the error line says which one is being looked at. Both surfaces render it and both offer a retry, because every failure here is recoverable without restarting the shell (the network comes back, the API stops rate-limiting) and the shell cannot detect either happening. An empty bar module is indistinguishable from one the user never enabled; this is the rule `NotificationDaemonStatus` documents.
- **A unit or location change refetches; a cadence change restarts the timer.** `configure` compares the whole config (which is why `WeatherConfig` carries value equality — `Module.loadAll` pushes it on every sweep, and the settings UI notifies on every keystroke anywhere in it) and only a *changed* one acts. Waiting out the refresh interval — half an hour, since `refresh_minutes` defaults to 30 — to see a setting take effect reads as the setting not working.
- **The parse degrades per field, the way `TomlReader` does at the other end of the pipe.** A missing `current` block is fatal — there is no reading — while a ragged `daily` block costs the forecast alone: the day loop is bounded by the *shortest* parallel array, and a day with a hole in it is dropped rather than half-built.
- **A location is three config keys written together.** `location`/`latitude`/`longitude`, and `WeatherConfig.place` refuses a half-written pair outright — guessing which half to keep would put the user's weather on the prime meridian. An out-of-range coordinate is *absent* rather than clamped (`TomlReader.doubleOrNull`, added for this): a latitude of 400 is a typo, and clamping it to 90 would silently show the weather at the North Pole.

#### The glyphs (`weather_icons.dart`)

Meteocons, through `weather_icons_animated`, replacing Material Symbols — which replaced emoji. The set carries the WMO table's own granularity and then some: a *shower* is rain falling through a break in the cloud and Meteocons draws it that way, where Material Symbols had one `rainy` and a heavier version of it, so "Showers" and "Rain" were the same picture with different words under them.

Three things a change here has to keep true:

- **Nothing here animates, and the pack's moving formats are unreachable from this file.** The desktop widget's hero glyph used to be a Lottie — a `Ticker` running for as long as a wallpaper widget was on screen, beside a sky running another — and it is gone, along with the `lottie` dependency `pubspec.yaml` carried for one `FrameRate` constant and the `animate` flag every call site had to remember. `WeatherIcon` renders `svgStatic` and nothing else, which is what makes every surface that draws one safe to `pumpAndSettle`. (`svgAnimated` would never have been the alternative anyway: the animated SVGs carry their motion as SMIL, which `flutter_svg` parses and *drops*, so it is a still frame that merely costs more to parse.)
- **A tinted icon comes from an *outlined* family, never from the fill one.** `BlendMode.srcIn` over a full-colour Meteocon flattens it to a silhouette, and the silhouette of `partly-cloudy-day` is one blob where the sun and the cloud used to be. The outlined families survive being painted one colour, which is what the bar needs — a bar icon no theme can recolour is exactly what these replaced an emoji to avoid. Of the two it is **line** rather than `monochrome`, and the difference is not visual (`srcIn` flattens both to the same outline): 196 of the 236 monochrome files carry a `<style>` block nothing in them references, and `flutter_svg` logs `unhandled element <style/>` for every one it parses. `WeatherIcon` picks fill-vs-outline by whether the call site passed a `color`, so the choice cannot be made in one place and forgotten in another.
- **A slug this build does not know costs the icon, not the panel.** `conditionForCode`'s rule, applied to the pack: every name goes through `_glyph`, which degrades to `not-available`, and never through `WeatherIcons.named`, which throws — out of a `build`. `test/weather_icons_test.dart` is the other side of that guardrail, walking every row of the WMO table and failing on any that degraded.

Two things follow at the call sites. `size` is a box and a Meteocon is artwork inside a padded 512-unit viewBox — `clear-day` is 384 across — so a glyph asked for at 16 reads at about 12, and every size that came over from Material Symbols was grown by roughly a quarter. And `kLocationIcon` is still a Material Symbol: Meteocons is a weather set and has no place marker, so that one is drawn with a plain `Icon` at the two call sites that want it.

The settings row is `WeatherLocationField` (`lib/overlay/settings/shell/weather_location.dart`), the one `_ModuleSetting` in the Modules section whose control is not a value editor — a place name is what the user knows and coordinates are what the API wants, and only a geocoding request turns one into the other. It is a thin wrapper over `AnchoredSearchDropdown`, which grew an **async** `search` for it: debounced, answers applied in request order (a slow response for "lon" must not land on top of a fast one for "london"), and a throw reported as no matches rather than as a list left on the previous query's results. The automatic row is always first in the list, because it is how a chosen location is undone. It also carries the **synchronous** half: `lib/world_cities.dart` (below) is ranked on the keystroke and the geocoder's answers are merged in *under* those rows rather than replacing them — a request that lands must not take New Delhi off a list it was already on, a place the geocoder repeats is dropped rather than listed twice, and a failed lookup therefore costs the geocoder's half alone, because the table is local data and a network that is down is no reason to stop offering it.

#### The sky (`weather_sky.dart`)

**Nothing in it moves, and that is the design rather than an omission.** This painter used to run a 30fps `Ticker` for as long as the widget was on the desktop — which is to say permanently, on a machine that may be doing nothing else — for a decoration. There is now no `Ticker` in the file, no `ValueNotifier` handed to a painter, no `animate` flag, and no `kSkyFrameInterval`: the card paints once per change of conditions and costs nothing at all until the next reading lands half an hour later. The consequence for tests is that a tree containing `WeatherSky` may be `pumpAndSettle`ed like any other; the consequence for the *picture* is that a still frame has to carry what motion used to, which is what the rest of this list is about.

Six things a change here has to keep true:

- **The layout is data, computed once.** `SkyField` holds every cloud, star, drop and fog band as plain numbers built from a *seeded* `math.Random`, rebuilt only when the conditions move. That is what makes "how many clouds at 60% cover" and "nothing falls out of a clear sky" plain unit tests with no canvas behind them, and with no ticker it is also the whole per-card cost. The seed is fixed so the same weather draws the same sky on every monitor and across a restart — a field that reshuffled itself on every rebuild would be the most distracting thing on the desktop, and with nothing moving it would be the only thing that ever changed.
- **Everything a frame used to derive from the elapsed time is a field instead.** A drop carries its `y` rather than a phase and a speed, a star its `brightness` rather than a twinkle rate, a fog band its `shift` rather than a drift. And a drop knows its own `SkyDropShape` — streak, flake or pellet — rather than the painter re-deriving it from `precipitation` plus a sideways-drift test, which is what lets sleet be a genuine mixture in the one place that decides it. The drops are also *stratified* down the box rather than scattered: a still frame is studied, so a clump stays a clump.
- **Depth is what makes a still sky a scene.** Each cloud carries a `depth`; the far ones are smaller, higher, paler and flatter, the near ones larger and more contrasted, and the list is sorted back to front. Without it a static field reads as stickers on a gradient, which is exactly what the drift was hiding. Clouds are also kept to a band across the top of the card and sized against `min(width, height * 1.5)` — the readout is everything below that band, and a cloud sized off the width alone is twice the height of a 2x1 card.
- **A cloud is one path, not a pile of circles, and it is painted in three passes.** Overlapping ovals in a single non-zero path fill as their union, so a translucent cloud has no seams where its puffs overlap; separate circles make it a cluster of bubbles. The passes are a blurred mass beneath it, the graded body, and a lit crown clipped back inside its own silhouette — a flat fill is the other half of what read as amateurish, and the crown has to stay blurred by more than it is shifted or it leaves a hard white wedge where the shifted silhouette crosses one of its own notches. `cloudsForCover` returns **zero** below 5% — a stray cloud over a "Clear sky" label is the picture contradicting the reading beside it — and **fog draws no clouds at all**, whatever the cover says: what is in the air is the weather, and a bank of edged clouds over the haze bands is indistinguishable from overcast.
- **A thunderstorm gets a bolt, not a flash.** A veil that appears for a fifth of a second every six is either always on or never seen in a picture painted once, so the field carries one `SkyBolt`, drawn left of `kCelestialCentre` (a stroke through the disc reads as a mistake), stopping above the readout, and tapering — segment by segment with a falling stroke width, because a stroke is uniform and a bolt that does not taper is a lightning *symbol*. The shape is a real zig-zag, each segment crossing back over the last; a stroke that only wanders is a scratch on the card.
- **The disc is dimmed by washing towards haze, and ramped off a floor.** A half-transparent yellow disc composited over a blue sky is *green*, and so is a yellow lerped halfway to blue; washed out to haze white and then faded on a square-root ramp it goes pale the way a sun behind thin cloud does. `celestialOpacity` subtracts a floor before rescaling, because the clouds no longer cover the whole card: at 90% cover the old linear figure left a pale circle hanging in clear air below the cloud line, which reads as a smudge on the wallpaper rather than as the sun.

The desktop widget draws the reading over it, and three things follow from the sky being the card. Its `DesktopWidgetSpec` asks for `padding: EdgeInsets.zero` — a field added for it, defaulting to the `EdgeInsets.all(10)` the frame used to hard-code — and `PopupCard` clips to the theme's radius, so painting to the rim is rounded for free. Its text is **white on a `SkyScrim`**, not on the theme: the palettes run from a near-black thunderstorm to an almost-white snowfall and no theme foreground is legible on both, the same call the lock screen makes over a wallpaper. And the expanded layout carries **no hero glyph** — it used to set a 58px Meteocon beside the temperature, a drawn sun over a sky already drawing one, which was the single thing on the card that read most like a first draft. The sky is the condition's picture and the label under the reading is its name; the small tinted glyphs survive in the detail row and the forecast strip, where they are labels rather than a second subject. The compact 2x1 layout keeps its icon, because at that size there is no sky left to read.

**What fits is measured, not thresholded.** The layout used to decide what to draw from pixel constants — "details need 250px of card, a forecast needs 190" — two numbers only ever right for one type size, which quietly disagreed with each other about the shed order they were supposed to implement. `_Sections` (`desktop/widgets/weather_widget.dart`) answers how tall each block is *at the size it will actually be set in*, and the layout takes blocks in priority order until the next will not fit: the forecast strip goes first, then the day's high and low (the big number above it is today's actual temperature), then the detail row — and within that row wind goes before humidity and humidity before feels-like. That is also what lets the content column be built from plain `SizedBox` slack rather than `Spacer`s, since nothing is laid out into less room than it needs; an `OverflowBox` above it makes the pixel or two the estimate can be out cost a clipped row rather than a flex overflow. Both rows that decide what fits **measure** — the detail row's labels and the forecast column's high-and-low pair — through one `_measureText` that reads the style off `DefaultTextStyle`, because the same readings fit under one theme's font and overflow under another's, and a measurement taken in the platform default is a measurement of a different font.

**Every size on that card is one table times one factor, and the factor is sub-linear.** This is the only widget in the shell the *user* resizes, in a grid whose cell size they also choose, so a literal chosen against one card is wrong on every other one — the forecast strip was set at 10px against a 30px reading and stayed at 10px on a card four times the area. `_CardScale` multiplies the whole table through by the **geometric mean** of the two edge ratios against `_referenceCard` — the 312x204 a 3x2 widget occupies on the default grid — because a card stretched wide but left one row tall has no more room for a bigger type than it started with, and taking the wider edge would set it in a size its own height cannot carry. It then raises that to `_scaleExponent`, and **that is not a taste decision**: the geometric mean of the edge ratios *is* the linear scale, so applying it exactly is the one law under which the content occupies the same fraction of the card at every size — under which nothing new can ever fit, however far the widget is dragged out, which is why the old card had to gate its forecast strip on a raw pixel threshold instead. It never goes **below 1**: the literals are a floor rather than a midpoint, and a card under the reference is already being laid out at its own minimum and clipped rather than asked to draw a smaller version of itself. `_forecastDays` scales its per-column budget by the same factor, so a bigger card answers mostly with the same days set larger — the count rises far more slowly than the width does — rather than with a row of cramped columns.

### Lunar phase (`lib/moon/`, `lib/desktop/widgets/moon_widget.dart`)

Which phase the Moon is in, drawn, and what that does to the world. The third desktop widget, and the first feature in the shell whose data source is neither a daemon nor a web API but arithmetic: everything on the card is a pure function of the clock and — for two of its lines — a pair of coordinates.

| File | Responsibility |
|------|----------------|
| `moon_ephemeris.dart` | The astronomy. Meeus's chapter 47 tables in full (60 longitude/distance terms, 60 latitude), the Sun's chapter 25 series, obliquity, sidereal time, and the Moon's altitude for an observer. Flutter-free and clock-free, so it is a plain unit test. |
| `moon_phase.dart` | `MoonPhase`, `MoonReading`, `computeMoonReading`, the phase search, and `moonTimesFor` — the rise/set scan. |
| `moon_facts.dart` | `MoonFact` — tides, night light, stargazing, eclipse windows, distance and the next phase, as a kind, a title and a sentence. |
| `moon_format.dart` | The readouts: `HH:mm`, `28 Aug`, `in 6 days`, grouped kilometres. `lib/timers/timer_format.dart`'s split. |
| `moon_store.dart` | `MoonStore.instance` — the singleton `ChangeNotifier` with `WeatherStore`'s lease rule and a one-minute tick. |
| `moon_render.dart` | `MoonDisc`/`MoonPainter` — the drawn Moon — and `MoonNightSky`, the backdrop. |

Eight things a change here has to keep true:

- **The location is the weather module's, and borrowing it must not start a forecast poll.** `[modules.weather] location` is where a user has already said where they are, and a second place to say it would be a second place to keep in step. `WeatherStore.resolvePlace()` was added for this: configured coordinates first, then whatever a weather fetch has already resolved, then one IP lookup — shared with `refresh`'s and cached for the life of the shell, so a machine with a configured location opens no socket for the Moon at all. It answers null rather than throwing, because its caller works without it.
- **A missing location is not a failure, and the widget must not render it as one.** The phase, the illumination, the age, the tides and the eclipse windows are the same everywhere on Earth; the coordinates buy the rise and set times and which way up the disc is seen, and nothing else. So there is no loading state and no error state — the one row that needs a location says what would be gained, and the rest of the card is unaffected. `MoonStore.locating` is what separates "still looking" from "asked, and there is no answer".
- **Every phase instant is found by search, never counted off a mean lunation.** Real lunations run from 29.27 to 29.83 days, so epoch-plus-multiples is up to seven hours out — a full moon predicted on the wrong evening. Newton's method against the true elongation costs about six position evaluations and lands within a couple of minutes of the published times. Both searches are *strict*: asked for the next full Moon at the instant of one, the answer is next month's, or the readout says "full moon in 0 days" for the fourteen hours either side.
- **The rise/set scan samples and bisects rather than interpolating three positions.** The Moon is the body that makes Meeus's closed form awkward — its declination moves degrees in a day and its parallax moves the horizon it is measured against — and a scan handles the days with two moonrises, or none, by simply not finding a crossing. `MoonTimes.alwaysUp`/`alwaysDown` is what lets a circumpolar day say which one it is instead of showing two blanks. It is computed once per local day and cached, and the day is built from its parts (`DateTime(y, m, d + 1)`), because the day the clocks change is 23 or 25 hours long.
- **The Moon is painted, not photographed.** The shell ships no image assets at all — no `assets:` section, themes embedded as constants, wallpapers found by path — so a NASA render would be the first, in the Flutter bundle *and* the Makefile *and* the snap. And one photograph is one phase: a lunation needs thirty of them, or a shadow drawn over one, at which point the shadow is `moon_render.dart` anyway. The terminator is therefore computed as the ellipse it is (semi-axis `r × (1 − 2f)`, signed, so one expression covers crescent, quarter and gibbous); the dark side is drawn in earthshine rather than left out, because "the old Moon in the new Moon's arms" is a real sight and a crescent floating on nothing reads as a clipping bug; and the southern hemisphere gets the canvas rotated half a turn, which is why the maria are held in unit-disc coordinates.
- **Nothing on this card animates, and that is worth keeping.** No ticker, no `Ticker`-shaped trap: the picture changes over hours and the widget can be on a desktop for weeks. This was the one desktop widget a test could `pumpAndSettle`; the weather card has since joined it, for the same reason. The star field dims as the Moon brightens — which is not decoration but the same fact the "stargazing" line states, and a card showing the same brilliant field behind a full Moon as behind a new one would be contradicting its own text.
- **A fact says only what the numbers support.** Spring and neap tides, dark skies for meteor watching, the reduced activity of nocturnal animals under a bright Moon, and the eclipse windows (a syzygy within 1.5° of a node) all follow from the geometry the feature already computes. Everything the Moon is popularly supposed to do and demonstrably does not — to sleep, to moods, to birth rates — is absent on purpose, and adding one back is making the shell lie to somebody. The tide direction is *which milestone is next*, not which is nearest: three days after a new Moon the range is still near its spring maximum and is nonetheless shrinking.
- **Every number on this card is derived once per reading, and the picture is repainted at the resolution it can show.** This feature is arithmetic rather than I/O, which makes it the one place in the shell where the *computation* is the cost — and three separate paths were paying it far more often than the reading moved. `MoonReading`'s four phase instants are **memoised getters, never constructor arguments**: each is a Newton search over the whole of Meeus 47.A/B and together they were nine tenths of a reading, charged every minute to a `_publish` that needs none of them and to a compact card that draws neither an age nor a countdown (a tick is 8x cheaper for it, and `nextPrincipalTime` is *answered from* `nextNewMoon`/`nextFullMoon` where it is the same search). `MoonStore.facts` derives `moonFacts` once per reading, because the widget reads them from `build` and a desktop widget's `build` runs on every frame of a drag — the rule `_WeatherSkyState` states about its field, with two more ephemeris evaluations behind it. And the illumination reaching either painter is snapped to `kDrawnIlluminationStep` (`moon_render.dart`), which is what stands between a continuously-moving reading and the most expensive painter in the shell: a thousandth of the disc moves the terminator a twentieth of a pixel, so the repaints it suppresses are ones nothing could have seen. The same file's ray systems are one stroked path each rather than nine strokes, because a `MaskFilter` is an offscreen blur per *draw* — and the store's `_publish` signature carries only values a surface actually renders, which is why the altitude and `isUp` are not in it.

### Fortune (`lib/fortune/`, `lib/desktop/widgets/fortune_widget.dart`)

A line out of `fortune(6)`, set over an oil lamp in the dark. The fourth desktop widget, and the first whose content the *user* asks for: the weather and the Moon refresh themselves because the thing they report on moves, and a fortune does not — so nothing here polls, and the only thing that ever replaces the text is somebody pressing for it.

| File | Responsibility |
|------|----------------|
| `fortune_reader.dart` | The `fortune` command behind an injectable runner (`DiskReader`'s shape), plus `normalizeFortune` — the pure unwrap of the cookie files' 70-column hard wrapping. |
| `fortune_store.dart` | `FortuneStore.instance` — the singleton `ChangeNotifier` with `WeatherStore`'s lease rule and no timer at all. |
| `fortune_text_fit.dart` | `fitFortuneText` — which rung of the size ladder a fortune is set on, measured with the very `TextStyle` the card renders in. |
| `lamp_scene.dart` | The picture: `LampField` (the layout, as data), `LampGeometry` (where the lamp and the fortune go), `LampPainter`, `LampScene`, `LampScrim`. |

Seven things a change here has to keep true:

- **One fork for the machine, and the lease is what makes it one.** The desktop surface is one FlutterView per monitor, so without the store this would be one `fortune` per display showing a *different* line on each — and a two-monitor user pressing refresh on one card would watch the other one not move. The first lease fetches (which is the "when you start the shell" half); later ones find a fortune already there and fork nothing. Nothing polls, because a fortune does not go stale and one that replaced itself on a cadence would be a card that silently threw away the line the user was in the middle of reading.
- **`refresh` notifies at the end and never at the start**, which is what makes it safe to call from `acquire` — that runs inside the acquiring widget's `initState`, and a synchronous `notifyListeners` from there is a `setState` on every *other* surface already holding a lease, during a build. `WeatherStore.refresh` is arranged the same way and for the same reason. The consequence is deliberate: a refresh over an existing fortune does not report as `loading` at all, because replacing the card's whole contents with a spinner for the few milliseconds a fork takes is a flash rather than feedback — the button's own feedback is its hover tint and the fortune changing, and nothing else.
- **`/usr/games` is tried by name, and a missing command is a visible state.** `fortune-mod` installs to `/usr/games`, which is on a login shell's `PATH` through `/etc/profile` but is **not** inherited by a graphical session started from a display manager — so on the distributions where `fortune` is most likely to be installed, `Process.run('fortune')` is also most likely to answer ENOENT. Reporting that as "not installed" would be wrong on exactly the machines that have it. When no candidate answers, the card says so and names the package (never a package *manager* — it is `fortune-mod` on Debian, Fedora and Arch alike, and guessing between three managers is how a hint becomes wrong on two distributions out of three). A failed refresh keeps the last fortune on screen: `WeatherStore.error`'s rule.
- **The size is measured, never counted.** A fortune is four words or twelve lines and the card is the same size either way, so the type size comes from laying the text out at each rung of a ladder until one fits — `TrackMarquee`'s discipline, for the same reason it has it. Two things inside that. The ladder is discrete because a continuous solve lands on 13.7px and a card resized by a pixel would re-set its whole fortune imperceptibly differently. And **`maxLines` is always a number, never null**: a `Text` carrying `TextOverflow.ellipsis` with no line cap does not wrap and ellipsise the last line the box holds, it collapses to **one line** — so the obvious shape for that field renders a four-line fortune as its first eight words on every card, whatever the measurement said.
- **The fortune goes above the lamp; beside it is the fallback.** Above is the wider of the two boxes, and width is what a paragraph wants — the same fortune in a 250px measure and in a 145px one is four comfortable lines against nine narrow ones. Picking by *area* is the obvious rule and it chooses the narrow ribbon on nearly every card, because a full-height column beside the lamp is always the larger rectangle and never the better one. Beside is therefore kept for the shape that leaves nothing above the lamp at all (a one-row widget, or a six-column one left one row tall), chosen on a height threshold rather than a span — the two shapes cross over at a different place for every cell size the user can configure.
- **There are two ways to ask, and the lamp is one of them.** The explicit button in the corner is the feature; a genie's lamp that could not be *rubbed* would be a picture of the wrong thing, so the lamp body is a tap target too, and hovering it brightens the flame — a hover cue on a picture, because there is no rim to light up and a cursor change alone does not say the lamp is the thing to press. Both are taps rather than pans: the card is dragged from anywhere on it, and the two recognizers resolve against each other — a press that moves is the drag, one that does not is the button. It follows, as it does for the media widget, that nothing on this card may grow a *pan*-driven control.
- **The picture is a still frame, and nothing on this card animates.** The field is data built from a *fixed* seed (so the same smoke curls the same way on both monitors and across a restart) and `LampPainter` is a pure function of it at one instant — `kLampStillMoment`, chosen by looking at the alternatives: a plume continuous from the flame to the top of the card with puffs at every stage of their climb. There is no `Ticker` and no per-frame repaint, which is the lunar widget's rule applied with more force, because this card has no excuse of reporting on something that changes: a decoration on a wallpaper, on a machine that may be doing nothing else, has no business repainting for as long as the desktop is switched on. Two consequences to keep. The card is **`pumpAndSettle`-able**, unlike the weather widget, and `fortune_widget_test.dart` pins that with a settle plus `transientCallbackCount == 0` — a ticker added anywhere in here hangs that test rather than merely failing it. And a new fortune replaces the old one **outright**: a fade or a slide would be the only moving thing on the card, moving exactly when the user has asked to read something. The one thing left that moves is the hover tint every control in the shell has, `DesktopWidgetFrame`'s own selection rim included; the lamp's rub glow is a discrete repaint on hover rather than a transition. The lamp is painted rather than photographed for `moon_render.dart`'s reason — the shell ships no image assets at all — and drawing it is also what puts the smoke at exactly where the spout is at every size the grid allows.

The card's text is white on a `LampScrim`, not on the theme, which is the call the weather widget, the lunar widget and the lock screen all make: the scene runs from a near-black sky to the glare beside the flame and no theme foreground is legible across both. The scrim is diagonal rather than `SkyScrim`'s bottom-up, because the readout on this card is in the corner *opposite* the light and dimming the lamp's own corner would be dimming the point.

### Tux (`lib/tux/`, `lib/desktop/widgets/tux_widget.dart`)

A penguin who says one nice thing a day. The fifth desktop widget, the smallest, and the first whose subject is nobody and nothing: the weather reports on the sky, the Moon on the sky at night, the fortune on a program installed on the machine, and this one reports on the fact that somebody turned the computer on.

| File | Responsibility |
|------|----------------|
| `tux_greetings.dart` | The lines, the salutations, and which of each today gets. Pure — no `package:flutter` and no `package:meta` behind it — plus `dayOrdinal` and `nextRollover`, the two pieces of calendar arithmetic the store needs. |
| `tux_art.dart` | `kTuxSvg` — Tux as SVG *source*, embedded as a string constant — and `TuxArt`, the one place `BoxFit.contain` is spelled. |
| `tux_store.dart` | `TuxStore.instance` — `FortuneStore`'s lease shape with a one-shot midnight timer instead of a fetch, plus `tidyGreetedName`/`defaultGreetedName`. |

Seven things a change here has to keep true:

- **The greeting is a function of the local date, and the store holds none of it.** `TuxStore.greeting` is `greetingForDay(now())` and nothing else. That is what makes both monitors agree (the desktop surface is one FlutterView per display, and a line picked at random per build would differ across them and change on every rebuild — a greeting that rewrote itself while it was being read), what makes a restart bring back the same line, and what makes "it changes once a day" true without anything having to notice that it did.
- **The rotation is a full permutation, not a hash.** `ordinal % n` recites the list in written order; hashing the ordinal repeats a line two days running about once a month. `_strideFor` takes the first stride coprime with the list length at or above its golden-ratio fraction, so every line is seen once before any is seen twice and consecutive days land far apart in the list. `test/tux_greetings_test.dart` walks a full cycle and fails on the first repeat.
- **Every day count goes through UTC midnights, and the rollover instant is built from the date's parts.** Differencing two *local* `DateTime`s measures elapsed time and `inDays` truncates a 23-hour spring-forward day to 0 — which would repeat yesterday's greeting — and `add(Duration(days: 1))` on that same day lands an hour past midnight. `overlay/calendar/month.dart` states both halves of this rule at the other end of the shell; this is the same rule with a greeting behind it instead of a grid.
- **One timer for the machine, held by a lease, and it is a one-shot.** `TimersStore._syncTicker`'s rule: the last `release()` cancels it, so a desktop with no Tux on it arms nothing at all and an idle shell wakes for this exactly never. It fires *once*, at the next local midnight, rather than ticking — the thing being waited for happens once a day, and a card that repainted every minute to notice it would be the most expensive still picture on the desktop. `acquire()` notifies nothing, for `FortuneStore.refresh`'s reason: it runs inside the acquiring widget's `initState`.
- **Nothing here claims anything about the user.** These are the lines a friend says on the way past, not affirmations that assert facts about somebody the shell knows nothing about — a greeting that told the user they were doing great on a day they were not is worse than one that just says hello. Two smaller rules fall out of the same honesty. No line and no salutation may name an *hour* (`Morning` is wrong more often than it is right on a greeting fixed for the whole calendar day, and making it right would mean three more timers for a card whose whole reason for existing is that it wakes once); `today` and `tomorrow` are fine, because the greeting *is* today's. And the name is the account's GECOS first name, from `lock/user_identity.dart` — the place the lock screen already asks, so there is not a second one to keep in step — put through `tidyGreetedName`, which says **nothing** rather than something odd: `Hello, svc_build_agent_07` is a shell echoing a variable, and a bare `Hello` is the correct greeting for a machine whose passwd entry says nothing about a person.
- **1x1 is the design, not the degraded case.** Every widget before this one takes two cells at its floor because a phase name, a track title or a fortune needs a width of text to sit in; this one is a picture, and a single cell is exactly what a picture holds. 96 logical pixels holds a drawing or a sentence and not both, so at that span the card is Tux and hovering him reveals the greeting over the whole card — setting the line under him at 7px instead would be a card that technically shows the greeting and factually shows it to nobody, which is the rule `fitFortuneText` already states about a fortune set too small to read. Two cells wide moves the line out beside him permanently; two cells *and* two rows moves it under him, larger. The arrangement is chosen by **span**, never by pixels, because the pixels follow a cell size the user sets — and the type size inside it is **measured**, through `fitFortuneText`, which this borrows rather than growing a second ladder beside: it is the fortune card's by history and not by subject.
- **He is on the theme's card, and nothing on it animates but the hover.** The weather, lunar and fortune widgets paint a backdrop and set white text on it because their pictures run from near-black to near-white and no theme foreground survives both; Tux is one drawing on a flat surface, so the surface may as well be the `PopupCard` every other floating thing in the shell uses and the greeting is then plain themed text that follows the theme's font and colours. A new line — from the day turning over or from a tap — replaces the old one **outright**, with no fade and no slide, for the fortune card's reason: it would be the only moving thing on the desktop and it would be moving exactly when somebody has just asked to read something. `test/tux_widget_test.dart` pins that with a settle plus `transientCallbackCount == 0`.

**The drawing is a string constant, which is what keeps "the shell ships no image assets" true.** `moon_render.dart` and `lamp_scene.dart` state that invariant and it still holds literally — there is no `assets:` section in `pubspec.yaml`, nothing for the Makefile to install and nothing for the snap to stage — because `kTuxSvg` is embedded the way `theme/builtin_themes.dart` embeds the shipped palettes as TOML text, and works identically under `flutter run`, `make install` and the snap, none of which resolve paths relative to the bundle. It is SVG rather than a `CustomPainter` because the request was for an image that scales: an SVG is artwork somebody can open, edit and swap for a different penguin, where a painter is a function only Dart can read. Four things it has to keep. It carries a `viewBox` and **no** root `width`/`height`, which would argue with `BoxFit`. It is **flat** — solid fills, no gradients, no blurs — because 1x1 is the size it is for and every one of those is the first thing to go at 96px, which is also why the shapes that identify him (the white front, the orange beak, the two eyes looking slightly inward) are the largest things on the canvas. The flippers are a shade **lighter** than the body, because pure black on black is a silhouette with no penguin in it and the raised one has to read as an arm rather than as a nick out of the outline — and he is off-centre in his own `viewBox` precisely so that raised flipper has somewhere to go. And there is no `<style>` and no SMIL: `flutter_svg` logs `unhandled element <style/>` for every one it parses, which is what `weather/weather_icons.dart` picks a whole icon family to avoid, and drops SMIL silently. `flutter_svg` moved from `dev_dependencies` to `dependencies` for this — it was test-only for as long as the only thing naming it was `weather_icons_test.dart` pinning which Meteocons variant each rendering reaches for.

### The overlay (`lib/overlay/`)

Clicking the clock opens a full-screen layer-shell overlay (`lib/overlay/overlay.dart`, class `SettingsOverlay`) — a scrimmed backdrop over a fixed 800x560 panel with **top tabs**. Adding a tab means one entry in the top-level `_tabs` list plus one child in the `IndexedStack` that builds the body.

The body is an `IndexedStack`, not a `switch`: the settings tab hosts `ShellSettingsPage`, which owns a nested `Navigator`, and rebuilding the body on every tab change would tear it down and drop the user back to the category landing page.

**The Shell pane's routes are instant, and a route transition here is very likely a mistake.** Every route in that nested `Navigator` fills the same box against the same opaque panel fill, so an animated push spends its whole duration drawing the outgoing page *through* the incoming one — which reads as the pane flickering rather than as movement, and is what the 220ms slide-and-fade this replaced actually looked like. `_categoryRoute` (`settings/shell.dart`) is therefore a `PageRouteBuilder` with `transitionDuration` and `reverseTransitionDuration` at `Duration.zero` and no `transitionsBuilder` at all. If one is ever wanted back, note the trap the old code documented: `ModalRoute` calls `transitionsBuilder` from a `ListenableBuilder` on the route's own animations, so it runs on every frame of the push — a `CurvedAnimation` spelled inline there is minted per frame, registers a status listener on the parent it never unregisters, and hands the transition widgets a different `Listenable` each tick, so they re-subscribe instead of simply being ticked. It belongs in a `State` that owns the curve for the life of the route and disposes it.

**The panel is opaque whatever the theme says.** `overlayPanelFill` (`overlay.dart`) takes `popup_background`'s colour and overrides its alpha, so a translucent palette — `glassy` ships `popup_background` at `0xB0` — still tints the panel but cannot make it see-through. What is right for a three-row menu is wrong for this surface: it is a workspace of small text, chart strokes and form fields, and reading them through the wallpaper is what the translucency costs. Depth comes from the scrim `FadeOverlayScaffold` paints behind it, which dims the desktop without taking contrast off the content. `test/overlay_panel_fill_test.dart` pins it.

**And so is everything that floats over it.** The same reasoning applies with more force one layer up: a dropdown list, a colour picker, a confirmation or the file picker is read *over the panel's own form rows*, so a translucent card shows the page it is covering straight through itself and neither layer survives. `OpaquePopupScope` (`lib/popup_surface.dart`) — the sibling of `PopupAttachScope`, which carries the joined panel edge the same way — is the marker that says so, and `SettingsOverlay` wraps its **`Overlay`** in one — above it rather than inside the panel, because that is where `showRootModal` and every `AnchoredSearchDropdown` insert their cards. `PopupCard`/`popupDecoration` read it themselves; the four surfaces that hand-roll their own fill (the search dropdown's card, the colour picker, the file picker, and the panel) go through `OpaquePopupScope.fill`. Only the alpha is overridden — the hue, rim, rounding and shadow stay the theme's — and the scope cannot span FlutterViews, so a popup opened as its *own* layer-shell window (the root-owned file picker and app chooser the desktop surface uses) is outside it and keeps the theme's alpha. `test/opaque_popup_scope_test.dart` pins it.

The flip side, and the trap for the next tab author: **`IndexedStack` keeps every tab alive once built.** A tab that owns a `Timer` keeps running it while the user is on some other tab. A tab that polls must therefore be told when it is the visible one — see `SystemTab.active`, which drives the lease it holds on `SystemStatsStore`, and `CalendarTab.active`, which drives the world clocks' one-second tick. Both are **required** parameters, so a call site cannot forget.

- **`lib/overlay/settings/`** — the settings tab: a sidebar (Network / Bluetooth / Display / Audio / Shell) over one page per category. `controls.dart` holds the themed form controls (`SettingsSection`, `SettingsRow`, `SettingsToggle`, `SettingsActionButton`, `SettingsDropdown<T>`, `SettingsBadge`, `SettingsRescanButton`, `SettingsTextField`, `SettingsIconButton`, …) shared with the calendar and system tabs. **Pages under `overlay/settings/` import `controls.dart`; they never redeclare a control.** This is a greppable rule like the ThemeScope one — the four big pages each used to carry private clones with 6–11-line drifts, which is how the audio and bluetooth pages lost the theme font and the display page froze its palette (its clones took `ThemeConfig` as a constructor parameter). A control the library lacks gets *added to the library*, generalized from the best copy. `test/settings_shared_controls_test.dart` pins the theme-font half of this. The audio pages' mute toggles, the file picker's hidden-files eye, the network page's back arrow and the notification panel's two dismiss ✕ were four more hand-rolled icon buttons; they are `SettingsIconButton` now, which grew `box`/`color`/`hoverColor`/`enabled` so the dense 18-square cases (the world clocks' remove ✕, the panel tabs' close ✕) fit it too. The system monitor's popup sub-tabs were the one `UnderlineTab` clone that survived that migration. `SettingsTextField` grew the same way when the file picker wanted a search box: `leading`/`trailing` are the slots that make it one (a magnifier, a clear ✕) and `controller`/`focusNode` let the caller *drive* it — Ctrl+F focuses and selects, Escape clears. Two rules fall out of that. A borrowed controller or node is never disposed by the field, and its focus listener is removed by name rather than left as a closure on a node that outlives it. And `trailing` must be a widget in both states, never null in one: swapping it in and out restructures the field around its `EditableText`, which re-inflates the element and drops the focus the user is typing into — the picker passes a spacer of the clear button's own size.

  **There is one dropdown, and it is a real one.** Every selector in the settings UI — the audio device and profile pickers, the display pane's mode list, the font row, the time-zone and weather-location pickers, the module adder — is `AnchoredSearchDropdown`, floating its card in the *root* overlay. Two of them used to expand *inline* instead, pushing the rest of the form down the moment they opened, which on the audio and display pages is everything the user was about to reach for; the module adder shoved a panel's own module slots off the pane the user was picking a module *for*. Three things follow from making them one control. The card is the **trigger's** width (`matchTriggerWidth`), because a card narrower than the control it drops out of reads as a different control and a wider one overhangs the row — except where the trigger is a compact action at the pane's right edge rather than a full-width row, and the module adder is now the one of those: it takes `alignRight` and grows leftwards instead (see the add-button rule below). It **flips above the trigger** when the room below will not hold the list — an inline dropdown could not open off the bottom of the screen and a floating one can, so the side is chosen at open, from the rows it would show. And it carries a filter field only past a threshold (`showSearch`, `SettingsDropdown.searchFrom`): a search box over the two outputs a machine has is chrome asking to be typed into, while a monitor's thirty modes genuinely want one. `test/settings_dropdown_test.dart` pins all of it — the floating half by asserting the row's rect does not move when the list opens.

  **A row that has to explain itself takes the card's width off the prose, not off the trigger, and measures it.** `SettingsDropdownItem` has two dim slots and they are not interchangeable: `detail` is a word or two sharing the label's line — the display pane's `preferred` — laid out *unflexed* beside an `Expanded` label, so a sentence put there takes the whole row, ellipsises the label to nothing and is then clipped at the card's edge, which is what the popup-animation row shipped as. `description` is the slot for prose: it wraps under the label, and its presence is what gives the card a width of its own (`SettingsDropdown.cardWidth`, defaulted for a described list). Three things follow. Such a card **anchors its right edge** to the trigger's, `alignRight`'s reasoning reached from the other direction — a settings row's control sits at the pane's inner edge, so a card wider than it has somewhere to go only leftwards. Its **row extent is measured, never a constant**: the rows are one fixed extent because the generic's keyboard reveal is arithmetic over it, so the number has to be the tallest row's, and the same sentence is two lines under one theme's font and three under another's — `describedDropdownRowHeight` lays the text out in the very styles the row renders in and with the `MediaQuery`'s `TextScaler`, the rule `TrackMarquee` and `fitFortuneText` already state. And the row and the measurement share **one description cap** (`_kDescriptionMaxLines`) and one pair of styles, so a sentence longer than the card was sized for ellipsises rather than overflowing a box measured for fewer lines. `kDropdownRowInset`/`kDropdownCardPadding`/`dropdownContentWidth` (`lib/search_list.dart`) are public for the same no-drift reason: a caller sizing text to the card has to subtract exactly what the card puts around it.

  **An add button sits at the top right of the collection it adds to, never under it.** An adder below a list walks down the pane every time it is used — a panel's third module slot pushed "Add module" off the bottom of the scroll view outright, and the Desktop page's two adders moved further away with every pin. `SettingsSubLabel.trailing` is the slot for a list inside a section ("Pinned items", "Shown", "Left modules"), `SettingsSection.trailing` for a section whose whole body *is* the collection (the theme picker's "New theme…"), and `SettingsStringListEditor` renders its own heading and puts its adder there. The button is a `SettingsAddButton` at `ShellSizes.iconButton`'s height, so it lines up with the column of row icons below it. Two things follow. A free-form adder — the flavour with no `suggestions` to rank — keeps its text field but the button is what *reveals* it, above the rows, so both flavours are the same control in the same place; the same shape "New theme…" and "Add panel" already had. And a dropdown adder is `alignRight`, not `matchTriggerWidth`: the trigger is now a compact action at the pane's right edge, so the card grows leftwards from it rather than being sized to it. "Add panel" is pinned *outside* the panel tab strip's scroller for the same reason it moved at all — as the last tab inside it, the one control that creates a panel scrolled out of reach exactly when there were enough panels to want another. `test/settings_add_button_test.dart` pins the placement.

  The two big pages are split along their own seams: `settings/shell/` holds one file per Shell category (`appearance.dart`, `modules.dart`, `panels.dart`, `background.dart`, `desktop.dart`, `lock.dart`, `calendar.dart` — `shell.dart` keeps the page scaffold, the category table, and the nested Navigator), and `settings/audio/` one file per audio tab plus `audio_slider.dart`/`level_meter.dart`. Two structural rules live in those splits: the modules section's rows are a declarative `_ModuleSetting` table whose defaults are read off each module's *const config object*, so they cannot drift from `fromMap`; and the appearance section's `ListenableBuilder`s are scoped to the theme-value subtrees, because `ThemeStore` notifies on every frame of a colour-picker drag.
- **`lib/overlay/settings/settings_search.dart` + `settings_catalog.dart` + `settings_search_bar.dart` + `settings_highlight.dart`** — the search field across the top of the settings pane, and "take me to that field".

  The settings are two hundred-odd controls over six sidebar panes and eight Shell categories, which is a good arrangement for *reading* and a poor one for finding: a user who wants the bar taller has no way to discover that the row is called "Height" under Panels & Layout. The pieces are `settings_search.dart` (`SettingsField`, and a `rankSettings` in the shape of `launcher/app_search.dart`'s — pure, so the ordering is a plain unit test), `settings_catalog.dart` (the table), `settings_search_bar.dart` (the field and the results card) and `settings_highlight.dart` (the seam from a picked result to the row).

  Seven things a change here has to keep true:

  - **The catalogue is where the labels live, and that is the whole no-drift argument.** It is a hand-maintained table of destinations, which is exactly the kind of thing that rots — so every row it names is built with `SettingsRow.field`, which takes its label *from* the entry. A renamed setting is one edit, and there is no second copy of the string to forget. `modules.dart` goes a step further: a `_ModuleSetting`'s **config path is its entry's id split on the dots**, so a `[modules.*]` key, the row that edits it and the result that finds it are one string in one place — the same trick that file already plays with `fromMap`'s defaults. `theme/`'s palette moved the same way: `SettingsCatalog.themeColors` replaced the `_colorLabels` map the search would otherwise have had to copy.
  - **A description is prose the user reads; a tag is a word they would type.** Both are matched, in that order of weight, and the description is also the result row's second line — so what the index matched on is what is shown. Tags are for the words that are in neither the label nor the description: "wifi" for the Network pane, "colour" for the palette rows, "screenshot" for a directory called "Save to". Over-tagging is how a search stops ranking, which is why the network *module*'s poll interval is deliberately not tagged "wifi" — somebody typing that wants the Network pane, and a tie on an exact tag hit is decided by nothing better than the label's spelling.
  - **An empty query answers nothing**, not everything. The card floats over the pane, so a list of two hundred rows on the first click into the field would cover the page. `rankSettings` returns `const []` and the hint is what says what the field is for.
  - **Ties break by label and then section, never by table order.** Several modules have an "Icon size" and so does the desktop grid; the shell has to list them the same way every time, whatever order the catalogue happened to be concatenated in.
  - **The bar floats over the body and dismisses through a barrier.** It is a `Positioned.fill` whose field is drawn in the top-left corner, so the sidebar and the pane are laid out exactly as they were before it existed and the results card hangs *over* the very row it is about to send the user to rather than displacing it. `RenderStack` has no `hitTestSelf`, so at rest every click goes straight through to the page; while results are open the rest of the area is a `GestureDetector` barrier under them, which is `AnchoredSearchDropdown`'s arrangement and for its reason — most controls in this UI are `HoverRegion`s with no focus node, so a card that waited to lose focus would sit over the page through every toggle the user flipped.
  - **A jump moves three separate pieces of state, and only two of them travel through the controller.** The tab and the sidebar category are `_SettingsOverlayState`'s own; the Shell pane's route is a nested `Navigator`'s and the row's scroll offset is a `Scrollable`'s, and those are what `SettingsHighlightController` carries. `SettingsHighlightScope` is an `InheritedNotifier`, and who depends on it is deliberate: `_ShellCategoryView` does (its whole reaction to a jump *is* a rebuild), while the Shell pane and the rows read it with `readOf` and subscribe to the controller directly — a row that depended on the scope would re-lay every row on the page twice per jump, once on the target landing and once on it being cleared.
  - **Holding the page mounted is the mechanism, and the claim is what ends it.** A `SliverList` never builds a child far past the viewport, so a row forty settings down the Appearance pane has no element for `Scrollable.ensureVisible` to scroll to and would simply never be found. `_ShellCategoryView` therefore widens its `scrollCacheExtent` to effectively unbounded *while a target for its own category is pending* — the eager list the laziness exists to prevent, paid for one frame on an explicit user action. `SettingsHighlightController.claim` hands the target to the **first** row that matches (several rows legitimately share one id: every panel in Panels & Layout renders the same "Height"), that row scrolls to itself from a post-frame callback and clears the target, and the extent drops straight back to 600. A target nothing claims — a pane-level entry, a row behind a `ConfigValue` that is not rendering — expires on a timer rather than leaving a page mounted for the life of the overlay, and a result that highlights nothing never widens the extent in the first place.

  The pulse itself is `_SettingsRowHighlight` (`controls.dart`), and it is `UrgencyFlash`'s rule applied to a widget that repeats forty times a page: with no id it is a pass-through, with one it still holds no ticker until a jump claims it, and the `AnimationController` is **disposed the moment the pulse finishes** — so a row somebody searched for once does not keep a settled ticker and an `AnimatedBuilder` for the life of the pane. The breath is a raised cosine resting at exactly 0 in both directions, for `urgencyFlashWash`'s reason: the row has to pass through the very colour its neighbours are, or the pulse reads as that row being permanently different rather than as the one being pointed at. `test/settings_search_test.dart` pins the catalogue's invariants — unique ids, every route naming a category that resolves, every entry carrying a description — and `test/settings_search_bar_test.dart` pins the bar and the jump.

- **`lib/overlay/calendar/`** — the calendar tab, described below.
- **`lib/overlay/system/`** — the system monitor tab, described below.
- **`lib/overlay/file_picker.dart`** — the in-app file picker, opened either as a modal into the root `Overlay` (`showFilePicker`) or as a window of its own (`FilePickerWindow`, for the desktop surface, which has no usable `Overlay`; `FilePickerController` is that seam).

Four things a change to the picker has to keep true. **The right-hand pane has two forms and neither is the fallback for the other**: tiles, which is how a wallpaper is chosen, and a line-by-line list carrying size and modified date, which is how a config file is. `FilePickerViewMode` is runtime state like `_showHidden` and is deliberately not persisted — there is no config schema for a modal's own chrome — but it *is* remembered for the life of the process (`_stickyViewMode`), because adding three wallpapers is three opens of this dialog. **The search filters the folder being browsed and nothing else**: the tree is how you change folder, so a filter that reached across the filesystem would be a second and far slower way to navigate; changing folder therefore ends the search rather than carrying it. **Ctrl+F focuses it and Escape ends it, and only an Escape with nothing to end closes the dialog** — both are read by the dialog's own root `Focus`, which is an ancestor of the field, so they arrive from anywhere in the card. And **the query is a `ValueNotifier`, never `setState`**: the tree pane lists each expanded node's children on build, so a `setState` per keystroke would walk the open branch of the filesystem once per character; only the pane body, the footer's counts and the field's clear button listen. The listing itself is statted once per directory read into `PickerEntry`, for the same reason — the size and date columns are two syscalls per row, and the pane rebuilds on every keystroke.

The pure half — `listDirectory`, `matchesSearch`, `filterEntries`, `formatEntrySize`, `formatEntryModified`, and the older `readDir`/`sortEntries`/`subDirs` — is widget-free and pinned by `test/file_picker_test.dart` against a temp directory.

`lib/config_store.dart` (`ConfigStore.instance`) is the live, writable view of `config.toml` that the settings UI mutates; it is a `ChangeNotifier` with a debounced atomic write.

### Places (`lib/world_cities.dart`)

The shell's own gazetteer: three hundred-odd major cities, each with its country, its IANA zone and its coordinates. One table for the two pickers that ask the user where somewhere is, because each of them had a list already and neither was one a user recognises.

The world clock's came from the IANA database, whose names are *zones* rather than places — one representative settlement per offset history — so India is `Asia/Kolkata` and New Delhi, Mumbai, Bengaluru and Chennai are simply not in it, as San Francisco, Boston and Seattle are not in `America/Los_Angeles` and `America/New_York`. The weather's came from a geocoding request, which knows every one of them and answers none of them until the network does.

Four things a change here has to keep true:

- **A city carries its zone *and* its coordinates**, because the two pickers want different halves of the same row: the clock stores the zone and titles the row with the name, the weather stores the coordinates and the name. A table serving only one of them would be a second table to keep in step, which is the state this replaced.
- **A wrong zone costs that city, never the picker.** `worldTimeZoneNames` drops a city whose zone this build's database does not know rather than throwing — the `TomlReader` rule, applied to data the shell ships — and `test/world_cities_test.dart` resolves every one of them against the live database, because that degradation is otherwise exactly what would hide a typo.
- **`aliases` is what makes a renamed city findable.** Bombay, Madras, Calcutta, Saigon, Peking and Rangoon are what a good many people still type, and a picker answering "no matches" to a name printed on every map before 1996 reads as a broken search rather than as a rename. They are searchable and never displayed: the row says what the place is called now.
- **The head of the table is the answer to an empty query**, so it is ordered by how likely a row is to be the one wanted rather than alphabetically — a list opening on Abidjan, Abu Dhabi and Accra is a list nobody scrolls. The rest is grouped by region, which is the only order a person adding a city can maintain. The searchable text is folded to lower case once, when the `final` table is first touched — `TimeZoneName`'s trick, which is `SearchableApp`'s — so a shell whose user never opens the calendar or the weather settings builds none of it.

The file is Flutter-free and I/O-free, which is what keeps it a plain unit test and what lets `time_zones.dart` take it without dragging the weather layer in behind it. The `WorldCity` → `WeatherPlace` conversion therefore lives in `weather_location.dart`, at the one call site that wants it.

### Calendar (`lib/overlay/calendar/`)

The Calendar tab is a month grid the user can page through, beside a column holding the local time, the world clocks they have added, and the timers-and-stopwatches section under them. Account integration (Google Calendar, over OAuth) was removed and is unsupported — the tab does no network I/O, holds no credentials, and needs no start-up service, so `main()` starts nothing for it. The section is `lib/timers/`'s, not the calendar's (see below); the tab supplies it the `active` flag and the store seam, and nothing else.

| File | Responsibility |
|------|----------------|
| `month.dart` | Pure month math — `buildMonthGrid` returns a fixed 6x7 `MonthGrid`, so the panel never changes height between months. Days are built with `DateTime(y, m, n)`, never `add(Duration(days: 1))`, which drifts across DST. `dayDelta` is the same discipline for the `+1d`/`-1d` badge: both sides go through `DateTime.utc` midnights, because differencing two local dates measures elapsed *time* and `inDays` truncates a 23-hour DST day to 0. |
| `calendar_tab.dart` | The tab: the month pane, the divider, and the clock column. `weekStart` and `worldClocks` are constructor parameters that fall back to `[calendar] week_start` / `[calendar] world_clocks` from `ConfigStore`; widget tests inject **both**, because the singleton throws before `initShared()` and passing only one still reaches it. The `ConfigStore` listener is what makes a week-start change in the settings tab re-lay the grid, and an added clock appear, without closing the overlay. |
| `time_zones.dart` | The zone layer: lazy `ensureTimeZonesInitialized`, `worldTimeZoneNames` (the IANA zones merged with `lib/world_cities.dart`), `resolveZone`, the pure `rankTimeZones` and formatters, and the `ClockSource` seam (`SystemClockSource` / `FixedClockSource`). |
| `analog_clock.dart` | The dial. A `StatelessWidget` reads `ThemeScope` and passes plain colours into a `const` painter — the `time_series_chart.dart` convention. |
| `clock_column.dart` | The column: dial, digital readout, date, the world-clock rows, and the `footer` the timers section is passed in as. Owns the tick. |
| `timezone_picker.dart` | The `+` and its searchable list — a thin wrapper over `AnchoredSearchDropdown` (`lib/search_list.dart`), supplying only the trigger, the `rankTimeZones` ranking, and the city/region row. |

Six things a change here has to keep true:

- **`time_zones.dart` is the only file that imports `package:timezone`.** That is what keeps `rankTimeZones` and the formatters plain unit tests with no database behind them, and `config.dart` — parsed at start-up, long before the overlay exists — free of the dependency. The database is *data*, not the formatting machinery `month.dart` refuses: DST transition tables change by political decision every few months and cannot be hand-rolled.
- **`initializeTimeZones()` is called lazily, never from `main()`.** `package:timezone/data/latest.dart` embeds the database as a Dart byte literal, so there is no asset bundle and no binding forcing it earlier; the calendar keeps its "starts no service" property and the cost lands on the first overlay open. `standalone.dart` and `browser.dart` are the variants that read from disk or HTTP and are unusable here.
- **`resolveZone` returns null for an unknown name rather than throwing, and `config.dart` never validates one.** `getLocation` throws, and a hand-edited or deprecated zone in the config would then take down a build. The row renders as "Unknown time zone" with its remove button intact — dropping it at parse time would delete the user's data on the next write.
- **A zone tzdata has merged away is followed, not treated as unknown.** `package:timezone/data/latest.dart` embeds the **canonical** zones only — 341 of them — and recent tzdata releases have merged every zone whose rules have agreed since the 1970s into one another, leaving the old name behind as a *link*. That is `Europe/Amsterdam`, `Europe/Copenhagen`, `Europe/Oslo`, `Europe/Stockholm`, `Asia/Kuala_Lumpur` and thirty-odd more — 38 of the cities in `lib/world_cities.dart` — so without `_kZoneLinks` (`time_zones.dart`) the picker silently offers a third of Europe's capitals, and a config naming one renders "Unknown time zone" for a name `localectl` and every airline ticket still uses. It is a **fallback**, consulted only when the database has no such name, so a link tzdata later splits back out is answered by the database. Embedding `latest_all` instead is the other fix and is worse: it carries 206 more pickable names, nearly all deprecated spellings of zones already listed (`Asia/Calcutta` beside `Asia/Kolkata`), and the package's API cannot say which of two identical zones is the current one — so the picker would have to show both.
- **The picker offers places, not just zones, and a `WorldClock` carries the label that makes that true.** The IANA database names *zones* — one representative settlement per offset history — so a picker built from it alone has no New Delhi (India is `Asia/Kolkata`), no San Francisco, no Boston and no Cape Town, which reads as a search that does not work rather than as a database that names things differently. `worldTimeZoneNames` therefore adds every city in `lib/world_cities.dart` whose zone does not already carry its name — Tokyo, London and New York keep their one IANA row — and a city row carries `TimeZoneName.label`, which `_addWorldClock` writes into the entry: without it a user who picked New Delhi would get a clock titled Kolkata. Two things follow. A city whose zone this build's database does not know is **dropped** rather than thrown for, the `TomlReader` rule applied to data the shell ships, and `test/world_cities_test.dart` is what stops that degradation from quietly hiding a typo. And "already added" stays keyed on the **zone**, so adding New Delhi marks Mumbai and Kolkata as added too — a world clock is stored under its zone and the three of them are one clock showing one time.
- **The list is written straight back through `ConfigStore`; there is no store.** `DesktopStore` exists because the grid renders in N FlutterViews, because drag state is high-frequency and must not reach disk, and because it needs a signature guard against per-keystroke notifies. None applies here: one consumer in one window, and add/remove *are* the persisted events. `set` replaces the whole list — there is no append API, and mutating what `get` returned would neither notify nor save.
- **Nothing on this tab may repaint the panel behind it.** A `RenderObject` marked needing paint dirties everything up to the nearest repaint boundary, this surface had none, and the two things it does most often are exactly the two that used the whole of it: a day cell tinting under the pointer, and a second hand. Both re-recorded the entire overlay picture — forty-two cells, the dial's painter, both lists, the tab strip — and damaged the whole output, so the highlight visibly trailed the cursor across the grid. The cells own a `RepaintBoundary` each and the clock column owns one, and `test/calendar_tab_test.dart` counts the paints above a hovered cell to keep it that way. Two things follow for the next such fix. **The label is built outside the hover builder and handed in as a child**, so the rebuild the boundary contains is a decoration and not a paragraph — an identical child widget is one the framework skips outright. And **the column's boundary is above its `LayoutBuilder`, not around the three readouts**: changing a `Text` marks needs *layout*, layout stops at the nearest *relayout* boundary — the tightly-constrained `Column` — and that `Column` then marks *itself* needing paint on the way out, stepping straight over any boundary nested inside it. A repaint boundary contains a repaint; only a relayout boundary above it contains a relayout.
- **The world-clock list is a `ListView` with a fixed `itemExtent`, never a `Column`.** A `Column` overflows the moment the user adds one clock more than the column is tall, and no widget test would catch it because the test picks the count. The dial gives way under a `LayoutBuilder` for the same reason — it shrinks with the column and is dropped altogether under 340px, leaving the digital readout, which says the same thing in a fifth of the height: `overlayPanelSize`'s last clamp is against the output's own height, so a short display yields a panel under the 800x500 minimum. **The column's two lists share what is left equally.** `CalendarClockColumn.footer` is `Expanded` with the same flex as the clock list, so the timers section is half of the space below the dial rather than a strip along the bottom of the month grid — the composer is a labelled field and two buttons, which is a column of controls and not a band. Both lists grow with what the user put in them, so an equal share is the only division that does not privilege whichever was given a fixed height; and `kClockColumnWidth` went to 280 to fit a duration field, two buttons and an entry's three controls across it.

### Timers and stopwatches (`lib/timers/`)

The section under the calendar's world clocks starts countdowns and stopwatches; whatever is running is rendered beside the time in the clock module and can be paused, reset or stopped from either place. Several can run at once, in which case the bar collapses to one icon and a count whose popup carries every entry and its controls.

| File | Responsibility |
|------|----------------|
| `timer_format.dart` | `formatTimerDuration` and `parseDurationInput` — pure, Flutter-free, the `overlay/calendar/month.dart` discipline, so the readout and the three input shapes the field accepts (`5`, `1:30`, `1h30m`) are both plain unit tests. |
| `timer_store.dart` | `ShellTimer` + `TimersStore.instance` — the singleton `ChangeNotifier`, same shape as `OsdStore`/`TrayStore`, plus the notification a finished countdown posts. |
| `timer_widgets.dart` | `TimerRow` (one entry and its three controls), `TimerComposer` (the labelled field and the two Start buttons), `TimersPane` (the calendar section), `TimersPopupContent` (the bar popup) and `TimerBarIndicator` (what sits next to the clock). |

Six things a change here has to keep true:

- **Nothing is persisted, and no service is started.** A countdown restored across a restart is either wrong — the shell was down for longer than it had left — or a surprise, and a stopwatch that survived one measures nothing anybody asked it to. Timers are runtime state like the OSD's, so there is no config schema, nothing in `[modules.clock]` to load, and nothing for `main()` to await. The calendar tab's "starts no service" property survives this feature.
- **Stopping removes; pausing does not.** "Stopped" is what makes an entry stop rendering in the bar, so `stop` is a removal rather than a third state. A paused entry has to stay visible — it is the only thing the user can resume from — so a "stopped" state that also stayed in the list would leave the clock module needing its own rule for which non-running entries still count.
- **Elapsed time is derived, never accumulated.** An entry holds the time banked by previous runs plus the instant the current run began, and every readout is a subtraction against the wall clock; the ticker's only job is to ask for a repaint. A ticker that added its own period instead would drift by however late each wakeup was and would lose the whole of a suspend. A backwards clock step (NTP, a resumed laptop) is dropped rather than subtracted, so a readout can stall but never runs backwards.
- **The ticker exists only while something is counting.** `_syncTicker` starts and stops it off every mutation, so an idle shell wakes for this store exactly never — the `SystemStatsStore` lease discipline, applied to a store whose consumers cannot hold leases. It notifies four times a second rather than once: the readouts show whole seconds, but the entries are aligned neither to each other nor to the wall clock, so a one-second period would leave a countdown's own boundary up to a full second late.
- **One entry is a readout, several are an icon.** Spelling out two countdowns and a stopwatch in a panel is a bar module that re-lays the whole panel every second; and the single readout is tabular-figured and zero-padded for the same reason. Either way the tap opens the same popup, which is where the controls are — that is what lets the bar pause and stop a timer without the overlay being opened at all. The clock module closes that popup when the store empties, because the button it is anchored to has just rendered itself away.
- **The field arrives with a duration in it, and the pane's own content scrolls.** `kDefaultTimerDuration` seeds the composer with `5:00` and a started timer puts it back there rather than emptying it, so the primary button is live on arrival and the common case is one click; the accepted forms sit beside the field's label, because a bare box with a placeholder was not telling anyone that `1h30m` parses. There are no preset chips — a row of them is a second way to say what the seeded field already says, and it cost the entry list a line. The pane's composer is the *first item of its list*, not a header above it: the section is half a column whose height follows the output's, so on a short display that half can be shorter than the composer is tall — as a header that overflows, as an item it scrolls, and the rows keep their fixed extent either way.
- **Both surfaces render the same `TimerRow`, and the pane takes `active`.** A control added to the row is a control the calendar page and the bar popup both grow; a second copy is how they drift apart. `TimersPane.active` is required for the reason `CalendarTab.active` and `SystemTab.active` are — the overlay body is an `IndexedStack` that keeps every tab alive, and a pane that subscribed unconditionally would re-lay its rows four times a second behind whatever tab the user moved on to.

### On-screen indicator (`lib/osd/`)

The OSD is the card that appears when volume, microphone volume, or brightness changes: an icon for what changed and a bar for its level, bottom-centred on every monitor, fading out after a period of inactivity.

| File | Responsibility |
|------|----------------|
| `osd_store.dart` | `OsdStore.instance` — the singleton `ChangeNotifier` the card watches, same pattern as `NotificationStore`/`TrayStore`. It holds **one** `OsdRequest`, so a `show()` replaces whatever is on screen; that is what makes brightness supersede a still-visible volume bar instead of stacking a second card. `visible` going false is the cue to fade out; the card answers with `onFadeOutComplete()`, which clears `current` and lets the host drop the window. |
| `brightness_monitor.dart` | Reads `/sys/class/backlight/<device>/{brightness,max_brightness}` and watches the `backlight` udev subsystem for change events — the same event-driven approach `modules/battery.dart` takes with `power_supply`. The sysfs root is injectable so tests never touch the real `/sys`. |
| `osd_service.dart` | `startOsdService()` (from `main()`) wires the sources into the store. Volume and mic come free from the existing `PulseClient` subscription (`onSinkChanged` / `onSourceChanged` / `onServerChanged`); the service seeds last-known levels at startup and only shows the card on an **actual** change, because PulseAudio emits sink events for unrelated reasons (a stream connecting, a port switch) that would otherwise flash the card. |
| `osd_audio_tracker.dart` | `OsdAudioTracker` — which devices are the default ones and what level each was last seen at, and the decision of whether an event is worth a card. Its own type because `startOsdService` owns a live `PulseClient` no test can drive, and because the names and the levels have to move together; `test/osd_audio_tracker_test.dart` pins it. |
| `osd.dart` | `OsdWindow`, the card itself. Uses the `reverse().then(...)` fade-out handshake `SettingsOverlay` uses. |

Volume and mic reach the store over `PulseClient`'s subscription, and `lib/pulse_client.dart` runs libpulse in its own isolate. Four things a change to that driver has to keep true, because getting any of them wrong is invisible until an *external* volume change (the keyboard's knob, `pactl`) silently stops arriving — a change made *through* the client always works, so the bug hides:

- **`dispatch` is not optional after `prepare` succeeds.** `pa_mainloop_prepare` asserts `state == STATE_PASSIVE` and `abort()`s otherwise, and only `pa_mainloop_dispatch` puts the loop back into that state. Bailing out between the two — on a poll error, say — means the *next* `prepare` takes the whole shell down with SIGABRT rather than returning an error. The one value that may skip it is `-2`, "quit requested", which parks the loop in `STATE_QUIT` for good; `_dead` exists so the driver never touches it again.
- **A productive `dispatch` means keep cycling, not yield.** Delivering one external volume change takes several cycles back to back: read the subscription event, flush the `get_sink_info_by_index` its callback issued, read that reply. Re-arming through `Timer.run` after the first of those strands the rest — which is exactly what `9338ade` did, and why only shell-initiated changes reached the OSD. `_cycle`'s rule is stated on the pair (poll result, dispatched count): work → keep cycling; `poll > 0` with nothing dispatched → the wakeup pipe, so yield and let `_handleMsg` run; both zero → idle or `EINTR`, so **retry in place**. That last case is the anti-spin one — `pa_mainloop_poll` maps a signal-interrupted `ppoll` onto "returned, nothing ready" and does not retry, and the Dart VM's thread interrupter fires at 1 kHz under `flutter run`, so re-arming on each turned an idle 20 Hz loop into an ~820 Hz spin worth 7 of the shell's 9% idle CPU.
- **A default-device move is reported on the `SERVER` facility and on no other.** Neither the device being left nor the one being adopted emits a sink/source event of its own, and every consumer in the shell filters events by device *name* — so a `PA_SUBSCRIPTION_EVENT_SERVER` case that does nothing (which is what it was) does not read as a dropped event. It reads as the volume module and the OSD deciding to stop reporting, for the rest of the session, from the moment the user picks another output in settings; and worse, the module's slider goes on writing to the device that was left. `_ServerChangedEvent` carries the re-read `PaServerInfo` out to `onServerChanged`, and the two consumers re-resolve on it. Re-resolving is not a pair of setters: the name and the level baseline have to be committed together (`OsdAudioTracker.seed`, `SoundControlState._adoptDefaultSink`), or an event landing between the queries is measured against the *other* device's level — which flashes a card for a change nobody made.
- **`pa_mainloop_wakeup` is worth calling but cannot be relied on.** The pipe it writes has no `pa_io_event`, so the wake is invisible to `dispatch` and only the `poll > 0, dispatched == 0` rule notices it; and `prepare` drains that pipe unconditionally, so a byte written while the isolate is between turns is swallowed. A request that loses that race just waits for the message queue.

Requests cross the isolate as one generic `_Request(id, kind, args)` / `_Reply(id, payload)` envelope — adding one is a `_ReqKind` member, a `_handleMsg` case, and a one-line client method; only unrequested pushes (device changes, level frames, the ready handshake) have classes of their own, named `*Event`. And a volume write is always as wide as the device: the isolate caches channel counts per sink/source name as their infos arrive, because `pa_cvolume_set` at a hardcoded width sets the wrong volume on mono and surround devices — invisible on the stereo default.

`tool/pulse_spike.dart` is how this is verified, and the reason `pulse_client.dart` imports no Flutter: it exercises subscribe → dispatch → stream against the real server with no engine to draw with. Run it, change the volume from anywhere else, and it exits non-zero if nothing arrived; it reports default-device moves too, which is the only way to see the `SERVER` facility working. `GRACEFUL_PULSE_LOG=1` turns on `pulseLog` (`lib/pulse_log.dart`) in both isolates — it gates on the environment rather than on a hook `main()` installs, because a top-level assignment would not cross the isolate boundary.

The windows are owned by `_GracefulShellRootState` (`lib/main.dart`) alongside the background, not by a panel module — the indicator is not tied to any panel. They exist only while `OsdStore.current` is non-null: the shell has no input-region support, so a permanently-mapped overlay surface would swallow clicks. For the same reason the window is kept tight around the card (`kOsdWindowSize`), anchored to the bottom edge only, which also lets layer-shell centre it horizontally for free.

### System monitor (`lib/system/`, `lib/overlay/system/`)

`lib/system/` is the UI-free sampling layer, shared by the `SystemMonitorModule` bar widget and the overlay's **System** tab. Every reader takes its `/proc` and `/sys` roots as constructor parameters — the same shape `BrightnessMonitor` uses — so tests point them at a temp directory and never touch the real ones.

| File | Responsibility |
|------|----------------|
| `models.dart` | `CpuSample`, `MemorySample`, `LoadAverage`, `NetSample`, `DiskUsage`, `ProcessRaw` (raw counters, what crosses the isolate boundary), `ProcessRow` (the resolved view row), `HistorySample`. |
| `proc_reader.dart` | The cheap reads: `/proc/{stat,meminfo,loadavg,uptime,cpuinfo,net/dev}` and `/sys/class/thermal`. Six small files, so they stay on the UI isolate. |
| `process_reader.dart` | The expensive `/proc/<pid>/stat` walk, plus the **pure** `computeProcessRows` that resolves two raw snapshots into rows. |
| `process_sampler.dart` | The seam between the store and the walk. `IsolateProcessSampler` runs it in `Isolate.run`; tests inject a synchronous fake and never spawn an isolate. |
| `process_killer.dart` | Signals processes, with the guards. |
| `disk_reader.dart` | `df -B1 -P` behind an injectable runner, on its own slow cadence. |
| `history.dart`, `format.dart` | Ring buffer for the graphs; byte/duration/temperature formatting. |
| `system_stats_store.dart` | `SystemStatsStore.instance` + `startSystemStatsService()` — same singleton `ChangeNotifier` pattern as `OsdStore`/`TrayStore`. |

Four things a change here has to keep true:

- **Leases, not timers.** The store polls only while somebody holds a lease. A *light* lease (CPU, memory, temperature, load, network) is what the bar module holds for its lifetime; a *detail* lease adds the per-process walk and is held only while the System tab is the visible tab. There is one sampler for the machine — before this, a two-monitor setup ran two independent `/proc` walks. Because the bar module holds a light lease from start-up, the history buffer is already full when the tab is first opened, so the graphs draw populated. The battery, network and weather modules follow the same rule with their own stores (`BatteryStore`/`NetworkStatusStore`/`WeatherStore`, each in its module's file): one poller per machine, leased by the widgets, configured through the module's `fromMap`. A `Timer.periodic` in a widget `State` is the anti-pattern all four of these exist to prevent.
- **The process walk runs in an isolate; the arithmetic does not.** `Isolate.run` returns raw tick counters and the store diffs them on the UI isolate. That keeps the delta pure and unit-testable, and it is what lets the sampler be stateless.
- **`comm` in `/proc/<pid>/stat` can contain spaces *and* parentheses.** Splitting the line on whitespace is the classic bug; `parseStatLine` anchors on the **last** `)`.
- **Kills are keyed on `(pid, starttime)`, never on the PID alone.** A process can exit and have its PID recycled between the row being drawn and the user confirming — a start-time mismatch refuses the signal. `ProcessKiller` also hard-refuses the shell's own PID (killing it takes every panel down) and PID 1; both refusals live in the killer, not the UI, so they cannot be bypassed. There is no automatic SIGTERM→SIGKILL escalation: an editor answers SIGTERM with a save prompt, and killing it five seconds later would destroy the user's work, so the grace period only *offers* a force-quit.

`lib/overlay/system/` is the tab: `system_tab.dart` (Overview / Processes sub-tabs, and the lease), `overview_page.dart`, `process_table.dart` (sort, filter, kill), `kill_confirm.dart`, `time_series_chart.dart` (a `CustomPainter` area chart — there is no charting package), and `stat_tile.dart`. `lib/usage_bar.dart` holds the fill bar both the tab and the bar module's popup use.

### Application launcher (`lib/launcher/`, `lib/modules/launcher.dart`)

A centred search card on a full-screen overlay layer-shell window, opened by `Ctrl+Space` (configurable under `[shortcuts]`) or by the magnifier bar module. It searches installed applications, offers each one's desktop-entry *Actions* in a flyout, and answers a typed mathematical expression or a typed quantity (`1kg`, `72f`, `5 km to mi`) in a row above the results.

| File | Responsibility |
|------|----------------|
| `launcher_controller.dart` | `LauncherController.instance` — the seam between the two entry points and `_GracefulShellRootState`, which owns the window. Same shape as `LockController`. Deliberately *not* `InputTriggerStore`: that store reports compositor triggers and its listener toggles on any notification, so a second signal there would open the settings overlay instead. |
| `app_index.dart` | `AppIndex.instance` + `startAppIndexService()` — the process-wide app list, built at start-up and refreshed from a `GAppInfoMonitor` "changed" signal (the `MonitorWatcher` pattern). |
| `app_search.dart` | Pure ranking: exact > prefix > word-start > substring, weighted name > generic name > keywords > id. `SearchableApp` folds case once at index-build time. |
| `expression.dart` | The calculator, over `math_expressions`. `looksLikeExpression` is the load-bearing half — without it `e`, `pi`, and `42` all "evaluate". |
| `unit_convert.dart` | The converter: the unit table, `parseQuantity`, `convertQuery`, and `peersFor` — which units a bare quantity is answered in. Pure, so the table and the peer choice are plain unit tests. |
| `launcher_overlay.dart` | The card. Takes its app list and launch callbacks as parameters, so widget tests never touch GIO. |

Nine things a change here has to keep true:

- **The window is created with no `monitor:`.** `layer_shell` then omits the `wl_output`, and miracle places shell surfaces on its *focused* output, which it retargets whenever the pointer crosses a monitor boundary — so the launcher appears where the user is. `_openSettings` does the opposite and pins to the first monitor.
- **Clicking the backdrop must dismiss.** The shell has no input-region support, so this surface swallows every click on the monitor, including the bar button that opened it. Without dismiss-on-backdrop a mouse-only user has no way out.
- **`Focus` nests *inside* `DefaultTextEditingShortcuts`.** Key events propagate upwards from the focused node, so the lower handler gets first refusal — that is what lets Up/Down/Enter/Escape win while Backspace and the arrows still edit text. Right only opens the flyout when the caret is collapsed at end-of-text, or it would make the caret unmovable.
- **The actions flyout is a `Stack` child, not an `OverlayPortal`.** Rows have a fixed `itemExtent`, so its position is arithmetic against the scroll offset. An `Overlay`'s entries do not rebuild on `setState` (see `overlay/overlay.dart`), which would be a trap for content that changes on every keystroke.
- **`AppIndex` does not share its `AppEntry`s with `modules/app_directory.dart`.** That widget unrefs its own list in `dispose`; sharing would unref `GAppInfo*`s the index still holds. For the same reason the root brackets the launcher's lifetime with `acquire()`/`release()`, which defers a refresh while rows are on screen.
- **The converter's gate is `looksLikeExpression`'s twin, and the two cannot both fire.** A conversion is a number and a unit with nothing between them, which is the one shape the calculator's gate refuses outright — so the two rows are mutually exclusive *by construction* rather than by the order `_onQueryChanged` tests them in. The strictness is the calculator's and it is there for the calculator's reason: every keystroke is also an app search, so `7zip`, `1password`, `x11-utils`, `gtk2-engines` and `2 apps` have to come back null, and `test/launcher_unit_convert_test.dart` walks that list.
- **Which units a bare quantity is answered in is a choice made for the reader, not for the arithmetic.** `1kg` is a question about pounds, so a peer from a *different* system is listed first; within each group the peer nearest a human-sized number leads, with a value **below** 1 counted at three times the distance of one above it, because `0.125 d` and `180 min` are the same three hours and only one of them is a number somebody says out loud. A conversion outside `[kReadableMin, kReadableMax]` is dropped — `1 mm` in miles is the row spending a quarter of itself saying "very small" — but never all of them, because a row that renders nothing is the shell deciding the user did not want an answer. And the list is capped at `kUnitPeerLimit`: the row is a glance, not a table sitting on top of the results it introduces.
- **A specialist unit is reachable only by being asked for.** A knot is the right answer to `100 kph in knots` and the wrong first line of `100 kph`; nautical miles and gradians are the same. Each is the nearest-to-human-sized peer in its dimension, so each would otherwise *lead* every bare query in it — the ordering rule being right about the arithmetic and wrong about the reader. `ConvertibleUnit.specialist` is that exception, and it costs the unit nothing else: it still parses, still converts, and still answers when named.
- **Every ambiguous spelling is decided in the table, and the awkward one is `in`.** It is both inch's symbol and a conversion keyword, which is why the split is done over whole *tokens* and tried from the right until both halves parse — `5 in in cm` and `5 cm in in` both land. The rest: `m` is metres and minutes are `min`; `t` is the tonne and a short ton is spelled out; `oz` is mass and fluid ounces are `fl oz`; there is no bare `d`, because `3d` is somebody looking for a modeller; and kelvin is the one **case-sensitive** alias, so `300 K` converts while `10k` stays the thousand it was meant as. Temperature is also the one dimension whose conversions are affine rather than a ratio — hence the `offset` field, and hence its opting out of the magnitude ordering, which would throw away the freezing point of water for being too near zero.
- **The row answers; it does not act.** Nothing is selectable in it, Enter still launches the highlighted application, and the converted value is rendered rather than put anywhere — the calculator's contract, and the reason both rows can appear above a live result list without stealing the keyboard from it. Six significant figures rather than the calculator's twelve (`formatResult` grew the parameter for this): a conversion factor is a measurement, and `2.20462262185 lb` claims an accuracy the question never had.

### Emoji picker (`lib/emoji/`)

A centred search card over a scrim, in its own full-screen layer-shell window, opened by `Ctrl+Shift+E` (`[shortcuts] open_emoji`). Type to search, move with the arrow keys, **Enter** copies the highlighted emoji and closes, **Escape** or the backdrop leaves with nothing copied. The launcher's shape — a `SignalController` seam, a root-owned `_OverlayWindow`, a `FadeOverlayScaffold` — and the third overlay to take it.

| File | Responsibility |
|------|----------------|
| `emoji_data.dart` | `Emoji`, `EmojiCategory` and `kEmoji` — the table, embedded as a Dart constant. Flutter-free. |
| `emoji_search.dart` | `SearchableEmoji`, the lazy `searchableEmoji` fold, and the fuzzy `rankEmoji`/`scoreEmoji`/`scoreEmojiField`. Pure, so the ordering is a plain unit test. |
| `emoji_controller.dart` | `EmojiPickerController.instance` — `LauncherController`'s seam, verbatim. |
| `emoji_clipboard.dart` | `copyTextToClipboard` over `wl-copy`, behind an injectable runner, answering a `ClipboardResult`. |
| `emoji_picker_overlay.dart` | The card, the grid, the key handling, and the pure `emojiGridMove`. |

Nine things a change here has to keep true:

- **The table is a constant, which is what keeps "the shell ships no image assets" true one file over.** `theme/builtin_themes.dart` embeds the shipped palettes as TOML and `tux/tux_art.dart` embeds a penguin as SVG source for the same reason: nothing in the shell resolves paths relative to the bundle, so a table read from a share dir would work under `flutter run` and not under `make install` or the snap. Unicode's own `emoji-test.txt` is the obvious alternative source and it is the wrong one twice over — four thousand entries to page through for a smiley, and CLDR *names* alone, where what the search here is for is the **keywords** a person types ("lol", "shrug", "wfh"), which no upstream file supplies.
- **Every dimension is searched, and that is the feature rather than a nicety.** Not a preferred field with the rest as tie-breakers, which is `launcher/app_search.dart`'s model: 🍕 is reached by its name, by its *category* ("food"), by any keyword ("italian"), and by pasting the character back in. The weights are absolute — `_kBand` is wider than every tier inside it, so the vaguest hit in the name still outranks an exact hit in a keyword — and the character is matched **only exactly**, because a query that happens to share a code unit with an emoji means nothing.
- **Fuzzy is a subsequence, and Space is deliberately not a copy key.** A key `_onKey` takes never reaches the field at all — the Linux embedder forwards a key to the input method only when the framework did not take it — so binding Space would cost every query its spaces and leave a name typeable only as one word. Enter copies instead, and the search then handles both halves: a query may carry spaces and its words need only appear *in order* ("face joy" finds "face with tears of joy"), while typing straight through a name still works and `gfws` still finds "grinning face with sweat". A literal hit always beats a scattered one (`_kFuzzy` sits above every literal tier), so the fuzzy pass only ever *adds* rows, in the order it found them, and never reorders the ones a substring already answered. `rankEmoji`'s **trim** is load-bearing once Space reaches the field: `"face "` is a state every two-word query passes through, and no field is folded with a trailing space, so without it the grid would empty on the keystroke between the words.
- **The spread is greedy-leftmost, not optimal.** Finding the tightest packing of a subsequence is a dynamic program over the whole table on every keystroke; the leftmost match already separates "thumbs up" from "trumpet sound", which is the ordering the number exists to make. It is bucketed into `0.._kFuzzySpreadMax` so one extra character between hits can never outweigh a better dimension.
- **The grid is a fixed column *count*, never a width.** That is what makes every keyboard move plain arithmetic (`emojiGridMove`, public so `test/emoji_picker_test.dart` pins it) rather than something needing a layout pass, and it is what stops Down landing on a different emoji per monitor. The rule inside it is invisible in a screenshot and easy to lose: a vertical move that would leave the grid lands in the nearest row it can, **in the same column** — one rule serving both Up/Down and PageUp/PageDown, because on the first row Up is already in that column and so holds (never wrapping round to the other end) while PageUp from the middle travels to the top. The column is given up only for a ragged last row that has no cell in it, where the **last** cell is the landing, because arriving nowhere reads as the key being broken. The delegate takes `mainAxisExtent` rather than an aspect ratio for the same reason — the row height is what `_scrollSelectedIntoView` does arithmetic on, so it has to be the constant.
- **The selection is a notifier, and nothing about a pointer moving over the grid may reach the card.** The ring follows the pointer — entering a cell selects it — and a `MouseRegion` fires enter and exit as the *content* moves under a stationary cursor as well as the other way round, since Flutter re-runs the hit test after any frame that changed the annotations. So a scroll with the pointer anywhere over the grid moves the selection on **every frame of it**. Held as a `State` field written with `setState`, which is the obvious spelling, each of those frames rebuilt the whole card: the `OverlaySearchField` and its `EditableText`, the grid's delegate, and with it every one of the seventy-odd cells on screen — which is what made scrolling this grid cost what it did. `_selection` is a `ValueNotifier<int>` instead and `_EmojiCell` subscribes to it, `setState`ing only when its **own** flag flips, so the move costs the two cells it moved between plus the footer that names the selection. That is `_SelectedIcon`'s shape in the desktop grid, and `test/emoji_picker_test.dart`'s *pointer cost* group pins it the way `desktop_grid_test.dart` pins that one — on widget **identity**, which is the only thing that separates a rebuilt subtree from a repainted one. Three smaller rules travel with it. A cell does **not** go through `HoverRegion`, the shell's primitive for exactly this shape and the wrong tool here: entering a cell *is* selecting it and the ring is what says so, so the `bool _hovered` that primitive exists to own would be a second rebuild per cell, on enter and again on exit, for a value nothing paints — the `GestureDetector` still carries an explicit `behavior:`, which is what that rule actually requires. The glyph is built once and handed back unchanged, so ringing a cell updates a `DecoratedBox` and does not shape the paragraph again (the calendar tab's "hand the label in as a child" rule). And an unselected cell's decoration is **null** rather than a transparent border, because a `Border` at zero alpha is still a stroke asked for on all seventy cells; the glyph does not move when one appears, since the inset is symmetric and the child is centred.
- **The grid carries a repaint boundary, and the cells' own are only half the job.** A scroll marks the viewport needing paint and that mark travels up to the nearest boundary, which — the sliver delegate's per-child boundaries being *below* it — was the window itself: every scrolled frame re-recorded the search field, the footer and the full-output scrim along with the grid. The boundary around the `GridView` is what stops it on the way out. The same delegate is told `addAutomaticKeepAlives: false` and `addSemanticIndexes: false`: a fling builds cells by the hundred, nothing in a cell has state worth keeping alive off screen (the selection is the picker's, not the cell's), and `kExcludeSemantics` drops every window in the shell out of the semantics tree anyway. The repaint boundaries stay — they are what a scroll reuses rather than re-records.
- **A keystroke scores the category once per *group*, and the shared term list is what makes that legal.** The category is the widest of the three dimensions — a label, its extra terms and the label's own words, seven or eight strings against a name and a handful of keywords — and there are nine of them against six hundred rows, so scoring it per row was more than half the work of every character typed. `_categoryTerms` folds it once for the enum and every `SearchableEmoji` in a group holds *that* list, which `rankEmoji` then memoises on `EmojiCategory.index`; `test/emoji_search_test.dart` pins the sharing, because a constructor that went back to folding per emoji would leave the memo answering for terms it had not scored. Two allocations went with it. The word splitter is one top-level `RegExp` rather than one compiled inside a collection-for for each of the six hundred rows — that fold happens inside the first frame of the picker's window, so it was the startup cost. And the word-start needle `' $query'` is built once per query rather than once per *field*, which over the whole table was several thousand throwaway strings per keystroke; `_subsequenceSpread` walks code units for the same reason, `[]` on a `String` being an allocation per character in the innermost loop of the one pass that runs over every field the literal tests have already refused.
- **A copy closes without the exit animation.** `LauncherOverlay`'s call, for a sharper version of its reason: the whole point of this window is to put something on the clipboard and get out of the way of the field the user is about to paste into, and every frame it spends fading is a frame that surface does not have the keyboard back. Escape and the backdrop *do* play it — nothing is waiting on those.
- **The copy is `wl-copy`, and a missing one is a message rather than a silence.** Flutter's own `Clipboard` is not the route, for the reason `capture/capture_grab.dart` documents for screenshots: a Wayland client cannot set the selection without a seat and a serial, and the shell's surfaces are layer-shell ones. The MIME type carries its charset, because a receiver offered a bare `text/plain` may read it as Latin-1 and paste a smiley as four bytes of mojibake. The failure is reported by the **root**, through the notification store and not in a card that has already closed, and it names the *package* (`wl-clipboard`) and never a package manager — `lib/fortune/`'s rule about `fortune-mod`.

The search field itself is `OverlaySearchField` (`lib/overlay_search_field.dart`), extracted from the launcher's private copy when this wanted the same control: the settings library's rule that a control the library lacks gets *added to the library*, applied one layer out, because the `RenderEditable` mouse wiring in it is thirty lines a second hand-rolled copy would have got subtly wrong.

### Screen sharing (`lib/screencast/`, `lib/wayland_ffi/`, `lib/pipewire/`, `lib/native/`)

The shell **is** the xdg-desktop-portal ScreenCast backend. When an app asks to share the screen, xdg-desktop-portal forwards the request here, a layer-shell overlay asks the user which monitor or window to share (with live previews of each), and the chosen sources are captured with `ext-image-copy-capture-v1` and published as PipeWire video streams. All of it is pure `dart:ffi` — no C in the repo.

| Layer | Files | Responsibility |
|-------|-------|----------------|
| Native shims | `native/glib_source.dart`, `native/libc.dart`, `native/ffi_util.dart` | `GlibFdWatch` (`g_unix_fd_add`); `memfd_create`/`mmap`/`memcpy`; the shared dlopen plumbing (`processLibrary`, `openFirstLibrary` soname fallback, the one `g_signal_connect_data` binding). `packages/ext_session_lock` keeps its own copies — it cannot import the app package without a cycle. |
| Wayland FFI | `wayland_ffi/wl_ffi.dart`, `wl_types.dart`, `wl_interfaces.dart`, `wl_proxy.dart`, `wl_protocols.dart` | libwayland-client bindings, the `wl_interface` graph, listener vtables, and typed proxy wrappers. |
| Capture | `screencast/capture_connection.dart`, `capture_host.dart`, `capture_session.dart` | The registry/outputs/toplevels, and one continuous capture per source. `capture_host.dart` is the process-wide owner of that connection, shared with the shell's own screenshot and recording features — see below. |
| PipeWire | `pipewire/pw_ffi.dart`, `spa_pod.dart`, `spa_constants.dart`, `video_stream.dart` | libpipewire bindings, SPA pod build/parse, and the video-source stream. |
| Portal | `screencast/screencast_portal.dart`, `screencast_service.dart`, `pick_types.dart` | The `org.freedesktop.impl.portal.ScreenCast` objects and the engine wiring them to capture. |
| UI | `screencast/picker_controller.dart`, `picker_overlay.dart`, `picker_sources.dart`, `preview.dart` | The consent overlay and its live previews. |

Seven things a change here has to keep true:

- **The capture path needs its own Wayland connection, over libwayland.** `package:wayland` (what the rest of the shell uses) cannot pass file descriptors — its `writeFd`/`readFd` are stubs — and `wl_shm.create_pool` requires one. `WlDisplayConnection` is a second connection through `libwayland-client.so.0`, which does SCM_RIGHTS natively. Precedent for a second connection: `lib/overlay/settings/display.dart`.
- **Everything below the UI is Flutter-free, on purpose.** `pick_types.dart` exists so the portal, engine, capture and PipeWire layers import no Flutter, which is what lets `tool/screencast_spike.dart` exercise the entire stack as a `dart compile exe` binary — the only way to test this against a live compositor, since the picker overlay needs a Flutter engine. Keep new non-UI code Flutter-free; use `screencastLog` rather than `debugPrint`.
- **One thread, two fd watches.** The Dart UI isolate runs on the GLib main thread (see `lib/monitor_watcher.dart`), so `g_unix_fd_add` on the capture display fd and on `pw_loop_get_fd` is enough to drive both — no `pw_thread_loop`, no isolates, and every Wayland and `pw_stream` callback lands on the Dart thread, which is what makes `NativeCallable.isolateLocal` correct throughout. In a process with no GLib (the spike) the watch fails and the owner pumps manually; `PipewireVideoStream` registers itself in `_manuallyDriven` for exactly that.
- **Only the ext protocols are hand-transcribed.** Core interfaces (`wl_output`, `wl_shm`, `wl_buffer`, …) come from libwayland's exported `wl_*_interface` data symbols, so they carry no transcription risk. `test/wl_interfaces_test.dart` diffs the hand-written tables against the XMLs in `protocol/` — a wrong signature is memory corruption inside libwayland, not an exception, so that test is the guardrail. Copy new protocol XMLs into `protocol/` and extend the test.
- **The compositor paces the stream, not a timer.** After `ready` the session immediately creates the next frame; `ext-image-copy-capture` holds the copy until the content actually changes. That is why a static screen produces no frames — and why the spike needs something moving on screen. Previews are the exception: they pass `minFrameInterval`, because the picker runs a session per monitor *and* per window at once.
- **Dismissing the picker is a denial, not a deferral.** Backdrop tap, Escape, `Request.Close`, and a superseding request all resolve the pick with null, which becomes portal response 1. The decline-when-unheard rule (`hasListeners` false → immediate null) is inherited from `RequestController` — a backend that could answer without a visible consent surface is a backend that can silently record the screen. `startScreencastService` takes its `SourcePicker` as a required parameter for the same reason: there is no default.
- **`impl` version is 2, and the frame path never copies through Dart.** Version 2 predates restore/persist tokens (4) and virtual monitors (5), so the frontend never sends options this backend would have to understand. Frames go from the shm mapping to a `pw_buffer` with a libc `memcpy` on two raw pointers; previews take one bulk copy into a reusable `Uint8List` and decode via `ImageDescriptor.raw` with `PixelFormat.bgra8888` (XRGB/ARGB8888 are byte-identical to BGRx/BGRA little-endian), never a per-pixel reorder loop.

Install: `portal/graceful-shell.portal` and `portal/graceful-shell-portals.conf` go to `XDG_DATA_HOME` and `XDG_CONFIG_HOME` via `make install-portal` — not `PREFIX`, which xdg-desktop-portal does not search. The conf is only written when absent, so a user's existing backend preference is out-ranked (a `{desktop}-portals.conf` beats the generic one) but never overwritten. The snap adds a machine-wide copy under `/usr/share/xdg-desktop-portal/` from its install hook and does the restart itself — see the packaging section above for why both halves exist. There is no D-Bus activation file: the shell owns the name from session start, so screen sharing cannot start the shell.

The backend the shell **displaces** is `org.freedesktop.impl.portal.desktop.wlr`, which `/usr/share/xdg-desktop-portal/portals/{mir,miracle}.portal` claim by default. That happens at the config layer only. Never try to own or replace that bus name: it cannot be taken without `allowReplacement` from its current owner, and those `.portal` files claim `org.freedesktop.impl.portal.Screenshot` on it too — an interface this shell does not implement, so taking the name would break screenshots. The shell requests its own, `kScreencastBusName` (`screencast_service.dart`), with `doNotQueue`, and nothing else contends for it.

Verification, since none of this can be tested from the shell binary alone:

```sh
dart compile exe tool/screencast_spike.dart -o /tmp/spike
WAYLAND_DISPLAY=wayland-99 /tmp/spike                     # globals, outputs, toplevels
WAYLAND_DISPLAY=wayland-99 /tmp/spike --capture           # frames from each output
WAYLAND_DISPLAY=wayland-99 /tmp/spike --multi             # N sessions on one source
WAYLAND_DISPLAY=wayland-99 /tmp/spike --pipewire          # prints NODE_ID=<n>
WAYLAND_DISPLAY=wayland-99 /tmp/spike --portal            # the real backend, auto-accepting
python3 tool/portal_client_test.py [--window|--cancel]    # drives the portal contract
```

`--portal` grants every request without a picker (there is no Flutter engine to draw one), so it is a protocol harness, not a security-equivalent run.

Ten things a change here has to keep true:

- **There is one `CaptureConnection` in the process, and it is `CaptureHost`'s.** `startScreencastService` used to create and own it, which was right while the portal backend was the only thing capturing; a second owner would mean a second registry, a second `wl_shm` and a second copy of the foreign-toplevel list against a compositor that advertises one of each. `lib/screencast/capture_host.dart` (deliberately still Flutter-free — `tool/screencast_spike.dart` compiles that whole layer) memoises the connect, fans `onDied` out to both features, and **clears the connection when it dies**, so a compositor restart costs one failed capture rather than every capture for the rest of the session. A screenshot and a live screen share on the same source at once are fine; concurrent sessions were verified against miracle-wm when the picker's previews were built.
- **A window is captured through its own handle when there is one, and by cropping its output when there is not.** The two halves of the window picker come from different protocols with no id in common: miracle's tree is the only thing that says *where* a window is (so it is the only thing that can draw a rectangle under the pointer), and `ext-foreign-toplevel-list-v1` is the only thing the capture stack can turn into a source that follows it. `matchToplevel` joins them on `app_id` and title and **refuses to guess** — an ambiguous pair answers null and the caller falls back to the crop. A rectangle that stops following a window the user moves is a disappointment; recording somebody's *other* Firefox window is a leak. The join happens at the shutter rather than at the pick, because a configured delay sits between the two.
- **A connector is an identity only while both ends have one, and the corner is the pass behind it.** Every layer of this feature keys an output on its `wl_output.name` — miracle's tree, the capture connection, and the selection surface, which is handed GDK's connector for the monitor it was created on. Two of those three strings can be missing for reasons that have nothing to do with the display: GTK3 learns a connector from `xdg-output` and reports none when the compositor has no manager for it, and `wl_output.name` is a version 4 event a compositor below that never sends. Either gap leaves one end holding an empty string, two empty strings match nothing, and the result is *every* capture on the machine — area, window and screen alike — failing with "the display is no longer connected" about a display the user is looking at. So `CaptureTarget` carries the output's top-left corner in global logical pixels as well, `indexOfCaptureOutput` (`capture_source.dart`) and `resolveScreenOutput` (`window_targets.dart`) both take name → corner → lone-display passes, and the last two consider only outputs the *name* could not have answered for — a named output that is not the one asked for has already said "not me", so a display genuinely unplugged between the pick and the shutter still resolves to nothing rather than to whichever screen has since moved into its corner. `resolveOutput` (`display_provider.dart`) is the same rule one connection over, and the reason its own second pass exists.
- **Selection is logical, capture is physical, and the factor comes from the buffer.** miracle's rects and a layer-shell surface's layout are in the compositor's logical pixels; a captured frame is in the output's physical ones. `CaptureRect.scaledInto` is the only place that converts, and it derives the scale from the frame it is handed rather than from the output's advertised `scale`: a fractional-scaled output reports 1.5 and returns a buffer at whatever rounding it settled on, and a crop off by that rounding shows a sliver of the wrong window down one edge. It maps the two *edges* rather than the origin and the size, so adjacent crops can neither overlap nor leave a seam.
- **Only the surface's own size decides an area, which is what makes the feature work with the IPC socket down.** A layer-shell surface anchored to all four edges *is* the output, so its constraints are the output's logical size — exactly the space an `AreaCapture` crop is expressed in. A whole screen needs only the connector, which the panel already knows. So a miracle connection buys the *window* mode its rectangles and nothing else, and `CaptureScene.empty` is a first-class state rather than an error.
- **One `GET_TREE` for the machine, taken once when the selection starts.** The selection surfaces are a window per output and each would otherwise open its own round trip. It is also right that the snapshot does not update: the rectangles the user is pointing at have to be the ones being drawn, and a window that opens behind a full-screen selection surface cannot be clicked through it anyway.
- **The selection surface has no entrance and no exit animation, and its teardown schedules its own frame.** Every other overlay in the shell fades; this one is a tool, and a fade-in is a moment in which a drag the user has already started goes to a surface that is not listening. The exit matters more — the shutter fires the instant this comes down, so a fade-out would photograph a half-transparent copy of the selection surface, rectangle and banner included. The `closing` handshake is still honoured and resolves on the next frame, and that next frame has to be **asked for**: `addPostFrameCallback` requests none, nothing on this surface animates, and the closing notifier does not even rebuild it — `WindowTeardown`'s rule, and without the `scheduleFrame` the surfaces stay up for ever. `test/capture_selector_test.dart` pins it, because a test binding's `pump` also does nothing without a scheduled frame.
- **The settle between the surfaces coming down and the shutter is a fixed wait, because nothing reports the alternative.** A layer-shell surface is not gone when its controller is destroyed — `WindowTeardown` waits for Flutter to let go of the view and the compositor then has to recomposite the output without it — and no frame callback, protocol event or signal says when that has happened. So `kSelectorSettleDelay` is a wait, and the root answers `CaptureSelectionController` from `_onSelectionClosed` rather than at the click, so the wait starts from the teardown.
- **The recorder writes at a constant rate off the wall clock, and pins its geometry at the first frame.** `ext-image-copy-capture` is event driven — the compositor holds each copy until the content changes, which is what makes the screencast path cost nothing on a still screen — and ffmpeg's rawvideo demuxer has nowhere to put a timestamp, so handing it only the frames that arrived would render a minute of somebody reading a document as a fraction of a second. The canvas holds the newest frame and is written `fps` times a second whether or not anything moved, and how many writes are *owed* is computed from the elapsed time rather than counted per tick (`lib/timers/`'s rule: a late timer would otherwise shorten the file by however late it was). Both dimensions are rounded down to even, because every encoder here converts to `yuv420p`, which cannot represent an odd one and an area drag very often is. A window resized mid-recording is clipped into the canvas it started in rather than ending the recording. Writes are copied (`IOSink.add` does not copy, so handing it the canvas would let the next frame tear the one being written), pooled, and bounded to `_maxInFlight`, so an encoder slower than real time drops frames instead of growing the sink's queue without limit.
- **A missing external tool is a message, not a silence.** `ffmpeg` and `wl-copy` are the two, and neither is a Dart package: recording without ffmpeg says so and names the package — never a package *manager*, the rule `lib/fortune/` states about `fortune-mod` — and a screenshot with no `wl-clipboard` still writes the file and says in its notification why it could not also be pasted. Under the classic snap both resolve on the host `PATH` like every other host binary, so neither is staged. Every other failure — a source that went away, a frame that never came, a directory that cannot be written to, an encoder that refused — is a `CaptureException` carrying a sentence, which lands both in a notification and in `CaptureStore.error`, where the module's own menu shows it: the notification may well have expired by the time the user comes back to the icon to find out what happened.

The stores follow the shell's lease-shaped rules without being leased: there is one `CaptureStore` for the machine, so the recording readout on every monitor's bar shows the same clock and any of them stops the same recording, and its one-second ticker exists only while something is recording (`TimersStore._syncTicker`). Both modules push their config into it from `fromMap`, `system_monitor.dart`'s side-effecting shape, because the shutter may be fired from a monitor whose panel does not carry the module. The selection surfaces are root-owned and per-monitor like the OSD's windows, and modal with the two consent pickers: a full-screen surface that has taken the pointer must not be dismissed by something else wanting the screen.

### Background window (`lib/background.dart`)

Renders a full-screen wallpaper with time-of-day scheduling and crossfade transitions using `media_kit` for video support. One background window is created per monitor.

`MediaBackground({path, fit})` is the public "render this image or video" widget, shared with the lock screen; the image/video split is decided by extension (`isVideoPath`), and the `media_kit` `Player` lifecycle (muted, looping, disposed on unmount) lives entirely inside it.

**The wallpapers the machine already ships come from `lib/wallpaper_catalog.dart`, and never from the config.** `SystemWallpaperCatalog` walks `backgrounds/` and `wallpapers/` under every `$XDG_DATA_DIRS` entry — which is the one pair of names Ubuntu, Fedora, Debian, Arch, Mint, Pop, elementary, openSUSE and every KDE spin have agreed on, so enumerating distributions is not needed — plus the shell's own `graceful-shell/` share dir and the two pre-convention layouts (`desktop-base`, `pixmaps/backgrounds`). `_BackgroundSectionState` merges the result into the Available grid under whatever `[[background.entries]]` holds.

Four things a change here has to keep true:

- **Discovery must not write.** Seeding these paths into `[[background.entries]]` at first run is the obvious alternative and it is worse three ways over: the user could then delete them, a release upgrade replacing `f41-01-day.png` would leave a dead path until the auto-prune noticed, and every fresh config would carry tens of lines nobody typed. Reading them on each visit is what makes "cannot be deleted" a property of the *design* rather than a check in the UI — there is nothing behind the tile to delete.
- **Removal exists, and is offered on user-added tiles only.** With the machine's own wallpapers in the list, "hidden" stopped being a synonym for "gone", so a mistaken pick from the file picker would otherwise sit in Available forever. `_WallpaperRef.removable` is the whole rule (`onRemove: null` draws no button), and it is keyed on catalogue membership rather than on how the path got into the config — picking a system wallpaper through the file picker does not make it the user's to delete, because it would come straight back on the next build.
- **Deselecting a catalogue wallpaper drops its entry rather than flipping `shown` to false.** It is listed in Available either way; a hidden entry would show it twice and leave an undeletable path in the file.
- **The walk is bounded, because every tile decodes an image.** `maxDepth` stops a symlink into `/` (or `~/.local/share/backgrounds` pointed at a photo library) from turning a settings visit into a disk crawl, `maxEntries` caps the grid, and a KDE wallpaper package (`<Theme>/contents/images/1920x1080.png`, `…/3840x2160.png`, …) collapses to its largest resolution — a dozen identical previews per theme is not a list.

### Desktop icons and widgets (`lib/desktop/`)

A configurable grid of pinned items — `.desktop` entries, files and folders — and of **widgets**, which occupy a rectangle of cells rather than one, drawn on the background surface over the wallpaper. Double-click opens (an app launches; a file or folder goes to its default handler, which for a directory is the file manager), single click selects, **dragging on bare desktop rubber-bands a selection box over everything it touches**, drag rearranges — **dropping one icon on another swaps them**, and dragging one of several selected icons moves the whole group. Right-click gives a real popup menu; right-clicking bare desktop offers Add application / Add file or folder / **Add widget** / Organize / Change background.

Sixteen things a change here has to keep true:

- **The background surface now exists for two reasons, and `needsRestart` signs the *decision*, not its causes.** `_hasBackgroundSurface` (`main.dart`) is `background.entries.isNotEmpty || desktop.enabled`, so icons work with no wallpaper — and in that case the surface must render `SizedBox.expand()`, **not** `BackgroundWindow`, whose empty state is an opaque `0xFF1A1A1A` fill that would black out a desktop the compositor was painting. `ConfigStore._restartSignature` encodes `bg:<either>` rather than two parts, so enabling the grid on a config that already has a wallpaper does not demand a restart.
- **The grid must clear the panels, and it is the only thing on that surface that does.** The surface calls `spanFullOutput` (exclusive zone −1) so a translucent bar has wallpaper behind it, which means it reaches *under* the bars. `panelInsetsFor` sums each panel's `height + panelMargin` onto the edge its anchor names; the margin is read live from `ThemeScope`, so a theme change that re-floats the bars re-insets the grid on the same frame with no listener of its own. That works only because the background window is now wrapped in `ThemeProvider`.
- **Nothing in `build` may touch GIO.** `loadAppByPath` **refs** what it returns and `iconNameForItem` guesses a content type; both are resolved once per change of the item set in `DesktopLayerState._syncResolved`, which disposes the previous entries after installing the new ones (the `DockState._loadApps` contract). Resolving in `build` leaks one `GAppInfo` per frame. Every GIO call there is also wrapped in a `try`, because `flutter_tester` does not link GLib — the fallback is a font glyph, which is also what a machine with no icon theme gets.
- **`DesktopStore` splits persisted from ephemeral, and never reads `ConfigStore.appConfig`.** Items and geometry are written back; selection, drag and in-flight rename are not and must never reach disk. Every `ConfigStore.set` notifies synchronously, and every window in the shell has a `LiveConfigProvider` listening, so a drag persists once **on drop** — routing pointer positions through the config would wake every surface on the machine dozens of times per gesture, and reach the disk besides. (Before `LiveConfigScope` a `set` rebuilt every panel on every monitor outright; the cost is smaller now, but the rule is the same and the disk write is unchanged.) `_onConfigChanged` compares a signature and early-returns, because that listener fires on every keystroke anywhere in the settings UI.
- **Dragging is hand-rolled, and selection comes from a `Listener`.** Flutter's `Draggable` requires an `Overlay` ancestor, which a background-layer surface has no business hosting; the ghost is another `Stack` child and the drop resolves through `nearestCell` + `moveItemTo`. Selection is painted from `onPointerDown` rather than `onTap`/`onTapDown`: registering `onDoubleTap` makes `onTap` wait out the double-tap window, and `onTapDown` is still deferred until the tap recognizer beats the pan, either of which leaves the highlight visibly lagging the click. That pointer-down now fires **only when the pressed icon is not already selected** — pressing a member of a band selection to drag the group must not throw the group away first — and narrowing a multi-selection back to one happens on the completed `onTap` instead. The double-tap delay that argument is about therefore still never costs the *first* highlight anything; all it defers is dropping the *other* highlights.
- **The rubber band shares the background's `GestureDetector`, and never calls `beginDrag`.** Its pan recognizer goes on the same `Positioned.fill` that already owns `onTap`/`onSecondaryTapDown`, *under* the icons. `RenderStack` stops hit-testing at the first child that absorbs and the tiles are `HitTestBehavior.opaque`, so a press on a tile never reaches it and the band and the icon drag are never in one arena. The arena supplies the rest for free: a press with no movement lets `onTap` win and clear the selection, so there is no threshold to hand-roll; and `PanGestureRecognizer` is primary-button only, so `onSecondaryTapDown` still opens the empty-space menu. Three things that are not free — `dragStartBehavior: DragStartBehavior.down`, or the pending slop delta is folded into the reported start and the band's corner jumps away from the press; `selectAll` compares sets before notifying, because it runs on every pointer move and this store is watched by every monitor's surface; and **no `beginDrag`**, because `isDragging` is what lights the grid lines and the lines exist to show where an *icon* will land. The band is a `DecoratedBox`, not a painter — `DesktopGridLines` is a painter because it strokes `columns × rows` rects, and `desktop_grid_test.dart` asserts it is the only thing on the `CustomPaint` path.
- **The band hit-tests the *rendered* list; the group move resolves against the *authored* one.** `targetsInRect` is given the output of `reflowIntoGrid`, so the box catches what the user can see. The drop then measures its delta from the rendered anchor and hands it to `moveItemsBy`, which translates the group **rigidly** — the delta is clamped by the group's bounding box, not per item, or an overshoot would pile the whole selection into one edge cell — and displaces bystanders into the cells the group vacated. That is exactly `moveItemTo`'s swap when the group is one icon, which is why the single-item drop still goes through `moveTo` (an absolute cell) and only a real group takes the delta path. `removeItems` exists for the same reason `_commit` is called once per drop: N removals must be one `ConfigStore.set`, not N.
- **Renaming borrows the keyboard, and gives it back.** The surface is created `keyboardMode: none`, so an `EditableText` on it would never see a key event. `DesktopLayer` asks the root (`_setDesktopKeyboard`) to flip that one monitor's surface to `onDemand` for the duration of a rename and back afterwards — including from `dispose`, so a monitor unplugged mid-rename cannot leave a surface holding focus. It is not simply left `onDemand`: a full-output background surface that can take focus would let a stray desktop click steal it from the focused application. The toggle is cached and force-committed for the reasons `setPanelMargin` documents.
- **"Add application…" is a list, not a file picker, and it pins a *path*.** The chooser reuses `AppIndex` and `rankApps`, so it gets keyword matching for free and pays nothing to build. Its rows hold `GAppInfo` pointers the index owns and whose refresh unrefs, so every host brackets it with `AppIndex.acquire()` / `release()` — the contract `_openLauncher` follows. `AppEntry.filename` (`g_desktop_app_info_get_filename`, transfer-none) is what gets stored, because `DesktopItem.target` is a path in every case; an entry with no filename is filtered out of the list rather than offered and then refused. The desktop opens it as a root-owned overlay-layer window and the settings pane through `showAppChooser` into its own `Overlay` — the same split as `FilePickerController` vs `showFilePicker`, and for the same reason.
- **The file picker cannot live on this surface.** `showFilePicker` inserts into the nearest root `Overlay`; on the background layer that modal would be drawn underneath every application window and every panel. `FilePickerController` (`lib/overlay/file_picker_controller.dart`) asks the root for an overlay-layer window instead, and declines immediately when nothing is listening — the rule `ScreencastPickerController` follows, so a headless run never awaits a window that will not appear.
- **A widget is a second list, not a wider icon, and `[[desktop.widgets]]` is keyed on an instance id.** An icon is identified by *what it points at*, is exactly one cell, and is what "Organize" compacts; a widget is identified by a generated `id` (two clocks are two widgets, and there is no path to name them by), spans a rectangle, and **organize must never move one** — reflowing a 2x1 media player into the icon flow is nonsense, and a widget the user placed deliberately is not clutter to be tidied. Merging the two lists behind one type is the tempting refactor and it loses every one of those distinctions. Ids are made unique at parse time (`DesktopConfig.fromMap`), because two widgets answering to one id would move together and remove together.
- **The two lists meet in exactly one place: a `blocked` set of cells.** `widgetCells` produces it and every icon helper takes it — `placeItem`, `moveItemTo`, `moveItemsBy`, `organizeItems`, `reflowIntoGrid` — so an icon is never placed, dropped, flowed or rendered where the user could not see or click it. The direction of precedence is deliberate and asymmetric: an *icon* in a widget's way is displaced (`displaceItemsFrom`, in the same commit), because an icon has somewhere else to go and nothing about it is lost by moving it, while a *widget* in an icon's way refuses the drop, because there is no exchange of places to make between a 1x1 and a 2x1. Refusing whole is also what a group drop does — moving the members that fit and leaving the rest would break the arrangement the user was preserving by dragging them together.
- **A widget mutation commits both lists at once, and `_commit` guards against its own notifications.** Adding, moving or resizing a widget can displace icons, so `DesktopStore._commit` takes both and writes both. Every `ConfigStore.set` notifies synchronously, so the `items` write would otherwise send `_onConfigChanged` straight back in to re-parse a subtree still holding the *old* widgets — a state that never existed, published to every monitor's surface. The `_committing` flag is what stops that; without it a single add also notifies three times.
- **Span limits belong to the type, are applied at render time, and hold the corner the user is not dragging.** `DesktopWidgetSpec.minSpan`/`maxSpan` are clamped through `spanFor`/`renderAreaFor` rather than written back, so a config authored while a widget allowed 6 columns survives a release that lowers the maximum — and comes back at full size if it is raised again. During a resize the clamp keeps the *opposite* corner pinned (`_applySpanLimits`), or the widget would slide out from under the pointer on reaching its limit. An unknown type has no spec and is therefore left exactly as authored, and renders as a placeholder rather than being dropped: the entry stays in the config, so there is still something to right-click and remove, and an upgrade brings the real widget straight back.
- **Nothing a pointer does per frame may cost what the desktop holds.** Two things on this surface run at pointer rate, and both used to be a walk of everything pinned to it. The rubber band's hit test was a scan of every icon per `onPanUpdate`; it is `DesktopBandIndex` (`desktop_layout.dart`) now — the grid makes an icon's cell its address, so the columns and rows a band spans are arithmetic on the rect and only the icons seated in that block are looked at, which is a cost proportional to what the band *selects*. And a rebuild recomputed both reflows and the `widgetCells` set behind them, which is the half that grew with the **widgets**: each one takes cells out of the icon flow, so `reflowIntoGrid` probes a larger blocked set for every icon before a single tile is laid out. `DesktopLayerState._layoutFor` memoises all of it, keyed on the identity of the `DesktopConfig` — which is a complete and O(1) answer, because `DesktopStore` replaces that object on every mutation and never edits one in place (`_commit`, `_reload` and `_onConfigChanged` all assign a fresh one, and the last early-returns on an unchanged signature). That is what makes the two notifications that arrive per frame — a band crossing an icon, a drag crossing a cell — change the selection and nothing else. `_syncResolved` takes the same key for the same reason: it runs on every store notification and its fallback builds a list of every target to compare. Two things follow. The index is built from the list the grid is *rendering*, `reflowIntoGrid`'s output, or the band would select what the config authored rather than what the user can see; and its range arithmetic is a **superset** narrowing that `Rect.overlaps` still decides, so the strict-touch semantics cannot drift with the divisions — `test/desktop_layout_test.dart` fuzzes the two against each other and pins the seat count.
- **A pointer moving over the desktop is not an event about the desktop.** The bullet above made a band's *own* work proportional to what it selects; what it left behind was everything else the layer rebuilt on the way past, which is what a `setState` on `DesktopLayerState` means — every icon tile and every widget card, and the cards measure their own text as they build (`fitFortuneText` walks a ladder of `TextPainter` layouts, the weather card's `_Sections` measures every row it might draw). Two things were doing it, and both are per-tile now. **Hover was a field on the layer**, and `MouseRegion` fires enter and exit with the button held down — `RendererBinding.dispatchEvent` passes a null hit-test result for every `PointerMoveEvent` precisely so the tracker re-runs the hit test — so a band dragged over a populated desktop rebuilt the whole layer twice for every icon it crossed, and merely *moving the mouse* across the desktop did the same. It is `HoverRegion`'s now, which is what that primitive exists for. And the **icon selection** was read from `build`, so `selectAll` — which the band calls on every pan update — rebuilt everything for each icon that entered or left the box; `_SelectedIcon` subscribes per tile and `setState`s only when its own flag flips, `DesktopStore.selectAll`'s guard applied one level down. What is left in `_syncLayerState` is the store state the layer itself renders — the config's identity, the drag flags, the picked widget, the open rename — and every one of those moves once per gesture rather than once per pointer move. Two corollaries. The band's existing tests drive a **touch** pointer, which is why they never saw the hover half at all; `test/desktop_grid_test.dart`'s *pointer cost* group uses a mouse and asserts on widget *identity*, which is the only thing that can tell a rebuilt tile from a repainted one. And a rebuild avoided is not a repaint avoided: nothing on this surface was a repaint boundary, so a mark that reached the layer re-recorded the wallpaper's full-output image scale and every icon's label shadow with it. The wallpaper, each tile and each card own one now — the calendar tab's rule, and `RepaintBoundary` is the answer here for its reason.

Verified against a live miracle: an `xdg_popup` parented to a background-layer surface stacks **above** both the panels and ordinary application windows, so the menus need no top-layer fallback.

**A widget is dragged from anywhere on its card, and that is what its own controls survive.** The card carries a pan recognizer and the widget's buttons carry tap recognizers deeper in the same tree, so a press that does not move resolves as the button's tap and one that does resolves as the drag — the `ListView`-with-buttons arrangement, and `desktop_widget_grid_test.dart` pins both halves. It follows that a widget must not put a *pan*-driven control (a seek slider, say) on its card without taking the drag somewhere else first. The card is dragged itself rather than by a ghost, unlike an icon — an icon's ghost exists because a group moves together and each member needs one — so `DesktopWidgetPreview` is what says where the drop lands, and the grips (`DesktopWidgetResizeGrip`) are drawn only while the widget is hovered, selected or in flight, because a desktop widget spends nearly all its life being looked at.

### Lock screen (`lib/lock/`, `packages/ext_session_lock/`)

**Lock** in the system module's power menu locks the session with the `ext-session-lock-v1` Wayland protocol. The compositor then hides every other surface — the shell's own panels included — and, per the protocol, blanks any output that has no lock surface, so a monitor we fail to cover is never *exposed*, only blank.

The lock surface is a **new window-controller type**, not runner C code. `packages/ext_session_lock/` is a standalone package that does for `ext-session-lock-v1` what `layer_shell.dart` does for wlr-layer-shell: it `dlopen`s `libgtk-session-lock.so.0` and binds six functions. `SessionLockWindowController` mirrors `LayershellWindowController._internal` almost line for line, except that where the layer-shell one calls `gtk_layer_init_for_window()` it calls `gtk_session_lock_lock_new_surface(lock, window, monitor)` — and, like layer-shell init, **that must happen before the window is realized**.

It depends on `layer_shell` only to reuse the generic GTK/Flutter FFI wrappers and to subclass `ExtendedWindowingOwnerLinux`, so lock windows register into the *same* `LinuxWindowRegistrar` as every other window. `initSessionLock()` (called from `main()` in place of `initLayerShell()`) calls `initLayerShell()` first and then swaps in the subclass, which is why panels and popups are unaffected.

| File | Responsibility |
|------|----------------|
| `lock_controller.dart` | `LockController.instance` — the seam between the Lock button (deep in a panel's tree) and `_GracefulShellRootState` (which owns every window). Same singleton-`ChangeNotifier` shape as `OsdStore`/`TrayStore`. |
| `session_lock_host.dart` | `SessionLockHost` — owns the `SessionLock`, the per-monitor lock windows, hotplug-mid-lock, and the detach → unlock → destroy teardown ordering, on behalf of the root (which keeps only: react to `LockController`, build a `SessionLockWindow` per `windows` entry, and call `dispose`, which abandons rather than unlocks). |
| `lock_screen.dart` | The UI: wallpaper via `MediaBackground`, clock/date, account name, and the reveal-on-any-key password field that blurs the wallpaper behind it. |
| `pam_authenticator.dart` | PAM over `dart:ffi`. |
| `user_identity.dart` | `getpwuid(getuid())` for the account name PAM needs and the GECOS name the UI shows. |

Five things a change here has to keep true:

- **Lock windows are created undecorated, before realize.** gtk-layer-shell calls `gtk_window_set_decorated(FALSE)` itself; the gtk-session-lock fork does not, and a decorated GTK3 window draws its CSD titlebar *inside* the lock surface. `SessionLockWindowController` makes the call explicitly.
- **Lock windows exist only while locked**, like the OSD windows and unlike the panels — `_GracefulShellRootState` creates one per monitor on request and destroys them on unlock, including for monitors hotplugged mid-lock.
- **Order teardown as detach → unlock → destroy windows, and unmap the role before each destroy.** Destroying a GTK window while Flutter still renders into its `FlView` is a use-after-free, so the views are detached a frame first. The unlock comes next — `unlockAndDestroy()` syncs with the compositor before anything else is torn down, matching gtk-session-lock's own example. Then, inside `SessionLockWindowController.destroy()`, `gtk_session_lock_unmap_lock_window()` runs before `gtk_widget_destroy()`: GTK destroys the `wl_surface` on unmap but gtk-session-lock only destroys the `ext_session_lock_surface_v1` in the window's finalizer, and Mir answers a surface dying before its role by deleting the role server-side — the finalizer's trailing destroy then hits an unknown object and the compositor kills the connection (`Error 22 dispatching to Wayland display`).
- **Never unlock on the way out.** `dispose()` drops the lock object without sending an unlock: if the shell is dying while the session is locked, the session must stay locked. The protocol guarantees exactly this — a client that disconnects without `unlock_and_destroy` leaves the session locked.
- **PAM's conversation callback is `isolateLocal` and the whole exchange runs in `Isolate.run`.** PAM invokes the callback synchronously on the thread that called `pam_authenticate`, and that call blocks for seconds on failure (`pam_unix` delays deliberately). The response array is allocated with the C allocator because PAM `free()`s it. This works unprivileged because `pam_unix` shells out to the setuid-root `unix_chkpwd`. An empty password is rejected before PAM is ever called, so an account configured `nullok` cannot be opened with a bare Enter.

### Authentication agent (`lib/polkit/`)

The shell is this session's **polkit authentication agent**, registered at start-up. polkitd never prompts anybody itself: when an application asks for a privileged operation whose action is `auth_admin` or `auth_self`, it looks for an agent registered for the caller's session and calls `BeginAuthentication` on it — and with **no** agent registered there is no prompt and no privilege, so every such call comes back `AccessDenied` immediately. That is the state `lib/keyboard/locale1_client.dart` documents having to word for the user today; registering an agent is what turns it into a question.

The prompt itself is one card in the middle of a full-output layer-shell surface in the shell's own theme — the eighth root-owned `_OverlayWindow` (`main.dart`), modal, and dismiss-on-backdrop like the two consent pickers.

| File | Responsibility |
|------|----------------|
| `polkit_types.dart` | `PolkitIdentity`, `parsePolkitIdentities`, `defaultIdentityIndex`, `PolkitAuthRequest`, `PolkitAuthOutcome`. Flutter-free (`package:dbus` alone, `locale1_client.dart`'s shape), so the identity parse is a plain unit test. |
| `agent_helper.dart` | The `polkit-agent-helper-1` line protocol and the process that speaks it, behind `PolkitHelperRunner`. Flutter-free. |
| `auth_session.dart` | `PolkitAuthSession` — one `BeginAuthentication`'s worth of state: prompts, retries, the identity switch, the outcome. |
| `auth_controller.dart` | `PolkitAuthController.instance` — the `RequestController` seam between the agent and `_GracefulShellRootState`. |
| `polkit_agent.dart` | `PolkitAgentObject` + `startPolkitAgentService()` — the exported `org.freedesktop.PolicyKit1.AuthenticationAgent` and the registration with the Authority on the **system** bus. Flutter-free. |
| `auth_dialog.dart` | `PolkitAuthDialog` — the card. |
| `polkit_config.dart` | `PolkitConfig` — `[polkit]`, beside the feature the way `power/power_config.dart` is; `config.dart` re-exports it. |
| `polkit_log.dart` | `polkitLog` — `lib/pulse_log.dart`'s shape, in its own file so the helper layer can report too without importing the D-Bus object. Never logs a prompt, a response or a cookie. `polkit_agent.dart` re-exports it, because `main()` is what points it at `debugPrint`. |

Eleven things a change here has to keep true:

- **The shell never authenticates anybody itself, and must not start.** The lock screen talks to PAM directly (`lib/lock/pam_authenticator.dart`) and this deliberately does not, because a polkit authentication is not "did this password check out" — it is *"tell polkitd that the holder of this cookie authenticated"*, and only the setuid-root `polkit-agent-helper-1` can say so. It runs the `polkit-1` PAM stack and then makes the privileged `AuthenticationAgentResponse2` call on the agent's behalf, which is why `SUCCESS` is answered by returning from `BeginAuthentication` with an **empty** reply: polkitd has already been told, and there is nothing left to send. An agent that ran PAM itself would have authenticated the user and still have nothing polkitd would accept.
- **The cookie goes to the helper on stdin, never in `argv`.** That *is* CVE-2015-3255: a cookie on a command line is world-readable through `/proc`, so any process on the machine could claim somebody else's pending authentication. The pre-0.113 argv form is not offered as a fallback, because a helper old enough to need it is a helper with the vulnerability. `PolkitAuthRequest.toString` drops the cookie for the same reason.
- **The subject is `unix-session`, and there is deliberately no fallback to `unix-process`.** A process subject registers the shell as the agent for its *own* authorizations alone, so every other application on the desktop would keep getting `AccessDenied` with a prompt sitting one window away — a state far worse to debug than no agent at all. No session id means the service throws and `ShellServices` records it as failed, which is truthful. `XDG_SESSION_ID` first (logind's PAM module sets it for every graphical session, and it is free), logind's `GetSessionByPID` second.
- **An agent already registered is a graceful decline; everything else throws.** polkitd allows one agent per session, and a desktop already running `polkit-gnome` or `lxpolkit` is one where prompts already work — so the shell yields, logs, and settles `ready`, the rule `startNotificationService` follows for its bus name. An unreachable system bus, no polkitd, or an export failure throws, so the status is not "ready with no prompts". `[polkit] enabled = false` is the opposite ordering: it lets a *later* agent win.
- **The helper is started by the dialog, never by the agent.** `PolkitAuthSession.start()` is called from `PolkitAuthDialog.initState`, so `RequestController`'s decline-when-unheard rule reaches all the way down to the process table: a request nobody is showing spawns no setuid process at all. A helper start that is superseded mid-flight is killed rather than adopted (`_generation`) — the alternative is a setuid process sitting on a PAM prompt for the life of the shell.
- **A retry is a new helper run, and PAM's own words beat the agent's.** The helper calls `pam_authenticate` once and exits, so a second password cannot go down the same pipe; three attempts is what every polkit agent has settled on (`kPolkitMaxAttempts`, and `[polkit] max_attempts` clamped 1–5). The prompt shown is PAM's own — a stack with a fingerprint or an OTP module is not asking for a password, and `PAM_PROMPT_ECHO_ON` must not be obscured — and a `PAM_ERROR_MSG` becomes the message, because "Account locked" is actionable where "that did not work" is not. A `PAM_TEXT_INFO` arriving mid-typing must not take what the user has typed: the field is emptied by a change of *attempt* and by nothing else.
- **Dismissing is denying, and every way out answers.** Escape, the backdrop, Cancel, the session lock sweeping the screen, a superseding request and shell shutdown all resolve to `PolkitAuthOutcome.cancelled` → `org.freedesktop.PolicyKit1.Error.Cancelled`, which is the one answer that does not make the caller ask again immediately. The window comes down through the `closing` handshake like every other overlay, and `_onPolkitPromptClosed` cancels a session the user never answered — a helper left on a prompt is a process nobody will ever talk to again. `PolkitAuthController.finish` is guarded on the session's **identity** rather than being a bare `complete`, because by the time a dialog has animated out a superseding request may be the pending one, and answering *that* with the outcome the user gave the last one would resolve a prompt nobody has seen.
- **A run nobody answered is not a failed attempt, whatever the helper called it.** This is the one that made the prompt *flash*: it appeared and was gone again inside a couple of milliseconds, too fast to read and far too fast to type into. `polkit-agent-helper-1` answers `FAILURE` to its **own** early refusals as well as to a password PAM weighed and rejected — `wrong number of arguments`, `needs to be setuid root`, and every `polkit-1` stack that denies before it opens its mouth (`pam_faillock` on a locked-out account is the everyday one) all print exactly that word, with the actual reason on *stderr*. Read as a wrong password it costs an attempt, so the dialog started a second helper, which refused the same way, and a third, and then closed on "Authentication failed". PAM cannot have refused an answer it was never given, so `PolkitAuthSession` turns on **`_answered`** rather than on the word: a terminal message for a run the user never typed into is `unavailable`, it retries nothing, and it carries the helper's own line. Two things follow. Retrying is not merely useless there but actively harmful — on a stack with `pam_faillock` in it those three refusals are themselves what locks the account, so the shell was manufacturing the state that makes the next prompt fail the same way. And the reason has to *survive* to the card: see the ordering rule below.
- **Nothing about a run's end may be read off one descriptor.** The helper's stdout, its stderr and its exit are three independent things and the event loop orders none of them, so every terminal decision waits for the ones that carry its answer. Finishing on the **exit** would drop a `SUCCESS` still sitting in the stdout pipe — an authenticated user reported as a wrong password, on a race that only ever loses on somebody else's machine — so stdout's own EOF is what ends a run and the exit is only the status plus a safety net for a stdout that never closes. Forwarding a **`FAILURE`** the instant its line arrives would drop the stderr line that says why, which is the whole of what an early refusal leaves behind, so a refusal (never a success, which needs no diagnosis and must not wait for one) is held until stderr is at EOF and travels with `PolkitHelperResult.detail`. Both waits are bounded by `_kExitGrace`, because a pipe that never closes has to cost the wording and never the run. `PolkitHelperDied` is the third shape — the helper ending with neither word — and is deliberately not a synthesised `FAILURE`: the two are indistinguishable at the wire and mean opposite things. `test/polkit_process_helper_test.dart` is where all of this is pinned, against real child processes speaking the line protocol, because no `PolkitHelperRunner` fake can reproduce an ordering.
- **Four outcomes, and only one of them lingers — and it is the only one that offers another go.** `authenticated`, `failed` and `cancelled` are answers to something the user just did, so the card goes; `unavailable` is news that nothing they typed caused — no `polkit-agent-helper-1` on the machine, no identity the agent can offer, or a run that ended without checking anything — so it stays, with its reason, a Close button and a **Try again**. Every cause of it can be gone by the time the card has been read (a `pam_faillock` window expiring, polkit installed, a stack fixed in another terminal) and the shell can see none of them happen, so the retry is the user's to trigger: `NotificationStore.retryDaemon`'s rule. It is the one place `outcome` goes back to null, which is safe because nothing has been told about it yet — the agent is awaiting `PolkitAuthController`, which the root only answers once the *window* comes down. Deliberately **not** offered over `failed`: that is PAM having weighed as many answers as the dialog allows and refused every one, and a button that sent it round again would leave a password oracle on the screen of a machine somebody has walked away from. The helper's path is searched by candidate (`/usr/lib/polkit-1`, `/usr/lib/policykit-1`, `/usr/libexec`, the multiarch and lib64 layouts), `lib/fortune/`'s `/usr/games` rule: a program that is present but unreachable must not be reported as missing, and the message names polkit rather than a package manager.
- **A `unix-group` identity is dropped, and a bad one costs that identity alone.** The helper authenticates *a user* and polkit does not say which member of a group it means, so groups are filtered out — libpolkit-agent draws the same line. A uid with no passwd entry, a missing uid, or a repeat is dropped rather than thrown for, and only a request with *nothing* left is refused (with a reason, not a prompt). The passwd lookup goes through `lib/lock/user_identity.dart` rather than a second `getpwuid` binding beside it. The dialog opens on the current user when polkit named them and never prefers root: an agent that opened on the root row would be teaching the user to type the root password at prompts they could have answered themselves.

polkitd restarting drops every registration it held and tells nobody, so `PolkitAgentService` watches `nameOwnerChanged` for `org.freedesktop.PolicyKit1` and re-registers — without it the shell would simply stop prompting, silently, for the rest of the session. `test/polkit_agent_test.dart` drives the D-Bus surface with the `screencast_portal_test.dart` harness, and `test/polkit_session_test.dart` drives every retry, cancel and identity switch through a `PolkitHelperRunner` that forks nothing. `test/polkit_process_helper_test.dart` is the exception that has to fork: `ProcessPolkitHelperRunner.path` exists for it alone, pointed at shell scripts speaking the helper's line protocol, because the pipe ordering above is the one part of the feature no fake can reach.

### Power button (`lib/power/`)

The machine's own power button, intercepted. A press opens the power menu by default — Lock, Log Out, Sleep, Restart, Shut Down over a full-screen backdrop — rather than powering the machine off where it stands, and `[power] key_action` is the whole policy: any one of those five verbs directly, or `"none"` to hand the key back.

| File | Responsibility |
|------|----------------|
| `power_config.dart` | `PowerKeyAction` + `PowerConfig` — `[power]`, beside the feature the way `weather/weather_config.dart` sits beside its store. `config.dart` re-exports it. |
| `power_actions.dart` | `PowerAction` — the five verbs, their labels and glyphs, `powerActionFor` (the `PowerKeyAction` → verb mapping), and `PowerActions.run`, the one place the session or the machine is actually acted on. |
| `power_controller.dart` | `PowerController.instance` — the `SignalController` seam between the Wayland-layer trigger and the root. |
| `power_inhibitor.dart` | `PowerInhibitor` and `LogindPowerInhibitor` — logind's `handle-power-key` lock, over the system bus. |
| `power_service.dart` | `PowerKeyService.instance` + `startPowerService()` — *when* the lock is held. |
| `power_menu_overlay.dart` | `PowerMenuOverlay` — the dialog, a sixth root-owned `_OverlayWindow`. |

Six things a change here has to keep true:

- **Intercepting the button is two halves, and one half alone is a bug rather than half a feature.** The compositor delivers the key (it is an ordinary `KEY_POWER`/`XF86PowerOff` press, registered like any other global shortcut through `[shortcuts] power_button`), but systemd-logind opens the ACPI power-button device *itself* and runs `HandlePowerKey` — `poweroff` on a stock system — whatever the compositor delivered to whom. A shell that only registered the trigger would draw its menu onto a machine that was already going down. `block` rather than `delay`, because delay is for work that must happen before the action and what is wanted is for logind never to act; the lock is released when the fd closes, crash included, so it cannot strand a machine that will not power off.
- **The lock waits for the compositor's answer, and that is what stops the button dying.** `InputShortcut.onOwnership` reports the trigger's `done`/`failed`/`unavailable` — and `reportUnregistered()` reports the compositor never advertising the protocols at all — into `PowerKeyService.setKeyOwned`. The lock is the *and* of that and the config — and of the config having been *published* at all, because the two arrive from services that race and a lock taken on the strength of the built-in default is one the user's own `inhibit_logind = false` had already refused. Inhibiting a key nobody answers is a power button that does nothing, which is worse than either behaviour on its own. It is also why `PowerInhibitor` is an interface — a unit test that took a real one would change what its host machine does when somebody presses the button.
- **The binding latches; the action does not.** Registration is one-shot at start-up (`InputTriggerManager._registered`), so `inputShortcutsFor` registers the power button whatever `key_action` says, `"none"` included — a binding skipped there would be one no setting could turn back on without a restart. What `"none"` costs instead is the inhibitor and the root's response, both read live: `_onPowerKeyPressed` reads `key_action` off `_liveConfig`, and `_onConfigChanged` pushes `[power]` into `PowerKeyService`, so switching the feature off in Settings gives the lock back on that keystroke.
- **The menu asks for no confirmation; the bar popup does.** They are the same five verbs (`PowerAction`), drawn twice, and the difference is how each is reached: the power menu appears *because* the power button was pressed, so answering it is already a second deliberate act, while a bar icon is one small target in a row of them where a mis-click lands on Shut Down. Hence `PowerAction.needsConfirmation`, which is every verb but Lock, and which only `modules/system.dart` consults.
- **Enter answers Shut Down, and the two ways out are Escape and the backdrop.** The fast path a physical button wants is press, glance, Enter, so the selection starts on Shut Down and the arrow keys (and hover, so the pointer and the keyboard cannot disagree) move it. Backdrop dismissal is not decoration: the shell has no input-region support, so this surface swallows every click on the output, and without it a mouse-only user has no way out of a menu they opened by brushing the case. The tiles are a `Wrap` for the same class of reason — five of them are 600px across and a small or rotated display is narrower than that.
- **`PowerActions.run` is the only thing that acts, and it is replaceable.** `PowerActions.runner` is a static because the three call sites — the bar popup, the menu, and the root acting on a configured verb — are each several layers from anything that could inject one, and because what a test needs is not a different runner but *no* runner. Lock goes through `LockController` like every other lock request; the rest go through `UbuntuSession` (which resolves to logind here) and, for suspend, `SystemdSessionManager` directly.
